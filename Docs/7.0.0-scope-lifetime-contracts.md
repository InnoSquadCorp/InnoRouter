# Runtime scope lifetime contracts (7.0 development)

## Identity and replacement

Persisted declaration paths and presentation/window IDs are not execution grants.
The Store owns a non-persisted UUID incarnation for every live node path. A scope
captures that incarnation once. Missing scopes capture no grant; creating their
path later never revives them. Repeated lookup of the same still-missing path
keeps its cached projection identity, separately from permission to mutate. Removed/replaced scopes project `nil` and reject
both relative actions and `performRoot` with `mutation(expiredScope(path))`.
Intentional application root requests use the owning Store directly.

The current value model has no logical instance ID on a plain `RouterNode`.
Therefore the explicit, minimal identity rule is:

- Ordinary actions and `.apply`/transactions **reconcile**. A retained path,
  node kind/container style, parent incarnation, and scene-root route retain
  their incarnation. Ordinary path, selection, badge, and detent edits do not
  expire retained scopes. Removing an edge or changing a node's kind/style
  expires that node and its descendants, not unrelated siblings.
- Snapshot restoration (including partial/recovered restoration) explicitly
  replaces runtime ownership for the complete restored Store state. Reusing
  persisted IDs does not reuse request authority.
- `store.replaceSubtree(at:with:context:)` explicitly replaces one subtree,
  including same-shaped/equal values. Its initially addressed scope must remain
  alive while the request is queued or deferred. It merges into the current
  tree at execution/rebase time, preserving unrelated state.
- Applying a feature plan explicitly replaces only that feature's owner
  subtree. Reacquire the feature's scope after replacement.

Replacement intent is independent of `context.source`, private request metadata,
carried through queue/policy/deferral/resume. Ordinary `.apply` cannot accidentally
become replacement merely because its source is labelled restoration. Value
inequality alone never means replacement.

Logical-ID validation remains unchanged: an active presentation UUID cannot be
reused with a different route, style, ownership path, or non-selection options.
Both restore and explicit replacement still run the reducer's continuity check.
For such a migration use a new logical presentation UUID; do not expect runtime
incarnation rotation to bypass logical graph validation.

## Admission and observation

The captured precondition runs before executable request preparation, after it,
after every policy/authorization suspension, and immediately before commit.
Deferred rebase preserves that original precondition. The existing prepared
candidate revision check remains; no submission-wide global revision fence was
introduced.

An equal-state restore/replacement still passes authorization and policies.
Only an allowed request rotates runtime ownership and retires old waiters. It
returns `unchanged`, makes no state assignment, and does not increment the state
revision. Rejection, cancellation, and unresolved deferral rotate nothing.

`scope(at:)` reads a per-path observable lifetime slot, so a mounted host can
reacquire a replacement scope even when state/revision did not change. Slots are
retained only by live cached scopes; the runtime identity map contains only the
current graph. Scene hosts reacquire scopes in their body. Ordinary sibling
mutations neither expire scope rights nor invalidate another path's lifetime
observation.

## Presentation ownership

Every awaited presentation has a distinct runtime waiter registration. Replacing
its owner, restoring its same UUID, or removing an outer modal retires old
result ownership exactly once as dismissal. Nested and still-deferred awaited
presentations are included. Old typed completion deferrals cannot dismiss a
restored presentation or supply their prepared value to it. Late cancellation
checks both waiter registration identity and captured child incarnation.
Native presentation/detent bindings capture the presentation-child incarnation,
so an old UUID-only callback cannot revive after remove/recreate.

## Scenario exactness

Actual Store request observations expose only a stable, payload-free
`replayLimitationCode`. Explicit ownership replacement, runtime-only callback
preconditions/preparation, and authorization configuration/intent are marked
unsupported until the portable replay contract can reconstruct them. Captured
scoped/feature callbacks are conservatively included; ordinary unguarded Store
actions and supported declarative history semantics are not blanket-rejected.
No runtime token or authorization grant is serialized. The Testing layer must
preserve the limitation and reject replay/source generation before execution;
a plain `.apply` replay cannot silently stand in for restore/replacement.

## Native boundaries and unverified behavior

Runtime incarnation is separate from native window/immersive lifecycle tokens.
Ordinary child edits and equal-ID restoration do not themselves change native
scene identity or request a native scene reopen.

Lifecycle modifiers capture both native lifetime and request ownership when the
content appears. Their content is keyed by runtime scope identity so explicit
replacement remounts scene-local content and acquires fresh ownership. This
**resets scene-local view ownership** and may reset local SwiftUI state. It is
not a claim that replacement has no UI lifecycle effects. Old disappearance
callbacks cannot dynamically recapture the new grant.

Linux tests exercise the actual Foundation/Observation Store and the pure native
callback synchronizers, including late old versus fresh current callbacks.
Native SwiftUI compilation/rendering, appearance/disappearance ordering, modal
bindings, real window/immersive effects, K1 native cancellation, and K2 mounted
split restoration remain Apple-unverified. Syntax parsing alone is not native
validation. The scene driver’s asynchronous platform-effect races remain part of
the separate native verification gate.

## Evidence and commands

The existing-API regression file is intentionally compilable against the
pre-fix engine. At baseline `9e67f602`, its 12 test functions ran: 11 failed on the
intended stale-authority/waiter invariants (33 assertion failures), and the
ordinary sibling/reconciliation control passed. There were no fixture setup
failures or timeouts. The same 12 functions passed after the fix.

Additional actual-Store contracts cover per-path observation, equal-state
state/revision preservation, feature replacement, intent-preserving deferral, preparation
ordering, unchanged logical-ID rejection, pending and completed waiter ownership,
registry cleanup, and pure scene callback ownership. Tests use Swift 6.4 strict
concurrency, warnings-as-errors, and `--no-parallel` through the engine runner.
The final focused run passed 31 functions: 25 lifetime contracts/regressions plus
all six existing `EnvironmentRouterStateTests`. The latter use the unchanged
read-only `RouterStateReader` declaration extracted from its native wrapper;
one old scope-array fixture was migrated to the typed `.branch` component.
Source responsibility budgets and formatter checks pass. Exact staged hashes
matched the working sources when the 31-function run completed.

```sh
python3 scripts/run-store-engine-contracts.py \
  --scratch /tmp/router-scope-contracts \
  --test-file RouterScopeLifetimeRegressionTests.swift \
  --test-file RouterScopeLifetimeContractTests.swift \
  --filter RouterScopeLifetime --warnings-as-errors
```

For the deliberate pre-fix failure control, compile only the existing-API
regression file so later unrelated test API additions do not mask the defect:

```sh
python3 scripts/run-store-engine-contracts.py \
  --scratch /tmp/router-scope-before \
  --runtime-source-revision 9e67f602 \
  --only-test-file RouterScopeLifetimeRegressionTests.swift \
  --filter RouterScopeLifetimeRegressionTests --warnings-as-errors
```

Each runner attempt archives exact staged source/test bytes, SHA-256 provenance,
and its complete log before restaging. Earlier failures remain available rather
than being overwritten by a passing run. This gate is not the full package or a
release gate, and does not establish native platform behavior.
