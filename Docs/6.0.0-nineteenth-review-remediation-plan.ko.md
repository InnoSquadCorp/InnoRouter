- **이전 완료 판정의 제한:** [18차 계획](6.0.0-eighteenth-review-remediation-plan.ko.md)과 [18차 증거](review-evidence/6.0.0-eighteenth-review.ko.md)의 Q01 전체 종료 보장은 재개방한다. AC03의 기존 테스트는 load 진입 후 navigation을 검증하므로, 예약 후 worker 진입 전 경계의 직접 증거는 별도로 보강한다. 이는 새로운 제품 결함 한 건을 추가한다는 뜻이 아니다.

## 3. 설계 결정

### D01 — 저장 명령의 수락 순서와 실제 I/O 순서를 연결

- **문제:** actor isolation은 상호 배제만 제공한다. 호출 우선순위가 다른 actor mailbox를 FIFO로 가정하면 삭제 뒤 old save가 실행된다.
- **제약:** 이미 실행 중인 동기 I/O의 강제 취소·rollback은 약속하지 않는다. 기존 수동 save의 관찰 수명 독립성과 pending resume의 commit 후 durability 계약을 유지한다.
- **대안 A:** actor 호출 전후 generation 검사만 추가한다. 저장 후 검사는 이미 쓴 파일을 되돌리지 못하므로 선택하지 않는다.
- **선택 B:** driver가 첫 관련 suspension 전에 명령 순서·수명을 예약하고, 명시적 per-driver queue가 유효 명령을 순서대로 drain한다. encode 완료·실패·취소는 예약을 ready 또는 skipped로 확정한다. 실제 storage에 미완료 명령을 여러 개 동시에 제출하지 않는다. 공통 coordinator는 두 storage protocol을 adapter로 연결하되 navigation state를 소유하지 않는다.
- **실패·복구:** 삭제는 이전 대기 save를 무효화하고 이미 시작한 I/O 다음에 실행한다. encode 실패·취소된 예약은 queue를 막지 않는다. remove 실패는 호출자에게 노출하고 삭제 완료로 표시하지 않는다. 성공한 삭제 뒤 새로 수락한 save는 정상 허용한다. 오래된 완료는 최신 status를 덮어쓰지 않는다.
- **검증:** reserve→encode→queue→storage start→completion의 경계에 save/save, save/remove, remove/save, cancel/resubmit을 배치한다. 메모리 상태뿐 아니라 실제 파일 bytes와 새 driver의 복원 결과까지 비교한다.

정확한 순서는 wall-clock이나 Task 생성 순서가 아니라 driver의 동기 예약 순서로 정의한다. queue에 들어간 durability 작업과 호출자의 기다림을 구분하고, 대기 취소가 이미 수락한 필수 삭제를 유실시키지 않게 한다. pending resume의 Store commit은 저장 실패를 이유로 되돌리지 않는다. 구현 전 상태 전이표에 수동·자동 save와 삭제의 반환·취소 규칙을 기록한다.

### D02 — 초기 restore phase를 표시 status와 분리

- **문제:** `status == .loading`으로 미완료 restore를 판정하므로, 동시 save가 status를 덮으면 재시도 권한이 바뀐다. 실패한 save만이 아니라 진행 중이거나 성공한 save도 `.saving`을 거치므로 같은 손실을 만든다.
- **제약:** 기존 generation·claim·host/manual owner 보장과 최신 navigation 보호를 유지한다.
- **대안 A:** loading 이외 status도 나열해 didAttemptRestore를 복구한다. status 조합이 늘어날 때 같은 문제가 반복되어 선택하지 않는다.
- **선택 B:** 초기 복원 phase를 미시도·진행 중(lifetime)·완료/명시적 중단으로 표현하고, owner 종료 원인에 따라 전이한다. 저장 성공·실패·표시 상태는 이 phase를 변경하지 않는다.
- **실패·복구:** 마지막 owner 취소·자연 detach는 미완료 초기 복원을 재시도 가능하게 한다. 다른 owner가 남으면 공유 작업을 보존한다. 명시적 stop 뒤 재관찰 정책, 이미 완료한 restore의 재실행 금지, stale worker 무효화를 유지한다.
- **검증:** save 성공/encode 실패/I/O 실패 × caller 취소/마지막 detach/공유 owner 유지/명시적 stop을 직접 검사한다. retry의 반환값·loadCount·state/revision·observer/owner/waiter 정리를 함께 확인한다.

### D03 — deep-link feature 순환을 호출 단위로 차단

- **문제:** 생성된 catalog·purity·resolver가 child 타입으로 다시 진입하며 순환을 끝낼 기준이 없다.
- **제약:** 재귀 route 자체의 일반 navigation·Feature mapping은 합법적인 사용으로 남긴다. 전역 mutable visited 집합이나 전역 cache로 호출끼리 간섭시키지 않는다.
- **대안 A:** 직접 Self feature만 macro에서 금지한다. 명시적 자기 타입·상호 참조·다른 모듈 경로를 놓치고 정상 재귀 navigation도 제한하므로 선택하지 않는다.
- **선택 B:** generated entry와 runtime bridge가 동기 호출 단위의 탐색 context를 공유한다. 현재 경로의 concrete route 타입과 연산 종류를 추적하고, 재진입 edge를 거절한다. 전체 방문 집합이 아니라 현재 경로를 사용하여 sibling의 같은 child 타입을 누락시키지 않는다. 이 변경이 걸리는 공개 진입점은 `DeepLinkFeatureRuntime.catalog(for:)`다. 구현 전에 context 전달 방식을 먼저 정한다. task-local 등 호출 문맥 전달이면 public API baseline이 바뀌지 않고, 파라미터 추가나 새 overload면 breaking change이므로 변경 이유·호출자 영향·migration·CHANGELOG를 같은 작업에 포함한다.
- **실패·복구:** 순환 edge의 catalog 기여는 비우고 pure explanation은 false로 처리하며, 해당 edge의 resolve·URL·case-name 결과는 nil로 종료한다. 독립적인 local·비순환 경로는 계속 동작한다. outbound recursive route를 잘못된 local route로 round-trip시키지 않는다.
- **검증:** direct Self, 명시적 자기 타입, A↔B, sibling 공유 child, 일반 비순환 그래프를 catalog/purity/resolve/explain/outbound API에서 확인한다. 서로 다른 generic 특수화가 계속 증가하는 경로는 T04에서 “상한 도입” 또는 “불필요” 중 하나로 판정하고 판정·근거를 증거 문서에 남긴다. 미정 상태로 T05로 넘기지 않으며, 상한을 도입하면 별도 FR/AC와 한계를 함께 추가한다.

compile-time 진단은 명확히 증명 가능한 경우의 보조 수단이다. runtime 종료 보장을 대체하지 않는다. 이전 crash 증거는 exit·generated 재진입·정상 대조이며 symbolicated stack trace를 확보했다고 기록하지 않는다.

### D04 — helper 전반에서 하나의 부모 타입 문맥 사용

- **문제:** Feature는 specialized type을 쓰지만 Presentation·Scene은 qualified 이름만 받아 nested generic 인자를 잃는다.
- **제약:** 지원 중인 constrained generic @Router를 보존한다. generic @CasePathable의 신규 지원은 추가하지 않는다.
- **대안 A:** Presentation·Scene의 출력 문자열에 각각 generic suffix를 붙인다. Self/result payload 분석과 또 어긋날 수 있어 선택하지 않는다.
- **선택 B:** 분석과 rendering이 같은 부모 타입 문맥을 사용하도록 통합한다. qualified 이름, generic parameter, Self payload 정규화를 분리하고 Syntax 기반 의미를 유지한다.
- **실패·복구:** 지원하지 않는 선언은 기존 명시적 진단을 유지한다. 지원되는 소비 코드를 generic-unsupported 진단으로 막아서 테스트를 닫지 않는다.
- **검증:** top-level/nested × non-generic/constrained-generic × Feature/Presentation/Scene/Tab/DeepLink 조합과 Self/명시적 부모 타입을 실제 plugin consumer로 검사한다. CasePath는 지원되는 non-generic Self/nested 사례와 generic 거절 대조로 분리한다.

### D05 — 실제 Swift 이름 충돌 규칙을 helper별로 일관 적용

- **문제:** Tab·Scene의 identifier-only 검사가 비활성 변수나 instance member를 거절한다.
- **제약:** 실제 static/catalog 및 nested helper 충돌은 계속 막는다. Tab·Scene의 조건부 annotated case 금지 정책은 별개이며 이번에 완화하지 않는다.
- **대안 A:** Tab·Scene에 예외문만 추가한다. Feature 등 다른 helper와 판정 기준이 계속 달라져 선택하지 않는다.
- **선택 B:** 실제 충돌을 분류하는 최소 공통 분석기를 사용한다. declaration kind, static/instance, parameter clause, helper namespace를 구분한다. compiler 조건부 활성 판단을 복제하지 않으며, 비활성 분기를 선제적으로 거절하지 않는다. 출발점은 신규 설계가 아니라 이미 같은 분류를 수행하는 `RouterFeatureExpansion.swift`의 `firstRouterFeatureMemberConflict`다. 이 함수는 nested type kind, static/class, parameterless case를 구분하고 `#if` 내부로 내려가지 않는다. 이를 helper namespace를 인자로 받는 공통 분석기로 일반화하고 Tab·Scene이 호출한다.
- **실패·복구:** 직접 확인 가능한 실제 충돌은 기존 전용 진단을 유지한다. 활성 조건부의 실제 충돌은 compiler 오류도 허용하되, 비활성 구성은 정상 생성·컴파일되어야 한다.
- **검증:** Tab·Scene·Feature에 instance/static, parameterless/payload case, function overload, nested type, #if off/on·중첩·elseif/else·플랫폼 조건을 적용한다. Presentation·DeepLink·CasePath도 같은 이름 분류의 적용/비적용 사유를 남긴다.

### D06 — 실패하는 테스트도 종료되는 장치

- **문제:** nil을 종료로 처리하지 않는 stream loop 때문에 cancellation 이후 cleanup에 도달하지 않는다.
- **제약:** suite timeLimit만 추가하거나 sleep을 늘려서 해결했다고 판단하지 않는다. 테스트용 fault injection은 production source에 넣지 않는다.
- **대안 A:** 외부 watchdog으로 항상 강제 종료한다. hang 검출은 가능하지만 gate·window·Task cleanup 보장은 없어 정상 테스트 장치로 선택하지 않는다.
- **선택 B:** nil/취소/timeout을 명시적 실패로 반환하는 await helper와 단일 cleanup 경로를 사용한다. gate 해제·stream 종료·Task 취소를 await보다 먼저 보장하고, native host·window 정리를 모든 exit path에 둔다.
- **실패·복구:** 각 continuation은 한 번만 종료하며 같은 테스트를 다시 실행할 수 있어야 한다. 프로세스 watchdog은 장치 자체가 고장났을 때의 최후 검출기로만 남긴다.
- **검증:** 실제 native test body에 이벤트 누락을 주입하고 취소 후 cleanup 완료, queue 후속 작업 진입, host 해제를 확인한다. 원래 정상 test body와 Swift Testing runner 경로도 함께 확인한다.

| AC-024 | FR-007 / T00,T07 | 모든 FR과 AC에 현재 후보의 직접 증거 연결. 기존 Q01·예약 경계 과잉 완료 문구 정정, 미실행/실패를 PASS로 바꾸지 않음 |
| AC-025 | FR-001~007 / T07 | 전체 suite·외부 consumer·migration consumer·필수 local gate 통과, 알려진 여섯 원인의 반례와 정상 대조 동시 통과. 환경 미지원 gate는 이름·사유 명시 |
| AC-026 | NFR-001~003 / T02,T07 | 공개 library product 3개와 플랫폼 하한이 그대로이고 accepted state/revision 변화는 각 1회·rejected 0회. 새 직렬 queue가 MainActor에서 파일 I/O를 실행하지 않으며, 서로 다른 driver 인스턴스의 durability 작업이 서로를 막지 않음을 barrier로 증명 |
| AC-027 | FR-007 / T06,T07 | 수정 후 `Macro-Diagnostics.md`의 E016·E048 설명이 실제 발화 조건과 일치하고 공개 동작 변경이 `CHANGELOG.md` Unreleased에 기록됨. `check-docs-consistency.sh`·`check-changelog-sync.sh` 통과 |

동시성 회귀는 barrier로 경계를 고정한다. 우선순위를 바꾼 원본 runtime probe도 반복 실행하되, 반복 횟수나 sleep만으로 순서를 보장했다고 쓰지 않는다. failure injection의 outer watchdog은 10초 이내 종료를 확인하는 보호 장치이며, test body가 정상 실패·cleanup하지 못한 watchdog 종료는 검증 실패다.

### 계약을 만족하는 것처럼 보이는 잘못된 수정도 거절

- 모든 save를 버리면 삭제 반례만 통과할 수 있다 → AC-006으로 새 저장·순서를 직접 확인.
- 모든 feature deep link를 nil로 만들면 crash만 사라진다 → AC-015로 정상 branch·allowlist·ambiguity를 확인.
- generic @Router를 일괄 거절하면 generated 오류만 사라진다 → AC-017~019로 지원·비지원 구성을 분리.
- 모든 이름 충돌 검사를 제거하면 정상 소비만 통과한다 → AC-022로 실제 충돌 검출 유지.
- timeout만 추가하고 cleanup은 못 하면 CI만 빨리 종료된다 → AC-001~003으로 실제 종료·후속 queue·자원 해제를 확인.
- load 진입 후 테스트를 예약 전 경계의 근거로 쓰면 기존 공백이 남는다 → AC-012에 별도 barrier·assertion 필요.

## 7. 종료·변경 관리

- **수정 완료:** T01~T06의 구현과 각 반례·정상 대조가 완료된 상태.
- **로컬 검증 완료:** 고정 후보의 모든 계획된 로컬 AC·필수 gate에 실제 통과 증거가 있는 상태.
- **배포 준비 완료:** 별도 pinned/원격/consumer/platform gate까지 충족한 상태. 이번 계획 완료나 로컬 PASS와 구분한다.
- **배포 완료:** 별도 승인된 tag·발행과 게시 확인까지 끝난 상태.

같은 원인의 변형은 기존 ID의 행렬을 확장한다. 수정 회귀·동일 계약 누락은 해당 작업을 재개방한다. 별도 원인이 재현되면 근거·영향·우선순위를 등록하고, 의미 있는 범위 확대나 공개 동작 변경은 사용자에게 알린 뒤 계획을 갱신한다. 검토 도중 발견되지 않았다는 사실을 “더 이상 결함 없음”으로 바꾸지 않는다.

commit은 승인 시 테스트 장치 / persistence / restore phase / recursive deep link / generic helper / collision 분석 / 통합 증거의 논리 단위로 나눈다. 이번 계획 작성은 commit·push 권한이 아니다. 향후 push 요청을 받으면 exact paths만 stage하고 remote parity·dirty worktree 보존을 확인한 후 사용자 지침의 XcodeBuildMCP cleanup을 수행한다.
