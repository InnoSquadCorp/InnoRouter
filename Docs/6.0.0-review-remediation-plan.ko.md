# InnoRouter 6.0 재검토 후 보완 계획

## 문서 관리와 적용 범위

| 항목 | 내용 |
| --- | --- |
| 상태 | 로컬 구현 완료 / 외부 릴리즈 검증 대기 |
| 버전 / 작성일 | 1.0 / 2026-09-05 |
| 결정 책임자 | 프로젝트 유지관리자(사용자) |
| 검토자 / 승인자 / 승인일 | 미기록 / 미기록 / 미기록 |
| 작성 요청 | 재검토에서 확인한 결함과 누락 기능의 작업 계획 작성 |
| 기준 구현 | `main`, HEAD `1ca15fa8`에 더해진 미커밋 6.0 작업 트리 |
| 제품 요구사항 | [FR6-036~053, AC6-031~048, NFR6-001~009, SC6-001~005](6.0.0-next-capabilities-spec.ko.md) |
| 기존 계획 | [추가 기능 1~6 순차 개발 계획](6.0.0-next-capabilities-plan.ko.md) |
| 다음 단계 | 고정 Swift 6.3 원격 CI, 실제 앱·기기 UI, 태그·배포 승인 |

이 문서는 기존 요구사항을 낮추거나 대체하는 새 기능 명세가 아니라, 재검토에서
발견한 결함과 기존 계획의 미완료 항목을 해결하는 후속 기술 계획이다. 기존
FR/AC/T6 식별자와 구현 이력은 보존한다. `R6-F`는 재현 결함, `R6-G`는 계획
누락 항목, `R6-T`는 이번 후속 작업의 식별자다. 아래 테스트 이름은 구현할
회귀 테스트의 가칭이며, 현재 존재하거나 통과했다고 주장하는 이름이 아니다.

이 문서의 R6-T01~08 로컬 구현은 완료했다. 커밋, 푸시, 태그, 배포는 이번 요청에서
수행하지 않았으며 아래 외부 gate와 구분한다.

## 검증된 사실, 가정, 미확인 사항

- **검증된 사실 — 직전 2026-09-05 재검토:** Xcode 27 / Swift 6.4에서 기존
  패키지 테스트 330개와 외부 소비자 테스트 4개가 통과했다. 별도의 진단 실행에서는
  아래 R6-F01~09의 문제 행동이 확인됐다. 이 수치는 수정 후 검증 결과가 아니다.
- **검증된 사실:** 외부 소비자의 생성 테스트 검사는 생성 문자열의 포함 여부만
  확인한다. 생성 결과 자체의 새 프로세스 컴파일·실행을 증명하지 않는다.
- **작업 가정:** 미배포 6.0 후보의 API와 녹화 자료 형식은 필요한 breaking change를
  허용한다. 기존 API를 잘못된 동작과 함께 유지하기 위한 별칭은 만들지 않는다.
- **수정 후 검증:** 현재 Xcode 27 / Swift 6.4 환경에서 전체 플랫폼 Release
  compile/interface, 새 회귀의 sanitizer·성능, 10개 동시성 시나리오 각 100회
  반복을 다시 통과했다. 고정 Swift 6.3과 실제 기기 UI는 외부 gate로 남는다.
- **미확인 / 담당:** 실제 앱 통합 대상과 검증 기기는 유지관리자가 지정한다.
  저장소 안의 독립 소비자·모의 도메인 공급자 검증은 이 지정 없이 진행할 수 있다.

## 변경하지 않을 기준

1. 기본은 `import InnoRouter` + `@Router` + 기존 host다. 새 기능 미사용 앱에는
   필수 설정이나 의존 제품을 추가하지 않는다.
2. 가변 이동 상태는 하나의 `RouterStore`만 소유한다. 이동은 기존
   reduce → prepare → revision/취소 검증 → commit 경로로 수렴한다.
3. 거절·취소된 요청은 그 요청에 의한 상태 변경과 revision 증가가 모두 0이어야 한다.
   동시에 성공한 다른 요청의 변경은 보존한다.
4. 공개 제품은 `InnoRouter`, `InnoRouterTesting`, `InnoRouterInspector` 세 개다.
5. Swift 6.3+, iOS/iPadOS·Mac Catalyst 18+, macOS 15+, tvOS 18+, watchOS 11+,
   visionOS 2+를 유지한다. iOS 17 하향, 5.x 구현 복구, 새 외부 서비스는 범위 밖이다.
6. 자료 유실·지원하지 않는 재현·검증 미실행은 명시적으로 드러낸다. 테스트 수,
   코드 커버리지, 문자열 생성 성공만으로 기능 완료를 판정하지 않는다.

## R6-T01 — 테스트 수명과 회귀 기반

- [x] R6-F01~09의 진단 순서를 저장소 안의 재현 자료로 옮기고, 해당 수정 단계에서
  일반 assertion으로 승격한다. 수정 전 실패 증거를 남기되 skip/영구 known-issue로
  완료 게이트를 우회하지 않는다.
- [x] `waitForEvent`, 시작·큐 장벽의 취소 결과를 구분한다. 임의 이벤트를 반환하는
  대신 명시적 취소/종료 결과를 사용하고, 등록과 취소의 경쟁도 정확히 한 번 정리한다.
- [x] `pendingWork`에 실제 남은 대기자를 포함한다. `finish`는 테스트 소유 작업의
  취소·배출 완료를 기다릴 수 있게 만들고, 필요하면 async/throws API로 변경한다.
- [x] 공유 runtime/clock 사용 시 다른 테스트 소유자의 타이머까지 취소하지 않도록
  소유권을 분리한다. 가상 시계 등록과 취소, 같은 기한의 처리 순서를 검증한다.

변경 범위: `RouterTestRequest`, `RouterTestStore`, `RouterTestClock`, 해당 테스트.
완료 조건: 취소 전/등록 중/등록 후/종료 후 시나리오에서 대기자·소유 작업이 0이고,
중복 resume와 객체 유지가 없다. 실제 라우터 스케줄러를 사용하며 동기화에
임의 sleep·반복 yield 횟수를 쓰지 않는다. 안전용 테스트 watchdog은 별개다.

## R6-T02 — 기능 영역 검증을 커밋 이전으로 이동

- [x] 큐 제출 때 통과한 projection을 실행 시점에도 유효하다고 가정하지 않는다.
  기능 scope의 타입·영역 전제조건을 부모 요청에 package 내부 정보로 전달한다.
- [x] 큐 진입 후 reduction 전, 비동기 prepare 뒤 commit 전에 검증한다. 실패는
  원래 전환 ID를 가진 구조화된 거절이며, 적용 후 결과를 거절로 바꾸지 않는다.
- [x] 일반 자식 액션뿐 아니라 전체 계획, 중첩 scope, 타입 모달의 같은 경계를 확인한다.
  모든 큐 요청을 제출 revision에 고정해 정상 FIFO 이동까지 거절하는 해법은 금지한다.
- [x] 부모 영역 교체·삭제, 같은 기능 두 인스턴스, 창 소멸, 정책 대기·취소를 검사한다.

변경 범위: `RouterFeatureScope`, `RouterStore` 요청/prepare/commit 접점,
feature mapping 테스트와 독립 소비자. 매크로 surface가 바뀌면 확장·동작 양쪽을 검증한다.
완료 조건: 거절된 자식 요청의 state/revision 변화가 0이고 형제 상태는 같으며,
성공 요청은 부모의 ID·정책·큐를 공유해 정확히 한 번 커밋한다.

## R6-T03 — 공통 부분 복원 검증·취소·보고

- [x] 디코딩과 경로 검증을 분리하고, snapshot과 history가 공유할 내부 불변 계획
  준비 계층을 만든다. 실제 적용은 기존 `RouterPlan`/`RouterStore`만 사용한다.
- [x] 각 validator 호출 전과 await 후에 취소를 검사한다. timeout/취소 후 다음
  경로·탭·창의 validator는 호출하지 않는다. 취소를 무시하는 앱의 이미 시작된
  작업을 강제 종료한다고 약속하지 않고, 그 한계와 결과 폐기를 문서화한다.
- [x] 보고서에 keep/remove/replace/의존 후속 제거와 구조 이유를 포함한다.
  원본 payload는 제외하고 사유는 안전한 구조 코드로 다룬다.
- [x] 빈 선택·필수 분할 열·전체 무효에서 기본은 명시적 실패, 대체 상태/선택은
  앱이 명시한 규칙만 사용한다. 대체 결과도 구조·도메인 검증을 거치고 순환 대체는
  횟수 제한으로 거절한다. 무관한 유효 영역을 임의 초기화하지 않는다.
- [x] 수동 및 자동 복원 연결, 손상/미래 버전 실패, 현재 모달 waiter 정리를 검증한다.

변경 범위: `RouterPartialRestoration`, snapshot 적용 및 `RouterStateRestoration`,
복원 테스트·보고서 예제. 완료 조건: 취소 뒤 신규 validator 호출 0, 해당 요청의
실패 커밋 0, 보고서와 최종 계획 일치, sibling/scene 보존. inspector의 순수
미리보기에서는 이 도메인 validator를 호출하지 않는다.

## R6-T04 — 히스토리 세션·커서·체크포인트

- [x] 이력 이동을 entry ID·세션 generation·기준 revision으로 식별한다. reset/stop은
  미완료 이동과 지연 승인을 무효화하고, commit 이전에도 같은 세대인지 확인한다.
  cursor를 범위 안으로 보정하는 것만으로 이전 세션 상태 적용을 숨기지 않는다.
- [x] 동기 package commit 관측 접점으로 현재 이력을 갱신한다. public AsyncStream은
  유지할 수 있지만 checkpoint/canGoBack의 정확성을 그 Task의 실행 순서에 맡기지 않는다.
- [x] 보류를 거절과 구분한다. deferral ID와 원래 목표를 연결해 최종 승인 커밋에서만
  cursor를 한 번 갱신하고, 재거절·취소·만료·reset 후 승인은 위치를 바꾸지 않는다.
- [x] 공통 부분 복원 검증으로 과거 경로를 준비하되 현재 topology와 병합한다.
  검증으로 목표가 바뀌면 실제 적용된 projection과 이력 항목을 함께 정합화한다.
- [x] 동시에 요청한 back/forward, 대기 중 정상 이동, 용량 축출, checkpoint import,
  stop 뒤 호출을 다룬다. 성공 시점의 항목 ID로 위치를 결정하며 오래된 배열 index를 쓰지 않는다.

변경 범위: `RouterHistory`, 공통 commit 관측/사전조건, `RouterStore+Deferral`, 테스트.
완료 조건: 항상 유효한 cursor, 이동 직후 checkpoint의 정확성, 새 세션에 이전

제품 범위는 정해져 있다. 아래는 각 단계의 첫 API 검토에서 기록할 구현 선택이며,
단계 중 계약을 낮추거나 실제 앱 선택을 추측해야 하면 유지관리자에게 돌려보낸다.

| --- | --- | --- |
