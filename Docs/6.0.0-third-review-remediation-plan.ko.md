## 확인된 사실과 범위

- 직전 리뷰에서 Apple Swift 6.4로 기존 논리 테스트 369개가 통과했다. 기존 known issue
  1건은 `finish`의 의도된 pending 진단을 확인하는 테스트이며 이번 결함을 숨기는 표시는 아니다.
- 별도 런타임 실행과 실제 `@Router` 매크로 확장으로 아래 7개 반례가 재현됐다.
  기존 테스트 통과만으로 이 반례가 해결됐다고 판단할 수 없다.
- 계획 작성 시 HEAD는 위 기준과 같고, 기존 변경 상태는 513개 항목 / 미추적 121개다.
  이 수치는 이번 계획 문서 추가 전 기준이며 대부분 기존 마이그레이션 작업이다.
- 임시 증거: [리뷰 기록](/tmp/innorouter-third-review-i2ckWv/README.md),
  [런타임 진단](/tmp/innorouter-third-review-i2ckWv/Probe.swift),
  [매크로 진단](/tmp/innorouter-third-review-i2ckWv/MacroProbe.swift),
  [런타임 결과](/tmp/innorouter-third-review-i2ckWv/probe.log),
  [매크로 결과](/tmp/innorouter-third-review-i2ckWv/macro-probe.log).
  `/tmp`는 임시 보관소이므로 T00에서 저장소의 회귀·증거와 연결한다.
- 유지할 결정: macro-first, 한 `RouterStore`, 세 공개 제품, Swift 6.3+와 현재 OS floor.
  미배포 6.0 후보에는 필요한 breaking change를 허용한다. iOS 17 하향은 포함하지 않는다.
- 수정 범위: 확인된 결함과 그에 직접 연결된 취소·수명·검증·진단 경로 및 회귀 테스트.
  새 제품·라우팅 엔진·원격 서비스·임의 앱 효과 자동 재현은 포함하지 않는다.
- Swift 6.3 고정 환경과 실제 플랫폼 UI 조작은 미검증 경계다. 로컬 코드 구현은 진행할 수
  있으며, 환경 확보와 최종 배포 판단은 유지관리자 책임으로 기록한다.

각 작업은 **실패를 검출하는 회귀 작성 → 계약/API 확인 → 수정 → 정상·실패 경로 검증 →
해당 diff 재리뷰** 순서로 닫는다. readiness는 큐·정책 진입·terminal 이벤트 장벽으로
동기화한다. 제한시간은 실패 테스트의 무한 대기를 방지하는 watchdog으로만 사용한다.
각 테스트는 실패해도 자체 gate/Task를 정리한다. 임의 sleep/yield 횟수, skip, assertion 삭제,
새로운 영구 known issue로 성공 판정을 만들지 않는다.

## R6R3-T01 — 큐에서 시작한 요청까지 취소 전파

변경 접점: `RouterStore`, `RouterStore+Scheduling`, `RouterStore+Policy`, 필요 시
내부 request 타입과 `RouterTestRequestLifecycle`.

- [x] 큐에서 실행으로 승격된 Task의 handle을 전환 ID에 연결해 소유한다. 취소 시 실제
  executor와 정책 race까지 전달하고 종료 시 handle·cancel 표식을 제거한다.
- [x] enqueue 직전/queued/승격 직전/active-policy/terminal 직후 경합에서 continuation은
  한 번만 완료한다. 취소된 요청은 commit하지 않고 다음 FIFO 요청이 진행할 수 있어야 한다.
- [x] timeout·coalescing·overflow와 취소의 경합에서 기존 결과 계약을 유지한다.
  Task handle 등록 전에 취소가 도착한 경우도 누락하지 않는다.
- [x] 직접 실행과 큐 경유 실행을 같은 취소 인수 테스트에 포함한다. `finish()`가 큐 출신
  active 요청 때문에 멈추는 경우 및 다른 store의 작업을 건드리지 않는 경우도 검증한다.

설계 선택: 현재 serialized executor의 명시적 소유권을 보완한다. 플래그만 확인하는 안은
정책의 await를 깨우지 못하므로 채택하지 않는다. 큰 스케줄러 교체는 이번 수정에 필요하지 않다.
앱이 취소를 무시하는 임의 코드를 강제 종료할 수 있다고 약속하지 않는다. 라이브러리의
요청·실행 lane은 취소로 종료하고, 늦게 돌아온 정책 결과가 commit으로 이어지지 않게 한다.

완료 조건: R6R3-AC01. 취소 요청 terminal 1회, 추가 commit/revision 0, 소유 runtime
request/waiter 정리, 뒤 요청 정상 완료. 외부 정책의 수동 release 없이 취소가 끝나야 한다.

## R6R3-T02 — presentation ID와 완료 요청에 결과 연결

변경 접점: `RouterStore+Presentation`, `RouterStoreTypes`의 waiter,
`RouterStore` commit 연계, deferral 경로, feature/scope의 typed overload.

- [x] 완료 요청을 scope뿐 아니라 최초 presentation UUID에 묶고 실행 직전·정책 대기 뒤·
  deferral 재개 시에도 같은 인스턴스인지 확인한다. 같은 route로 재표시된 새 UUID도 별개다.
- [x] 결과 값의 준비와 전달을 해당 완료 요청의 identity에 연결한다. 다른 `.apply`,
  사용자 dismiss, window 종료로 원래 모달이 사라졌을 때 준비된 값을 성공 결과로 보내지 않는다.
- [x] 동일 presentation에 겹친 완료 요청은 첫 소유 요청만 결과를 예약하고 뒤 요청은
  명시적으로 거절한다. 거절/취소 시 자기 예약만 해제하여 다른 요청의 값을 지우지 않는다.
- [x] 보류된 dismissal은 같은 완료 소유권을 유지한다. 승인 후 정확히 한 번 값 전달,
  재보류·거절·만료·취소에서는 그에 맞는 실패/정리 결과를 검증한다.
- [x] A→B 교체, 같은 route/새 UUID, 중첩 feature, 두 window, 중복 finish,
  외부 dismiss와 finish 경합, 정상 typed 결과를 테스트한다. 취소가 유발하는 dismissal도
  최초 UUID를 벗어나지 않는지 함께 확인한다.

설계 선택: UUID precondition과 완료 소유권을 함께 사용한다. route 비교만으로는 같은
화면의 새 인스턴스를 구분할 수 없고, 큐 전체를 revision에 묶으면 무관한 정상 이동까지
거절하므로 해당 presentation만 제한한다. 필요한 공개 오류 추가는 변경 이유와 함께 검토한다.

완료 조건: R6R3-AC02. 교체된 B의 상태와 waiter 보존, stale finish 추가 revision 0,
외부 dismiss로 제거된 A에 예약 value가 잘못 전달되지 않음, 정상 완료 value 1회.

## R6R3-T03 — 실패·취소된 replay의 소유 작업 종료

변경 접점: `RouterScenarioReplay`, `RouterTestRequest`, 필요한 내부 취소/보류 추적,
`RouterScenarioSourceGeneration`과 생성 시나리오 smoke.

- [x] 현재 결과를 await 중인 handle도 소유 registry에 유지한다. await 전에 registry에서
  제거해 취소 대상에서 빠지지 않게 한다. 루프와 각 비동기 경계에 취소를 연결한다.
- [x] assertion mismatch·잘못된 control·호출 Task 취소에서 남은 replay 요청을 취소하고
  terminal을 수거한 뒤 원래 실패를 반환한다. 먼저 완료된 요청의 정상 commit을 rollback하지 않는다.
- [x] replay가 만든 deferral을 실제 새 ID로 추적한다. deferred outcome의 기대값 검증이
  실패한 경우도 소유권을 놓치지 않고 취소한다. 반복 보류로 생긴 후속 ID까지 포함한다.
- [x] 같은 store의 무관한 앱 요청/기존 deferral 및 다른 store의 작업은 보존한다.
  runner 정리에 전역 `store.finish()` 또는 전체 deferral 취소를 사용하지 않는다.
- [x] 생성 테스트는 replay가 throw해도 자신이 만든 test store를 정리하고 원래 assertion
  오류를 잃지 않는다. 실패가 없는 상태·revision·terminal 음성 fixture는 통과시키지 않는다.
- [x] 겹친 요청 중 첫 mismatch, await 도중 취소, queued-active 취소, 재보류 후 실패,
  무관한 요청 공존, 생성 소스의 새 프로세스 실패/종료를 회귀로 검증한다.

설계 선택: replay 세션 단위 registry와 한 종료 경로를 둔다. Task handle을 버리는 안은

완료 조건: R6R3-AC03. replay 반환 뒤 replay 요청에 의한 추가 commit 0, 소유 pending 0,
무관한 요청 정상 진행, mismatch 또는 취소 원인의 보존. 이미 commit된 성공 단계는 유지한다.

  초기화하거나 fixture 상태를 몰래 적용하지 않는다. metadata/dependency 실패도 계속 무실행이다.
- [x] revision은 기존 상대 비교를 유지한다. 동일한 상태에서 시작하는 다른 baseline revision은

완료 조건: R6R3-AC04. 다른 초기 상태의 거짓 성공 0, preflight 추가 revision 0,

설계 선택: 부모/자식 독립 선언을 유지하며 route case별로 생성 권한을 적용한다.

완료 조건: R6R3-AC07. 자식 origin의 정상 왕복, 직접 부모 route의 허용 범위 유지,
