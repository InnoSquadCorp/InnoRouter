# InnoRouter 6.0.0 — 19~21차 검토 수정 증거

[19~21차 검토 통합 수정 계획](../6.0.0-nineteenth-review-remediation-plan.ko.md)의 T00~T07 실행 기록이다. 각 항목은 실제로 실행한 명령과 결과만 기록한다. 계획에 있으나 아직 실행하지 않은 항목은 **미실행**으로 남긴다.

## 판정

판정은 **코드 수정 및 로컬 자동 검증 완료**다. 여섯 원인의 반례와 정상 대조가 같은 후보에서 함께 통과하고, 계획한 로컬 게이트가 모두 통과했다. 다만 **AC-012는 닫지 못했다**(아래 미해결 참조). pinned toolchain 외의 배포 게이트 — exact commit 원격 CI, downstream revision, 플랫폼별 native runtime·접근성 — 과 commit·push·tag·release는 수행하지 않았다. 이 문서를 6.0.0 발행 완료 근거로 승격하지 않는다.

## 설계·호출자 영향

### 저장 명령 순서 (D01 / T02)

`RouterDurabilityGate`는 driver마다 하나씩 존재하는 package 타입이다. `reserve(_:)`는 동기이므로 호출자는 encode나 storage 진입으로 suspend하기 전에 자기 순서를 확정한다. `waitForTurn(_:)`은 자기 차례를 기다리고, 뒤늦게 수락된 remove가 무효화한 예약에는 `false`를 돌려주어 storage를 건드리지 않게 한다. `finish(_:)`는 예약마다 정확히 한 번 호출되며 encode 실패처럼 storage에 도달하지 못한 예약도 큐를 막지 않는다. 적용 지점은 `RouterStateRestoration`의 `saveSnapshot`·`removeSnapshot`과 `RouterPendingLinkPersistence`의 `persist` 세 곳이다.

순서는 driver 단위로만 직렬화되며 전역 lock은 없다. 공개 API·baseline 변화는 없다(`check-public-api` 통과).

### 초기 restore phase (D02 / T03)

기존 코드는 `status == .loading`으로 "초기 restore가 아직 안 끝났는가"를 판정했다. save 경로가 같은 status를 `.saving`·`.failed`로 덮으므로 판정이 무너진다. `didFinishInitialRestore`를 별도로 두고, 활성화 시작 시 내리고 `noSnapshot`·`restored` 결론에서만 올린다. owner 해제 두 경로(`detach`, `stopActivationIfUnowned`)는 이 값만 보므로 save의 성공·실패·진행 상태와 무관해졌다. 명시적 `stop()`은 기존대로 `didAttemptRestore`를 남기므로 재활성화 시 `observationResumed` 정책이 유지된다.

### 재귀 deep-link 종료 (D03 / T04)

전역 방문 집합이 아니라 **현재 호출 경로**를 추적한다. 서로 다른 부모가 같은 child를 가리키는 정상 구성은 cycle이 아니므로 계속 기여해야 하기 때문이다. 연산 종류(catalog·purity·resolve·caseName·url)마다 경로가 분리되어 catalog 탐색이 resolve를 억제하지 않는다. 탐색은 동기 호출 하나가 곧 한 번의 순회이므로 호출 사이에 상태가 남지 않는다.

측정된 수정 전/후:

| 진입점 | 수정 전 | 수정 후 |
| --- | --- | --- |
| self-recursive 전체 | exit 139, 출력 없음 | exit 0, 여섯 진입점 모두 종료 |
| 상호 참조 A↔B | 동일 crash | exit 0 |

**비재귀 대조군이 중요하다.** 같은 probe에 비재귀 route 두 개를 넣고 비교한 결과, feature child를 가진 비재귀 route(`featureParent`)도 `resolve=false`·`url=nil`이었다. 즉 재귀 route에서 관찰되는 그 값들은 이번 가드가 만든 결과가 아니라 feature 보유 route의 기존 동작이다. feature가 없는 `plain` route는 `resolve=true`, `url=probe://app/leaf/42`로 정상이다.

generic 특수화 증가 경로의 종료 상한은 **불필요**로 판정한다. 가드는 concrete 타입 identity로 경로를 판정하고, 실행 가능한 바이너리에 존재하는 특수화는 유한하므로 무한히 새로운 타입이 생길 수 없다. 별도 FR/AC를 추가하지 않는다.

공개 API는 바뀌지 않았다(`DeepLinkFeatureRuntime` 시그니처 동일, `check-public-api` 통과). 따라서 T04에서 예정했던 breaking change 판단은 "비파괴"로 종료한다.

### 부모 타입 문맥 통합 (D04 / T05)

`RouterMacro`가 부모 타입 문맥을 한 번 계산해 Presentation 분석·Scene 렌더링·Presentation 렌더링·Feature 렌더링에 모두 넘긴다. 이전에는 Feature만 `specializedRouterType`을 받고 나머지는 `type.trimmedDescription` 원본을 받았다. top-level generic router는 타입 문자열에 이미 `<...>`가 들어 있어 증상이 없었고, 다른 타입 안에 선언된 generic router에서만 인자가 사라졌다.

### 이름 충돌 분류 통합 (D05 / T06)

`firstRouterGeneratedMemberConflict`가 nested type·type-level 프로퍼티·parameterless case를 구분한다. 생성 멤버는 static이므로 같은 이름의 instance 프로퍼티는 합법이고, `#if` 내부는 macro가 조건을 평가할 수 없으므로 compiler에 맡긴다. Tab에는 원인이 둘이었다 — static/instance 미구분과 `variablesInsideConditional` 기반 비활성 분기 수집이며, 후자를 제거했다. Scene은 static/instance 구분만 추가했다. Feature는 기존 규칙을 그대로 같은 분석기에 위임했다.

수정 전 동일 파일 빌드 실패(E016 2건·E048 1건)와 수정 후 통과를 같은 fixture로 대조했다. 실제 충돌(직접 static `routerTabs`/`routerScenes`, nested `Scene` 타입)은 expansion 테스트에서 계속 거절된다.

### 호출자 관점 재검토

같은 작성자의 재검토이며 제삼자 리뷰가 아니다. 공개 호출자 기준으로 다음을 다시 확인했다. 저장·취소·재시작은 `save()`/`removeSnapshot()`/`activate()`/`stop()`과 pending-link `submit()`/`cancel()`/`resume()`/`restore()`가 서로 순서를 뒤집지 않는지, macro helper 조합은 Feature/Tab/Scene/Presentation/DeepLink를 한 route에 섞었을 때 생성 멤버가 서로를 막지 않는지다. 전자는 AC-004~008·AC-009~011의 테스트가, 후자는 nested generic consumer와 충돌 분류 테스트가 직접 덮는다. 공개 API baseline은 변하지 않았다.
