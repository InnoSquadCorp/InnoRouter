## 수정 전 실행 증거

별도 프로그램을 3회 실행했고 출력은 동일했다. continuation 장벽으로 정책 진입과
해제를 제어했으며 sleep 시간으로 경합을 추측하지 않았다.

```text
RESUME_CANCEL deferAgain=false caller=cancelled pendingRequests=1 nextBusy=true
RESUME_AFTER_POLICY deferAgain=false terminal=rejected deferrals=0 revision=0
RESUME_CANCEL deferAgain=true caller=cancelled pendingRequests=1 nextBusy=true
RESUME_AFTER_POLICY deferAgain=true terminal=deferred deferrals=1 revision=0
HISTORY_REBASE terminal=applied windows=1->0 modal=true->false revision=5
DUPLICATE_REPLAY fixtureSteps=1 policyCalls=2 returnedOutcomes=1 result=success
NATIVE_MODAL_ACTION replacementRemains=false revision=3
```

| 결함 / AC | 재현 순서와 관찰 | 수정 후 기대 | 실제 회귀명 / 수정 후 결과 |
| --- | --- | --- | --- |
| R6R5-F01 / R6R5-AC01 | present→첫 policy defer→allow resume→다음 policy 대기→호출자 취소. caller cancelled이나 active request 1, 다음 push busy. 정책이 새 defer를 반환하면 deferral 1 잔존 | gate를 풀기 전에 라이브러리 resume 종료·다음 요청 진행; 늦은 allow/defer의 commit·보류 0 | `presentationCancellationReleasesResumedPolicyLane`, `cancelledPresentationCannotBeRedeferred` / 수정 전 실패, 수정 후 통과 |
| R6R5-F02 / R6R5-AC02 | 모달 A→B 교체 apply가 policy 대기→A Binding에 nil→교체 승인. 새 B까지 제거됨 | B와 typed waiter 보존, stale dismissal 추가 revision 0 | `nativeDismissalUsesExactPresentationIdentity` / 수정 전 실패, 수정 후 통과 |
| R6R5-F03 / R6R5-AC03 | 두 번 push→history back 보류→새 창·모달→rebase 승인. 창과 모달 모두 제거 | 충돌 모달로 인한 실패·state/cursor 불변; 안전/queued rebase는 현재 수명 보존 | `historyRebasePreservesCurrentLifetimes`, `safeHistoryRebasePreservesNewWindow`, `queuedHistoryRebaseUsesExecutorEntryState`, `historyRebaseRejectsIncompatibleTopology` / 수정 전 원본 실패, 수정 후 통과 |
| R6R5-F04 / R6R5-AC04 | 한 step에 같은 ID의 submit→awaitTerminal→submit→awaitTerminal. 항상 reject policy를 두 번 실행하고 결과 한 개로 성공 | production 실행 전 invalidEventOrdering; policy/state/revision/pending 변화 0 | `replayRejectsDuplicateLogicalSubmission` 및 source generation 대조 assertion / 수정 전 실패, 수정 후 통과 |

수정 전 native probe는 실제 `RouterStoreStackSurface.swift`의 Binding 코드를 임시 파일에
포함하고 접근 helper만 덧붙여 실행했다. 수정 후 영구 회귀는 제품 Binding이 직접 사용하는
`makeRouterPresentationBinding`을 호출한다. 실제 OS 닫기 제스처는 아직 검증하지 않았다.

2026-09-06 R6R6 정정: 이 시점의 영구 회귀는 root sheet 교체 한 조합이었으므로 T02의
root/nested/window·style adaptation·typed waiter·detent 전체를 증명하지 않았다. 후속
`nativeDismissalIsScopedByPresentationIdentity`, `adaptedPresentationStylesPreserveDismissalIdentity`,
`deferredNativeDismissalUsesExactIdentity`, `staleNativeDismissalPreservesTypedWaiter`,
`staleNativeDetentUsesExactIdentity`, `nativeDismissalPolicyRejectionReconcilesBinding`,
`nativeDismissalCommitsMatchingPresentation`에서 누락 조합을 보강했다. 상세 결과는
[여섯 번째 리뷰 증거](6.0.0-sixth-review.ko.md)에 기록한다.

## 구현 결과 요약

- presentation UUID가 원본과 재개 transition ID를 소유하며 취소 시 실제 policy race와
  scheduler 실행을 종료한다. 정책이 취소를 무시하고 늦게 반환해도 commit 또는 재보류 전에
  precondition이 다시 적용된다.
- SwiftUI modal/detent Binding은 생성 당시 presentation UUID를 보존하고 system action을
  exact-identity precondition으로 제출한다. 교체된 presentation을 늦은 callback이 닫지 못한다.
- history rebase는 승인 시점이 아니라 실제 executor 진입 시점의 상태로 navigation-only
  plan을 다시 만든다. 새 창·장면·배지를 보존하며 모달 충돌과 topology 불일치는 구조화된
  거절로 끝나고 cursor/state를 바꾸지 않는다.
- replay와 source generator는 동일한 control graph validator를 사용한다. request의
  submit/resolve/terminal 상태, event index, deferral 생산·소비 순서를 실제 실행 전에 검증한다.
- 재리뷰에서 발견한 “rebase 승인 후 queue 대기 중 새 창 commit” 경합도 별도 회귀로 닫았다.

## 후속 검증 기록 규칙

- 구현 시작 때 환경과 기준 diff를 기록하고, 각 필수 변형의 실제 테스트명을 별도 행으로 추가한다.
- 수정 전 실패 assertion과 수정 후 통과 근거를 함께 남긴다. 정상 대조군도 기록한다.
- raw probe의 숫자 출력만으로 regression test가 구현됐다고 처리하지 않는다.
- 코드·로컬 자동·native UI·고정 toolchain/CI·실제 소비자 검증을 구분한다.
- 아직 미실행인 항목을 완료로 체크하거나 과거 실행을 최신 실행으로 바꾸지 않는다.
