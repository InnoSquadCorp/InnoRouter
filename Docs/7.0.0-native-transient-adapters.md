# Native transient adapters

The 7.0 host renders alert and confirmation-dialog families from the owning
stack's canonical Store. They contain immutable display metadata and no child
navigation node. The same surface is installed in recursively rendered stacks.
The renderer does not add a second Store, result registry, or persistence format.

`RouterTransientPresentationCapture` records the owner scope and exact runtime
presentation handle. Every callback submits through that captured authority.
Replacement with the same persisted UUID does not refresh an old callback.
An attempt arbitrates once, then retires. Rejection and deferral leave canonical
state in place; after native dismissal settles, reconciliation creates a fresh
attempt. Duplicate callbacks cannot select again or settle another waiter.

## Native settlement

- UIKit uses `UIAlertController` action handlers. A declared cancel button
  selects its declared typed value. An action sheet without one gets an explicit
  native cancel action that submits dismissal. On iPad, the supported popover
  delegate distinguishes outside interaction from an explicit button: outside
  dismissal submits `.dismissed`, including when UIKit invokes a declared cancel
  handler. The general alert presentation-controller delegate must not be
  replaced; UIKit rejects that configuration. Retirement during presentation
  waits for the actual `present` completion, and re-presentation waits for native
  dismissal/transition completion. There is no run-loop-turn or `Task.yield`
  settlement heuristic. tvOS has no popover delegate conformance.
- AppKit uses the `NSAlert.beginSheetModal` response. A response corresponding to
  a declared button selects it; an independent sheet end dismisses it. Native
  teardown retires authority before ending the sheet. Confirmation dialogs use
  the platform's native alert sheet with their declared actions and roles.
- watchOS uses `WKInterfaceController.presentAlert` and `WKAlertAction` handlers.
  WatchKit dismisses its sheet before invoking an action handler. Its native
  cancel control selects a declared cancel value; the explicitly supplied
  otherwise implicit cancel completes as `.dismissed`. Only the mounted owner
  drives the current WatchKit interface controller, and disappearance retires
  its attempt.

Native retirement itself never manufactures a typed value. Policy admission,
queueing, deferral, cancellation, generation checks, and final mutation remain
the existing Store's responsibility. A native controller may disappear while a
selection awaits a policy; a late outcome cannot regain removed authority.

## Executed checks

The original checkpoint failed three independent actual UI display checks.
The implementation then exposed an invalid UIKit delegate configuration and an
outside-cancel result mismatch; both failures were retained and corrected.
The sample iPad app verifies nested native transients, typed cancel/accept,
rejection and deferred allow/reject/cancel re-presentation, outside dismissal,
duplicate/stale callbacks, external removal and re-entry. Actual AppKit buttons
and app-hosted iPhone/Catalyst animated lifecycle tests complement those checks.

The UIKit animation regression belongs to the application-hosted
`RouterCatalystPlatformTests` target, which also supports iOS Simulator. A
headless SwiftPM XCTest process has no UIWindowScene/display animation clock;
it is not substituted for the animated app-hosted test. The latter requires a
real connected scene and keeps native animations enabled.

See the [Xcode 27 validation report](7.0.0-xcode27-validation.ko.md) for exact
source identity, executed platforms, retained evidence, and unverified scope.
The [UI probe](../NativeSceneSmoke/ROUTER7_UI_PROBE.md) provides reproduction
commands and separates the earlier failing runs from later passes.
