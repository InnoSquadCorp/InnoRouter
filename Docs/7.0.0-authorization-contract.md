# 7.0 authoritative authorization contract

Status: implemented and exercised in the Linux canonical Store engine. The
explicit catalog adapter is provisional pending app/maintainer API review.
These checks do not establish native host behavior, app acceptance, a technical
score, or release readiness.

## One authority, optional integration

An ordinary app without authentication continues to use `RouterStore`, actions,
and plans without a new catalog or session object. Applications protecting
navigation configure `RouterStoreConfiguration.authorization`. This is the
application authority for direct actions, direct plans, transactions, restoration,
and handled links. A standalone `RouterLinkPipeline.decide` result is only
preflight; extracting its plan is not an authentication grant. Configure the
Store to protect every application path.

`RouterAuthorizationConfiguration<Route>` contains four app-owned functions:

- `generation`: optional synchronous MainActor generation, incremented on logout,
  account replacement, revocation, or changed authorization semantics
- `requiresAuthorization`: a pure route predicate identifying protected targets
- `authorize`: a single asynchronous Boolean admission decision
- `catalog`: a synchronous provider of the current root declaration mapping

The library owns neither a user session nor server authorization. A login check
is not proof of per-resource access. Resource ownership and business rules belong
in app policies and server-side checks. Without a generation provider, the
library cannot detect external authorization changes during a suspension.

A minimal explicit selected-tab adapter looks like this (the corresponding
runtime construction is exercised by `RouterAuthorizationContractTests`):

```swift
let authorization = RouterAuthorizationConfiguration<AppRoute>(
    generation: { session.authorizationGeneration },
    requiresAuthorization: { $0 == .account },
    authorize: { session.isSignedIn },
    catalog: {
        RouterAuthorizationCatalog(roots: [
            .init(style: .tabs, branch: "home"): .home,
            .init(style: .tabs, branch: "account"): .account
        ])
    }
)
let store = try RouterStore<AppRoute>(
    initialState: initialState,
    configuration: .init(authorization: authorization)
)
```

The explicit adapter is intentionally small. It does not introduce another
public command hierarchy. A macro-authenticated catalog convenience has not been
claimed as implemented or consumer-approved. Nested descriptors identify their
container path; app mappings must reflect current declarations.

## Target union

The target set is the deduplicated union of:

1. The original route matched by URL admission
2. Every materialized route in the proposed state, including stored inactive
   branches, recursive presentations, regular windows, and immersive space
3. Root routes resolved from activated container descriptors

Only the selected tab branch activates its declaration and descendant roots.
Split columns are active together because they may be visible simultaneously.
A custom container with no selection treats its branches as active. An inactive
catalog-only tab is not a target, while a protected route actually retained in
an inactive branch still is. A configured authorization layer rejects unresolved
active descriptors before invoking the async callback. Unknown metadata cannot
silently mean public access.

Route-to-plan admission happens once in ordinary Store and host handling. The
matched route is carried as runtime request metadata through arbitration,
queueing, and policy deferral; no phantom route is added to navigation state.

## Generation and operation lifetime

Generation is captured before Store queue admission (and before host arbitration
defers its winning callback), and again protected across
snapshot decoding/partial-restore validation. The captured check travels with
the request, is evaluated at execution admission, after authorization, after
policy suspension, and immediately before commit. A queued request from an old
account cannot silently acquire the new account's generation. A policy-deferred
request retains its original generation; changed generations reject it rather
than retry automatically.

`policyTimeout` applies separately to each asynchronous policy/authorization
decision. `maximumActivePolicyOperationCount` is the shared actual-operation
budget for both categories. Reservations precede task creation. Logical timeout
or cancellation releases the waiting navigation request, but a noncooperative
callback still owns its registry slot until it exits. Its late return has no
commit authority. The current default of 64 remains provisional and uncalibrated.
A callback blocking MainActor synchronously cannot be preempted by a timer.

Login UI waiting is represented by a bounded pending slot, not by leaving an
authorization callback suspended. Returning false yields pending intent for a
handled link; it neither holds the execution lane nor occupies the callback
budget after the callback exits.

Generic policy bypass does not bypass authorization. The sole narrow exception
is a Store-owned native failure repair that removes the exact failed window or
immersive instance, verified against its current lifecycle identity. That repair
cannot introduce navigation and still passes cancellation, lifetime, reduction,
and revision checks. This is engine verification of the removal-only contract,
not evidence that a native OS callback fired.

## Durable pending and migration

Authentication-gated and decoded pending values require explicit current
pipeline re-admission:

```swift
await slot.resume(on: store, using: currentPipeline)
try await persistence.resume(on: store, using: currentPipeline)
```

Resume parses the saved URL once as a new admission. It rechecks current origins,
input limits, current catalog, target authorization, and Store topology. It must
have a current Store or pipeline authorization configuration. Omitting one does
not convert old protected intent into a grant.

The re-resolved recorded original route and payload must match the retained intent.
Legacy payloads lacking that field still retain their protected gated route in
the authorization target union. The
plan must preserve its surfaces, topology, routes, selections, and presentation
options. Fresh UUIDs for newly created windows/presentations are permitted.
Changed URL meaning, plan destinations, or navigation surfaces produce
`authorization.intentChanged`; the app must start a fresh explicit request to
accept changed intent. This prevents silent rerouting after a catalog/planner
update. The slot's default acceptance-only consumption retains rejected intent.

Persistence contains URL/route/plan intent and revalidation metadata only. It
never serializes authorization results, generation snapshots, closures, active
lifetimes, or waiters. Decoding old pending payloads also requires revalidation.
Legacy manually-created in-memory pending values can still replay without a
pipeline only when no Store authorization is configured; this path is not a
authenticated or durable continuation.

The existing `.required` pipeline syntax continues to express a route predicate
and login check for stack plans. Selection-only protected containers now need
`.configured(authorization)` with root declaration metadata. Old tests/examples
that relied on missing root metadata are migrated rather than treating unknown
roots as public.

## Failure and evidence contract

`RouterAuthorizationFailure` is a payload-free value with extensible `Code`:
`denied`, `generationChanged`, `unresolvedRoot`, `timedOut`, `capacityExceeded`,
`revalidationRequired`, and `intentChanged`. Store outcomes carry one
`.authorization(failure)` rejection. Adding a future raw code does not force an
exhaustive switch over every failure variant. No raw URL, route payload, or
account identifier is included in these errors.

`RouterAuthorizationContractTests` exercises Store application, restore, custom
planners, selected tab/split/scene targets, inactive routes, unresolved roots,
auth/policy/queue generation races, policy deferral, pending restart and changed
intent, cancellation, late completion, and operation recovery. It includes 1,000
saturated attempts after a timeout and 1,000 cooperative callback completions.
`RouterPlanLinkAdmissionTests` exercises the actual host arbitration entry point
without fabricating a Store or native view behavior. Final aggregate totals and
exact compiled source hashes belong to the immutable validation provenance, not
this design document.
