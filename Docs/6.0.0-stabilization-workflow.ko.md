# InnoRouter 6.0.0 안정화 작업·검증 원칙

작성일: 2026-09-13

상태: 작업 방식 정의 완료. 아래 결함의 수정·검증 완료를 의미하지 않는다.

## 1. 목적과 적용 범위

InnoRouter 6.0.0 안정화는 개별 버그를 고치는 단위가 아니라, 하나의 동작 계약을 구현하고 검증하는 단위로 진행한다. 발견된 사례에 조건문을 추가한 뒤 기존 테스트의 성공만으로 완료를 선언하지 않는다.

이 문서는 이후 안정화 계획·코드 수정·재검토·완료 보고에 적용한다. 제품 계약은 [기능 명세](functional-expansion-spec.md), 배포 요구사항은 [배포 가이드](../RELEASING.md)를 함께 따른다. 이 문서 작성 자체는 코드 수정이나 commit·push·tag·배포를 수행한 것이 아니다.

기본 방향은 다음과 같다.

- `@Router`와 생성된 typed helper를 기본으로 하는 macro-first 사용성을 유지한다.
- 첫 6.0.0 배포 전에는 필요한 breaking change를 검토할 수 있다. 내부 구조나 과거 API를 보존하려고 불필요한 상태·분기·호환 계층을 추가하지 않는다.
- breaking change를 선택하면 사용자 영향, 대안, migration, API baseline·DocC·consumer 변경 범위를 먼저 명시한다. 무관한 전체 재작성은 하지 않는다.
- 플랫폼·toolchain 하한은 이번 안정화에서 임의로 변경하지 않는다. iOS 17 지원과 새로운 기능은 범위 밖이다.
- 기존 미커밋 수정과 사용자 산출물을 보존한다. 작업 방식 변경을 이유로 이전 수정 전체를 되돌리거나 다시 작성하지 않는다.
- 기존 결함, 이번 수정으로 생긴 회귀, 선택적 기능 개선을 구분한다. 선택적 개선은 별도 backlog로 관리한다.

## 3. 코드보다 먼저 동작 계약을 작성한다

각 수정 묶음에는 문제, 제약, 대안 두 가지 이상, 선택·비선택 이유, 실패 시 동작, 검증 계획을 짧게 남긴다. 문서 분량보다 상태와 소유권의 모호함을 없애는 것이 중요하다.

복원 기능에서는 현재 구조에 유효성 검사를 보강하는 안과, 활성화 상태·소유권을 한곳에서 관리하는 안을 비교한다. 무조건 재설계하거나 최소 diff만 고집하지 않고, 불가능한 상태를 표현하기 어렵고 전체 생명주기를 검증하기 쉬운 안을 선택한다.

설계에는 다음 계약을 포함한다.

1. activation을 예약하는 단계에서 generation, 시작 revision, observer와 소유권의 관계를 확정한다. 호출자가 활성 상태를 전제로 행동할 수 있는 반환 시점보다 늦어서는 안 된다.
2. 하나의 driver에서 유효한 observer는 최대 하나다. 관찰이 필요한 활성 상태에서는 정확히 하나이고, 완전히 중단된 상태에서는 0개다.
3. 작업의 실행 진입, 각 suspension 이후 상태 변경, 외부 caller 반환 시점에 해당 작업·소유권이 여전히 유효해야 한다.
4. `stop()`으로 무효화된 작업은 새 활성화의 상태·observer·manual owner를 변경하거나 되살릴 수 없다.
5. 시작 이후 발생한 새로운 navigation은 늦게 도착한 복원 결과로 덮어쓰지 않는다.
6. caller 하나의 취소와 공유 activation 전체의 중단을 구분한다. 다른 유효한 소유자가 있으면 그 소유권을 보존하고, 마지막 소유자가 사라지면 관찰과 예약 작업을 정리한다.
7. 성공·실패·취소·재시작에서 각 waiter는 한 번만 종료된다. 명시적 stop 후 재관찰과 취소된 초기 복원의 재시도 정책을 구분해 정의한다.
8. 무효화된 관찰이나 예약 작업이 새 자동 저장을 시작하지 못한다. 이미 storage에 진입한 작업의 완료·취소·직렬화 보장은 storage 계약에 맞춰 별도로 명시한다. `stop()`이 이미 수행한 I/O까지 되돌린다고 가정하지 않는다.
9. navigation 상태의 유일한 변경 권한은 `RouterStore`에 유지한다. 수락된 전이는 상태 할당과 revision 증가를 각각 한 번 수행하고, 거부된 전이는 둘 다 수행하지 않는다.

매크로에서는 선언 위치가 이동해도 원래 payload 타입의 의미를 보존하고, 실제로 충돌하는 선언만 진단한다. generated 코드의 모양뿐 아니라 소비자의 컴파일과 typed helper 동작을 계약으로 삼는다.

## 4. 수정 전에 실패하는 테스트를 고정한다

각 제품 결함은 수정 전 후보에서 의도한 이유로 실패하는 회귀 테스트가 있어야 한다. test setup 오류나 무관한 컴파일 오류를 제품 결함의 재현으로 세지 않는다. 수정 후에는 같은 테스트와 정상 대조군이 함께 통과해야 한다.

### 비동기 경계 행렬

| 경계 | 배치할 사건 | 확인할 결과 |
| --- | --- | --- |
| 예약 완료 후 worker 실행 전 | 추가 activate, 새 navigation, stop 후 restart | 시작 기준 보존, 이전 worker 무효화, observer 단일성 |
| load·decode·복원 판단 대기 중 | caller 취소, host 제거, stop, 새 navigation | 공유 owner 보존, stale 결과 거부, 실패 정리 |
| 내부 완료 후 caller 복귀 전 | stop, 취소, restart | 제거된 claim이 살아나지 않음, waiter 단일 종료 |
| 활성 관찰 중 | 여러 host·manual owner 조합, 마지막 host 제거 | 남은 소유자에 맞는 관찰 유지·해제 |
| 저장 예약·encode·storage 실행 경계 | 취소, stop, 재활성화 | 새 stale 저장 시작 방지, 기존 I/O 계약 준수 |

실제로 가능한 각 경계와 관련 사건을 구체적인 테스트에 연결한다. 적용 불가능한 조합에는 이유를 남긴다. 알려진 반례와 상호작용이 큰 조합은 명시적으로 검증하고, 나머지는 모델 기반·생성형 시나리오로 보완할 수 있다. 생성형 테스트는 seed와 실패 경로를 재현 가능하게 남긴다.

### 테스트 장치의 신뢰성

- 이벤트 등록·작업 진입·완료를 명시적 barrier나 제어 가능한 의존성으로 동기화한다. 일정 시간의 sleep 또는 반복 yield만으로 실행 순서를 보장했다고 판단하지 않는다.
- deadline은 실패 감지에 사용한다. 시간 초과를 성공 동기화 수단으로 사용하지 않는다.
- timeout이나 취소 시 pending continuation, stream, storage gate, Task가 정리되어야 한다. suite 시간 제한만 붙이고 취소에 반응하지 않는 대기를 남기지 않는다.
- 이벤트 누락·worker 정지를 의도적으로 주입해, 테스트가 제한 시간 안에 실패하고 정리되는지 검증한다. mutation은 격리된 fixture나 복구 가능한 실험에서 수행한다.
- 마지막 host의 자연 detach는 수동 `driver.stop()`을 호출하기 전에 검증한다. 안전 정리용 stop은 이 assertion을 대신하지 못한다.
- 공유 테스트 도구를 먼저 보강할 수 있지만, 제품 동작 변경과 테스트 도구 변경의 효과를 구분해 확인한다.

### 매크로 정상·오류 대조

- 동일 이름의 parameterless case와 연관값 case를 구분한다.
- instance member, static member, 정상 overload, nested helper 충돌을 구분한다.
- `Self`와 명시적 부모 타입을 직접·중첩·generic 선언에서 비교한다.
- 조건부 선언은 활성·비활성 분기, 중첩 `#if`·`#elseif`·`#else`, 플랫폼 조건을 실제 consumer configuration에 연결한다.
- expansion fixture, behavior test, 외부 plugin consumer를 함께 사용한다. 언어 규칙이 판단 근거라면 일반 Swift 대조군을 실제 컴파일한다.

## 5. 동작 단위로 순차 구현한다

작업 순서는 다음과 같다. 단계마다 관련 실패 테스트의 전환과 기존 정상 동작을 확인한 뒤 다음 묶음으로 넘어간다.

1. **착수 기준 고정:** 현재 revision·dirty diff·환경을 기록하고, F01~F05와 Q01~Q02를 실행 기록에 등록한다. 근거 없는 기존 완료 표시의 정정 범위를 확인한다.
2. **계약과 테스트 준비:** 위 설계 비교와 경계 행렬을 작성하고, 실패해도 종료되는 테스트 장치를 준비한다. 현재 후보에서 반례 실패와 정상 대조군 성공을 확인한다.
3. **복원 생명주기 수정:** F01~F03을 하나의 activation·ownership 계약으로 해결한다. no-snapshot, 기존 저장 복원, 실패 후 재시도, 공유 host·manual owner 동작도 유지되는지 확인한다.
4. **매크로 의미 보존:** F04~F05를 수정하고 정상·오류 입력을 expansion·behavior·외부 consumer에서 확인한다.
5. **누락된 검증과 기록 보완:** Q01~Q02의 실패 종료, mounted 마지막 host 제거, 동시 manual 호출, 조건부 선언 검증을 완료한다. 테스트 장치 보강은 앞 단계에서 시작하되 여기서 누락 여부를 다시 확인한다.
6. **별도 검토와 최종 검증:** 아래 재검토·후보 고정·완료 판정 절차를 적용한다.

중간에 새로운 문제가 나오면 원인과 영향 계약을 기록한다. 이번 변경이 만든 회귀와 동일 계약의 누락은 해당 묶음을 다시 열어 처리한다. 무관한 기존 결함은 심각도와 배포 차단 여부를 판정하고, 작업 범위의 의미 있는 확대가 필요하면 사용자에게 방향을 요청한다. 새로운 기능은 안정화 묶음에 자동 편입하지 않는다.

## 6. 구현 검증과 별도 재검토를 구분한다

구현 직후의 검증은 수정 의도가 코드에 반영되었는지 확인한다. 별도 재검토는 public API의 호출자 관점에서 시작해 진입·상태 변경·외부 effect·반환·정리 경로를 다시 따라간다. 같은 작성자의 재검토를 독립된 제삼자 리뷰로 표현하지 않는다.

재검토에서는 다음을 확인한다.

- 바뀐 각 상태·소유권 필드의 모든 쓰기 지점과 종료 경로가 계약을 만족하는가?
- 성공, 오류, 취소, stale 완료가 새 작업의 상태를 변경할 여지가 없는가?
- History·Scene·restoration의 인접한 지연 완료·관찰·취소 패턴에도 같은 결함이 있는가?
- internal helper 테스트의 성공이 실제 host·외부 consumer에서도 이어지는가?
- 테스트의 assertion이 계약을 직접 확인하는가, 정리 코드나 최종 상태만 보고 우연히 통과하는가?

발견 사항은 재현된 제품 결함, 검증 공백, 선택적 개선으로 구분한다. 새 반례가 나오면 관련 계약과 테스트 행렬을 확장한다. 단순히 검토 횟수를 늘리는 것을 품질 향상의 근거로 삼지 않는다.

## 7. 후보와 증거를 연결한다

최종 검증 전 후보를 고정한다. 미커밋 작업이면 HEAD뿐 아니라 대상 tracked diff와 untracked 소스·테스트의 목록 및 hash도 기록한다. 사용자 생성 산출물은 후보에서 명시적으로 제외한다. commit 후에는 정확한 commit SHA와 대응시킨다.

인수 기준마다 다음 정보를 실행 기록에 연결한다. 빈 칸이나 과거 후보의 성공만 있는 행은 완료가 아니다.

| 인수 기준 | 보장할 동작 | 테스트·consumer 설정 | 실제 assertion 또는 compiler 결과 | 수정 전 반례 | 수정 후 결과·로그 | 후보·환경 | 상태 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 기준 ID | 관찰 가능한 계약 | 경로·테스트명·flag | 무엇을 검증하는지 | 실패와 정상 대조 | 실행 명령·exit·증적 | SHA/patch hash·toolchain·플랫폼 | 미착수/진행/통과/실패/미실행 |

검증은 위험에 맞춰 수행하되, 저장소의 필수 배포 게이트를 생략하지 않는다.

- 각 묶음: 관련 회귀·기존 동작 suite와 영향을 받는 consumer 검사.
- 최종 후보: 전체 테스트, `principle-gates.sh --platforms=all`, 외부 consumer, 매크로, public API, DocC·문서 예제, lint 등 필수 통합 검사.
- 비동기·메모리 변경: 관련 sanitizer 실행과 누수·정리 검증. sanitizer 성공이 논리적 실행 순서의 안전성을 대신하지 않는다.
- coverage·성능: 저장소의 필수 게이트와 baseline 비교. 테스트 수나 coverage 수치만으로 인수 기준을 충족했다고 판단하지 않는다.
- 배포 후보: 고정된 지원 toolchain, 정확한 후보의 원격 CI, downstream revision, 플랫폼별 필수 runtime 검증을 배포 계약과 대조한다.

같은 실행이 여러 기준을 실제로 검증하면 증거를 재사용한다. 코드·테스트·의존성·설정이 바뀌면 영향받는 검증을 다시 열고 실행한다. 문서 표현만 바뀐 경우에는 영향 분석을 남기고 필요한 문서 검사만 다시 수행할 수 있다. 영향 판단이 불확실하면 검증 범위를 넓힌다.

## 8. 완료·중단·인계 기준

완료 상태는 다음처럼 구분한다.

- **수정 완료:** 범위 내 계약이 구현되고 관련 반례·정상 대조군이 통과했다. 통합·배포 검증은 남을 수 있다.
- **로컬 검증 완료:** 고정 후보의 계획된 로컬 게이트가 통과했고, 인수 기준과 증거가 연결되었다. 미실행 배포 조건은 별도 표시한다.
- **배포 준비 완료:** 필수 원격 CI·toolchain·consumer·플랫폼 검증까지 충족하고 알려진 배포 차단 결함이 없다. 발행 권한을 대신하지 않는다.
- **배포 완료:** 승인된 tag·배포 작업이 수행되었고 실제 게시 결과까지 확인했다.

검증 환경이 없으면 해당 항목을 미실행으로 남긴다. mock·module·Simulator의 성공을 확인하지 않은 실제 UI·기기·배포 성공으로 바꾸어 표현하지 않는다. 알려진 실패를 timeout 확대, 테스트 비활성화, 근거 없는 완료 체크로 닫지 않는다.

인계에는 변경 범위, 설계 선택 이유, 해결한 ID, 검증 후보, 실행 결과, 미실행 항목, 남은 위험과 다음 행동을 적는다. 모든 필수 인수 기준에 증거가 있고 관련 반례가 통과했을 때 정해진 작업을 종료한다. 무결함을 입증하려는 끝없는 검토 대신 검증 범위와 잔여 위험을 명확히 보고한다.

commit·push는 사용자 요청 범위에 따라 수행하고, 논리적 변경 단위와 정확한 파일 경로로 나눈다. 사용자 산출물을 함께 stage하지 않는다. push한 경우 원격 일치·worktree 보존을 확인한 뒤, 사용자 지침의 XcodeBuildMCP 산출물 정리를 수행한다. 활성 build·test를 중단하지 않으며 회수 용량·최종 여유 공간 또는 생략 사유를 보고한다.

이 작업 방식의 목표는 “더 이상 문제가 없다”는 선언이 아니라, 동작 계약의 누락·수정 회귀·근거 없는 완료 판정을 검출하고 재발 가능성을 줄이는 것이다.
