# InnoRouter 7.0.0 기술 평가 계약

> 이 문서는 2026-10-04의 PR #54 검토 기준으로 작성한 보존용 Draft다. 2026-10-19 최신 main에 기록했으며, 현재 구현·출시 상태나 새 작업 승인을 나타내지 않는다. 현재 지원 버전과 계약은 [README](../README.md)와 [RELEASING](../RELEASING.md)을 따른다.


사용자 요청에 따라 **InnoRouter 7.0.0의 기술 점수 92/100 이상, 같은 기준의 Swift Navigation보다 5점 이상 높은 결과**를 목표로 한다. 아래 수치는 개발 목표다. 아직 새 rubric으로 두 라이브러리를 실행 평가하지 않았으므로 현재 점수·예상 달성 점수로 사용하지 않는다.

관련 구현·migration·출시 순서는 [전체 개선 계획](7.0.0-improvement-plan.ko.md)을 따른다. 이 문서는 그 계획의 R10/D10/V13에 해당하는 비교 규칙이다.

## 1. 평가 범위와 기준 고정

- 대상은 Apple 앱 탐색의 타입 안전성, 런타임 정확성, 기능 조합, 성능·메모리·빌드 비용, 복원·진단, 기술 호환성이다.
- GitHub stars, 사용자 수, 브랜드, 마케팅, 커뮤니티 규모, 다운로드 수는 가중치 0이다. 단, 실제 실행 가능한 platform/toolchain 범위와 dependency 비용은 기술 항목으로 남긴다.
- Swift Navigation의 foundation 역할과 InnoRouter의 통합 router 역할 차이를 기록한다. 넓은 기능을 기본 제공하지 않는다는 이유만으로 상대의 결함으로 판정하지 않는다.
- 각 라이브러리의 공식 권장 패턴과 필요한 앱 adapter로 동일 시나리오를 완성한다. adapter source·의존성·설정·runtime 비용을 포함하고, 기능 결과는 같게 맞춘다.
- 기본 권장 구성과 조정한 최소 구성은 별도 행으로 비교한다. InnoRouter의 Inspector는 선택 구성으로 측정하되 실제 사용 시 비용도 별도 보고한다.
- 공통 핵심 기능 점수와 전체 기술 점수를 함께 공개한다. 복원 등 확장 기능만으로 기본 탐색의 낮은 품질을 덮지 않는다.
- 비 Apple 플랫폼은 호환성 보조 결과로 공개한다. 결론은 이 평가 범위에 한정하며 Swift Navigation의 모든 사용처에 대한 전면적 우위를 주장하지 않는다.

**기준 고정 시점:** S01에서 아래 체크리스트를 실행 fixture·명령·측정 조건으로 구체화하고 revision을 고정한다. S00의 알려진 결함 수정은 먼저 진행할 수 있으나 S02 이후 평가 대상 구현을 최적화하기 전에 비교 계약을 고정한다. 결과가 불리하다는 이유로 가중치·상대 버전·실패 시나리오를 바꾸지 않는다. harness 결함 수정은 변경 이유와 함께 양쪽을 다시 평가한다.

처음 비교할 상대는 이전 검토의 공식 release `2.11.2`다. S01 시작 시 당시 최신 stable release를 확인하여 최종 tag/commit을 고정하고, 비교 중에는 동일 revision을 사용한다. S10에서 더 새로운 stable이 나왔으면 해당 버전을 추가 비교한다. 통과에 유리한 옛 버전을 선택해 현재의 우위로 표현하지 않는다.

## 2. 공식 자료에서 확인한 비교 강점

2026-10-04 확인. 문서/manifest 확인은 런타임 성능 검증이 아니다.

| 확인 내용 | InnoRouter에 필요한 대응 | 공식 근거 |
|---|---|---|
| enum destination으로 서로 배타적인 화면 상태를 표현하고 native SwiftUI binding과 연결 | sheet/alert/dialog 등 상호 배타성, compile-time negative consumer, native dismissal 상태 일치 | [Swift Navigation README](https://raw.githubusercontent.com/pointfreeco/swift-navigation/2.11.2/README.md) |
| observation, binding, transaction 기반의 작은 도구를 조합하고 UIKit/AppKit 경계를 제공 | scope 단위 관찰, animation/transaction 보존, 독립 feature 및 부분 도입 경로 | [공식 저장소](https://github.com/pointfreeco/swift-navigation) |
| 별도 library products와 traits로 기능 경계를 표현. compiler-plugin/SwiftSyntax 의존도 존재 | 제품 수만 세지 않고 실제 선택된 target·dependency graph와 빌드 비용 측정 | [2.11.2 Package.swift](https://raw.githubusercontent.com/pointfreeco/swift-navigation/2.11.2/Package.swift) |
| Swift 버전별 manifest가 있으며 platform floor가 manifest에 따라 다름 | tools-version 한 줄로 호환성을 단정하지 않고 실제 compiler가 선택한 manifest로 consumer build | [Swift 6.2 manifest](https://raw.githubusercontent.com/pointfreeco/swift-navigation/2.11.2/Package@swift-6.2.swift), [기본 manifest](https://raw.githubusercontent.com/pointfreeco/swift-navigation/2.11.2/Package.swift) |

Swift Navigation이 전혀 모달을 중첩할 수 없다거나 dependency가 없다는 가정을 하지 않는다. 공식 패턴으로 가능한 범위를 먼저 구현한다. InnoRouter의 차별화는 같은 결과를 얻는 데 필요한 코드, 강제되는 불변식, 수명·복원 계약과 실측 비용으로 입증한다.

비교 가능하지 않은 플랫폼 기능은 S01에서 양쪽 동일하게 applicability를 결정한다. library가 선택한 구현 범위에 없다는 이유로 필요한 시나리오를 사후 `N/A` 처리하지 않는다. 보조 adapter로 충족하면 기능은 통과하고, 그 코드·dependency·성능 부담을 해당 비용 항목에만 반영한다. 라이브러리 자체 결함과 adapter/harness 결함은 구분한다.

### 비용 항목의 산식

C2와 D1–D4는 다음 규칙을 사용한다. 각 항목의 metric·workload·기본/최소 구성은 결과를 보기 전 고정하고, 한 workload가 평균을 압도하지 않도록 비율의 기하평균을 사용한다.

1. 작은 값이 좋은 metric마다 `r = 해당 구현의 측정값 / 두 구현 중 작은 측정값`으로 계산한다.
2. 상대 점수는 `5 / sqrt(r)`이며 상한은 5점이다. workload별 값을 고정 가중치로 합산한다. C2는 handwritten tokens와 독립 설정 지점을 각각 50%로 둔다.
3. 측정 노이즈 안의 차이 또는 절대값이 계측 해상도 이하인 값은 동점이다. 분모가 0이면 비율을 사용하지 않고 사전 정의한 0/비0 절대 기준으로 판정한다.
4. 기능 요구를 생략하여 얻은 속도·코드량은 점수로 인정하지 않는다. 기능적으로 맞지 않는 구현은 먼저 고친다.
5. 메모리 누수·인증 누락·부분 commit 등 핵심 실패는 평균 점수와 무관하게 아래 필수 조건을 실패시킨다.

F2의 하위 체크 가중치는 실제 지원 matrix를 정하는 S01에서 고정한다. Linux/core 등의 범위 차이는 양쪽 모두 공개한다. 이를 좁게 설정해 높은 점수를 얻은 경우 전체 Swift 환경에 대한 우위라고 표현할 수 없다.

## 4. 공통 시나리오와 재현 조건

| 시나리오 | 공통 UI/입력 | 주요 점수 항목 |
|---|---|---|
| Q01 · 기본 탐색 | 두 tab의 독립 history, push/pop, swipe back | A1/A2, B1, C2, D1/D2 |
| Q02 · 중첩 모달 | sheet→push→child sheet→typed result, child alert/dialog | A1/A3, B1/B2, C2, D1/D2 |
| Q03 · feature 조합 | 독립 Swift modules 두 개, 기존 앱의 한 host에 추가 | A2, C1/C2/C3, D3/D4 |
| Q04 · 비동기 요청 | 로그인 pending, auth 변경, topology 교체, cancellation, duplicate | A4, B2/B3/B4/B5 |
| Q05 · 영속 상태 | nested/window 상태 cold launch, rename migration, 손상 입력 | A4, B3/B4, E1/E2 |
| Q06 · 플랫폼·빌드 | 동일 consumer UI, 각 지원 platform/toolchain과 선택 graph | D3/D4, F1/F2 |

소비 앱 source, UI, payload, 실패 주입 시점은 같게 맞추되 라이브러리별 코드는 권장 API를 사용한다. 불필요하게 비효율적인 상대 구현을 만들지 않고, 채점 전에 API 사용 적합성을 검토한다. 공식 사례와의 차이를 기록하며 가능하면 구현 작성자와 다른 reviewer가 확인한다.

기본 runtime 조건은 같은 Apple Silicon Mac의 Release build, 같은 Xcode/Swift/SDK, 같은 Simulator 또는 실제 기기다. iOS 기기 결과와 macOS 결과를 한 속도 수치로 섞지 않는다. download/network, 첫 shader/UI 준비, 애니메이션 시간은 분리한다. state 규모는 10/100/1,000 nodes, path 1/64/256, presentation depth 0/1/8을 사용하되 공통 지원 구간과 확장 stress 구간을 따로 집계한다.

runtime은 warmup 후 구현 순서를 교차하여 최소 3 batches×10 samples, build는 최소 clean 5회/incremental 변경당 10회를 측정한다. median/p95·분산과 bootstrap 95% 구간을 보고하고, p95 계산에 충분한 raw transition 표본을 남긴다. API callback 지연과 화면 애니메이션 완료를 구분한다. benchmark JSON에는 commit/toolchain/device/graph/config/command/sample 수·raw data 위치를 기록한다.

## 5. 기술 우위 완료 조건

아래 조건은 기술 목표의 통과 조건이며 실제 측정 결과가 아니다. 하나라도 미달하면 구현·설계 개선 loop로 돌아간다.

| Gate | 통과 조건 |
|---|---|
| G1 · 총점 | InnoRouter ≥92/100 **그리고** InnoRouter − Swift Navigation ≥5점 |
| G2 · 공통 핵심 | K 12개 항목의 합/60×100이 상대 이상. 타입(A1–A3), 기본 동작·수명(B1–B2), API(C1–C2), 비용(D1–D4), native(F1)의 각 그룹도 상대보다 낮지 않음 |
| G3 · 치명적 결함 | 알려진 P1/P2 미해결 0, auth gate 누락·부분 commit·결과 중복·stale callback mutation·확인된 navigation 리소스 누수 0 |
| G4 · 비용 상한 | 공통 runtime CPU median 및 p95 ≤상대 1.10배, peak RSS ≤1.10배, clean/incremental build ≤1.15배. 별도로 관찰 도구를 켠 비용 공개 |
| G5 · 재현성 | comparator/candidate exact SHA와 실행 graph 고정, 독립 배치 재실행 후 결론 유지. 환경 미검증 항목 없음 |
| G6 · 강건성 | 각 영역 가중치를 하나씩 ±20% 바꾸고 합을 100으로 재정규화해도 총점 우위 유지. metric의 95% 구간으로 보수적으로 계산한 점수 차이도 0보다 큼 |
| G7 · 통합 수용 | 실제 소비 앱에서 migration/cold launch/nested flow/auth 재개 수용, 최소 platform CI와 native 결과, 문서 예제 consumer 통과 |

G2의 공통 핵심은 A1/A2/A3/B1/B2/C1/C2/D1/D2/D3/D4/F1이다. aggregate 생성 시 ID 목록에서 분모를 계산하고 12개·60점과 일치하는지 검증한다.

G4는 개별 비용의 허용 가능한 최악 경계를 정한다. G2는 해당 그룹 전체에서도 동등 이상을 요구하므로 작은 범위의 허용 지연이 곧 비용 영역의 우위로 평가되지는 않는다. 기본 correctness를 성능과 교환하지 않는다.

독립 실행 전에는 `미평가`, 일부 항목만 있으면 `부분 검증`으로 표시한다. Swift Navigation의 기준 점수가 매우 높아 G1을 달성할 수 없으면 미달 원인과 비용을 보고하고 목표/범위 재결정이 필요하다. 점수를 올리기 위한 사후 가중치 조정은 하지 않는다.

## 6. 목표에 연결되는 필수 개선 작업

| 작업 | 적용할 개선 | 확인 지표 / 실패 시 다음 행동 |
|---|---|---|
| T01 · 기본 상태 모델 | 서로 배타적인 presentation family, validated state, typed scope/result | A1–A4. invalid case가 남으면 모델 변경 |
| T02 · 수명 정확성 | request provenance, authorization generation, subtree incarnation, terminal ownership | B1–B5. 통제된 await/restore/dismiss interleaving에서 실패하면 commit 경계 보강 |
| T03 · 작은 단위 조합 | 기존 FeatureRoute를 독립 module로 검증, host 단위 도입, 얇은 native bridge, 필요한 앱 코드 축소 | C1/C2. 단순 화면에도 추가 설정이 많으면 기본 API 단순화 |
| T04 · 관찰·비용 | 변경 scope만 관찰 갱신, 불필요한 전체 graph 순회/serialization 제거, persistent 구조 필요성 측정 | D1/D2. 수정 전 profile과 수정 후 동일 workload 증거 필수 |
| T05 · 빌드·dependency | macro-first 유지, 선택 target graph·SwiftSyntax compiler-plugin 비용·incremental 영향 최적화 | D3/D4. 모든 graph 측정은 필수; product/trait 추가는 실제 개선이 있을 때 선택 |
| T06 · 통합 기능 완성 | recursive modal, stable DTO/route migration, bounded policy/storage, Inspector/Testing parity | E1/E2 및 Q02/Q04/Q05. 상대 보조 구현과 결과 동등성 및 비용 비교 |
| T07 · 호환성 | Swift 6.3/6.4·native 지원표·UIKit/AppKit 부분 통합, 낮은 OS/core portability 비용 조사 | F1/F2. 현 지원 floor를 자동 낮추지 않고 점수와 확장 비용을 공개 |

S01에서 baseline을 확보하고, S04 후 기본 탐색·수명, S07 후 API·build, S09에서 전체 비교를 반복한다. 미달 항목은 담당 slice로 돌려보낸다. 기술 우위가 새 릴리스의 완료 목표인 만큼 S09의 Swift Navigation 비교는 선택 작업이 아니다. FlowStacks/XCoordinator는 보조 비교로 유지하며 G1의 주 comparator는 Swift Navigation이다.

## 7. 평가 산출물과 상태

실행 단계에서 다음 산출물을 작성한다. 현재 이 파일들은 작성 예정이며 존재하거나 실행된 것으로 취급하지 않는다.

- `evaluation-contract.json`: 항목 ID/가중치/하위 체크/manifest/toolchain/platform/구성 고정.
- `scenario-results.json`: 양쪽 시나리오, pass/fail/unverified, 원인 분류, 로그 위치.
- `benchmark-raw.json`: 비용 원자료와 반복 표본, 측정 조건.
- `technical-scorecard.json`: 산식, 점수, 공통 핵심, 필수 gate, 구간·감도 분석.
- `technical-comparison.ko.md`: 점수 및 한계, 앱 adapter 비용, 반복 가능한 명령, 미달 개선 작업.

현재 상태: **계획 작성 완료 / 평가 미실행 / 기술 우위 미달성 여부 미판정**. 기존 생태계 포함 점수 72 대 86은 다른 rubric의 과거 평가이므로 여기의 baseline으로 대입하지 않는다.
