발견 번호 F01~08은 두 리뷰의 발견 순서를 유지한다. 작업 순서는 의존성을 기준으로 재배치한다.

앞선 임시 probe는 제거되었으므로, 구현 시 올바른 기대값을 가진 영구 회귀를 먼저 작성한다.

### 유지할 제약

- 기본 사용법은 `@Router` + `InnoRouter` + native host다. 공개 제품은 runtime/Testing/Inspector 세 개를 유지한다.
- mutable authority는 Store 하나다. accepted transition의 state assignment와 revision 증가는 각각 1회,
  rejected/cancelled transition은 각각 0회다. 이미 완료된 commit은 늦은 취소나 저장 실패로 rollback하지 않는다.
- Swift 6.3+, iOS/iPadOS 18+, macOS 15+, tvOS 18+, watchOS 11+, visionOS 2+를 유지한다.
  iOS 17 하향, 5.x 호환층 복원, 최소 Swift 버전의 임의 상향은 범위 밖이다.
- 공개 API/fixture 형식 변경이 꼭 필요하면 6.0의 breaking 변경으로 명시적으로 처리한다.
  테스트를 맞추려고 의미를 숨기거나 잘못된 예전 실행을 그대로 재생하지 않는다.
- 사용자 코드의 비협조적인 policy/I/O를 강제 종료할 수 있다고 약속하지 않는다.
  라이브러리가 소유한 요청의 commit 차단·실행 lane 반환·후속 결과 무시를 보장한다.
- `Derived/`, `InnoRouter.xcodeproj/` 등 기존 비관련 파일을 보존한다. 구현·commit·push·tag·release는
  각각 별도 상태이며 commit/push/tag/release는 별도 요청과 검증 뒤에 수행한다.

## 3. 설계 선택

각 선택은 구현 시 영구 실패 회귀와 대조군으로 검증한다. 기본안이 제약을 충족하지 못하면
근거와 대안을 기록하고 범위를 다시 결정한다. gate를 약화시켜 완료로 만들지 않는다.

| 항목 | 대안 A — 기본안 | 대안 B — 비선택 이유 | 실패·복구 동작 |
| --- | --- | --- | --- |
| F01 | actor-safe teardown을 작은 helper/소유 객체로 분리하는 좁은 compiler-safe refactor부터 검증 | 최소 Swift 상향·전역 최적화 비활성화는 지원·성능 계약을 바꾸므로 사용하지 않음 | 크래시가 남으면 지원 도구 gate를 열어 두고 다음 단계의 검증 가능 여부를 명시 |
| F02 | phase-aware 공통 changelog 규칙으로 draft/RC/GA를 함께 검사 | 버전별 unreleased와 일반 unreleased를 중복 유지하면 충돌을 숨기므로 비선택 | 부정확한 release heading/빈 노트는 fail closed |
| F03 | 실제 umbrella DocC source와 출력 경로에서 migration 링크를 결정 | 옛 SwiftUI 문서 경로를 부활시키는 호환용 복제는 6.0 문서 경계를 흐리므로 비선택 | 대상 migration 문서가 없으면 명확한 실패, 다른 major 문서를 대신 링크하지 않음 |
| F04 | slot generation별 요청·deferral 소유권을 추적하고 cancel을 실제 Store 요청에 전달 | slot만 비우거나 정책의 협조적 취소만 기다리는 방식은 late commit/lane 점유를 막지 못함 | 취소한 generation은 invalid, 이미 commit한 결과는 유지, I/O 오류는 별도 노출 |

| F06 | scoped plan의 의미를 값으로 보존하고 실행/재개 시 최신 부모에 병합 | 캡처한 전체 부모 plan 재사용은 영역 격리를 파괴, rebase 전면 금지는 기존 기능을 축소 | scope 소실·타입/토폴로지 불일치는 commit 전 거절, sibling/scene 유지 |

### R6R10-T00 — 기준 보존과 영구 실패 회귀

- [x] HEAD/status/작업 대상 diff, 실제 Swift/Xcode 및 설치된 SDK/runtime을 기록한다.
- [x] 앞선 8개 발견의 현재 재현을 고정한다. 추적표의 실제 테스트 함수와 수정 전 로그는 이때 채운다.

### R6R10-T01 — Swift 6.3.3 Release 빌드 복구 · F01

접점: `RouterHistory.swift`, 관련 observer/waiter 소유 객체, compiler/consumer 검증.

- [ ] 실패한 CI와 같은 도구/최적화에서 최소 재현을 확보하고 optimizer가 문제 삼는 teardown 경계를 좁힌다.
- [x] MainActor 격리, observer 제거, waiter의 정확히 한 번 종료를 유지하는 최소 refactor를 적용한다.

- [x] runtime뿐 아니라 세 공개 제품을 사용하는 독립 consumer를 Release로 빌드한다.
  기존 external consumer 스크립트의 기본 Debug 성공만 제출하지 않는다.
- [x] Swift 6.4 대조 빌드·성능 smoke·수명 회귀를 함께 확인한다.

### R6R10-T02 — Feature plan의 scoped intent·rebase 격리 · F06

접점: `RouterFeatureScope.swift`, `RouterEnvironment.swift` authority 전달 경계,
Store request semantics/preparation/deferral, `InnoRouterTesting` capture/replay/generator, macro-first consumer.

- [x] scope path와 embedded subtree를 값으로 유지하고, 현재 부모 state에 병합하는 공통 preparation을 만든다.
  단일/nested Feature와 window-local Feature에서 절대·상대 scope 경계를 명확히 한다.
- [x] `.requireUnchangedState`는 원래 revision 제약을 지킨다. `.rebaseOnCurrentState`는 최신 부모에
  Feature 부분만 병합하고 topology/존재/Feature 소유권을 commit 전에 재검증한다.
- [x] 반복 deferral과 queue 대기에서도 현재 subtree에만 적용한다. Feature가 직접 장면을 생성·제거할 수 없다는
  기존 계약을 전체 parent plan을 통해 우회하지 못하게 한다.
- [x] replay가 closure나 녹화된 전체 state를 정답으로 복사하지 않도록 의미를 serializable request metadata로 전달한다.
  새 의미를 기존 fixture가 표현하지 못하면 version을 명시적으로 올리고 지원하지 않는 자료를 선거절한다.
- [x] macro-generated Feature mapping을 사용하는 독립 consumer에서 sibling·window 보존을 검증한다.

완료 기준: AC06. runtime만 고치고 capture/replay가 이전의 잘못된 전체-state 덮어쓰기를 재생하면 미완료다.

### R6R10-T03 — pending link 취소와 실제 resume 요청 연결 · F04

접점: `RouterDeepLinkHandling.swift`, `RouterPendingLinkPersistence.swift`, Store cancellation/deferral 관찰,
`RouterLinkPipelineTests` 및 scenario 회귀.

- [x] slot generation별 진행 중 transition ID/deferral ID를 소유하고, cancel이 해당 요청들을 무효화·취소하도록 연결한다.
  같은 generation의 중복 resume과 필요하면 여러 Store에 대한 소유권도 명확히 한다.
- [x] 실행 precondition도 generation을 확인해 마지막 commit 경계의 race를 닫는다.
  정책이 반환하지 않아도 취소한 요청은 terminal에 도달하고 다음 무관한 요청이 진행해야 한다.
- [x] `submit(.replaceExisting)`과 `cancel()`의 의미를 혼동하지 않는다. 기존 replacement 대조군의
  새 링크 보존 계약을 유지하고, cancel은 자신이 취소한 generation 밖의 요청을 건드리지 않는다.
- [x] commit 전 취소, commit 후 늦은 취소, durability 실패를 구분한다. `cancel()`의 성공 뒤 저장소가
  최신 slot에 수렴하고 이전 resume이 취소한 링크를 재저장하지 않게 한다.
- [x] `.onAcceptance`/`.always`, caller Task 취소, 중복 cancel 및 request cancellation provenance를 검증한다.

완료 기준: AC04. 비협조적 정책 gate를 풀어야만 취소가 완료되는 테스트는 통과로 인정하지 않는다.

### R6R10-T04 — deferred native close의 canonical/native 일치 · F05

접점: `RouterSceneLifecycle.swift`, `RouterSceneDriver.swift`, scene reconciliation,
`RouterSceneLifecycleTests`와 platform native tests.

- [x] native effect를 주입·관찰 가능한 최소 경계로 분리하되 navigation authority를 추가하지 않는다.
- [x] `.deferred` 직후 같은 authoritative lifetime을 reopen하는 기본안을 구현한다.
  이후 allow commit은 닫기를 반영하고 reject/cancel/expiry는 복구한 Scene을 유지한다.
- [x] UUID/catalog/immersive lifecycle token과 현재 state를 effect 직전에 재검증한다.
  중복 callback·반복 deferral·Scene 교체·driver 종료가 중복 open이나 새 lifetime 제거로 이어지지 않게 한다.
- [x] open 실패 및 stale rollback은 기존 system repair 원칙으로 처리하고, 실패를 성공 이벤트로 기록하지 않는다.
- [ ] 주입 effect 테스트와 실제 macOS/iPadOS 창·visionOS immersive 동작을 구분해 실행 근거를 남긴다.

### R6R10-T05 — scope 캐시의 수명·용량 정리 · F07

### 완료 수준

1. **계획 완료:** 범위/선택/AC/회귀/실행 순서를 정의한 단계다.
2. **수정 및 로컬 검증 완료:** 현재 단계. T00~T09의 코드·문서 수정과 로컬 자동화 검증을 완료했으며,
   exact Xcode 26.6과 실제 native interaction처럼 이 환경에서 닫을 수 없는 항목은 열린 gate로 분리했다.
3. **배포 가능 판정:** 수정 완료에 더해 정확한 후보의 pinned CI/native/external gate와 유지관리자 승인이 충족된다.
4. **발행 완료:** 별도 승인된 tag/release 실행 및 exact-tag 소비·배포 결과 검증까지 끝난 상태다.

### 향후 commit 분리안

commit/push 승인 시에만 적용한다. 각 묶음에 해당 회귀와 문서/API 변경을 함께 넣고 전체 stage를 하지 않는다.

1. compiler-safe lifecycle teardown 및 pinned Release 회귀
2. Feature scoped plan/rebase와 capture·replay·consumer
3. pending-link 취소 소유권과 durability 회귀
4. deferred native lifecycle 복구와 platform tests
5. scope cache 수명과 dispatch 회귀
6. 국소 native invalidation과 observation 회귀
7. phase-aware changelog 계약과 shell tests
8. migration release-note 경로·fixture 및 최종 근거 정리

### 실패 시 원칙

- 새 regression이 실패하면 해당 단계와 연관 gate를 열어 둔다. 기대값 완화·test skip·성능 기준 하향으로 숨기지 않는다.
- 다른 사용자의 작업을 되돌리지 않는다. 이미 commit된 수정의 rollback이 필요하면 정확한 대상과 영향을 먼저 확인한다.
- 구현 중 새로운 독립 결함이나 공개 계약 변경이 필요하면 이 8건의 완료 범위와 분리해 기록하고 필요한 결정을 요청한다.
