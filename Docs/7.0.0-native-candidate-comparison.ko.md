# Router 7.0 후보 native 실패: 이전 수정과의 비교

2026-10-06. **출시 준비는 계속 차단 상태다.** 이전 ticket 검사 수정의 효과와 한계는
결정적 테스트로 확인했다. 그러나 공식 실패 당시 native open의 실제 반환 enum과
두 번째 생성 요청의 호출 주체는 아직 확인하지 못했다. 이번 로컬 통과를 원인 수정으로
보고하지 않는다. 제품 동작·공개 API·재시도 정책을 변경하지 않았다. 최초 보고 이후 사용자가 진단용 draft PR 게시를 승인했다.

## 이전에 고친 것과 이번에 남은 것

| 순서 | 이전 검사 없는 구현 | 현재 ticket 검사 | 이번 확인 |
|---|---|---|---|
| native 실패 반환 → repair 대기 → matching appearance → repair 실행 | 이미 나타난 scene의 canonical을 잘못 삭제 | appearance가 ticket을 소비하므로 repair 거부 | 검사만 제거하면 canonical·revision 두 assertion 실패; 복원하면 통과 |
| native 실패 반환 → repair commit → 늦은 appearance | canonical 삭제 후 만료된 lifetime | 같은 결과. 검사 시점에는 ticket이 유효했음 | commit 완료를 await한 뒤 실제 admission helper를 호출하면 거부; canonical 복구 없음 |
| native 실패 반환 → appearance 없음 | 실제 native 실패를 canonical에 반영 | 같은 결과 | canonical nil, unrelated commit 보존, revision 2 |

이전 수정은 **이미 발생한 appearance의 효력을 늦게 실행되는 repair가 덮어쓰는 경합**을
막았다. 아직 나타나지 않은 scene을 예측하거나 완료된 repair를 되돌리는 변경이 아니다.
후자의 동작을 추가하면 명시적 dismiss나 교체 lifetime까지 되살릴 위험이 있으므로,
실제 native 실패의 원인을 확인하지 않고 그러한 정책 변경을 적용하지 않았다.

테스트는 continuation으로 unrelated Store 요청을 멈추고 request observation으로
repair 제출을 확인한다. repair 후 케이스는 restoration task의 완료를 기다린 뒤
appearance를 호출한다. sleep, 시간 추정, 반복 재시도로 순서를 만들지 않는다.
`onAppear`의 기존 수락/거부 코드를 package helper로 그대로 추출하여 테스트도 같은
경계를 사용한다. 기존 genuine `.error`/`.userCancelled`, driver 교체, lifetime 교체,
명시적 dismiss 및 거부 precondition 통제를 유지했다.

## canonical 삭제의 코드 경로: 증명한 부분과 추론

현재 코드는 복원 open이 `.error` 또는 `.userCancelled`를 반환하고 lifetime/ticket이
여전히 유효하면 아래 경로로 canonical immersive space를 제거한다.

`restoreRouterImmersiveSpaceAfterDeferredClosure`
→ `reconcileSceneSystemFailure(.dismissImmersiveSpace, executionPrecondition:)`
→ policies를 우회하는 Store request
→ `commitPreparedTransition`의 최종 precondition 검사
→ `commitOutcome` / 단일 state·revision commit.

이 경로와 repair 뒤 appearance 거부는 결정적 `.error` 테스트로 재현했다. ticket 검사는
repair 실행 전에만 영향을 준다는 것도 검사 유무 A/B로 증명했다.

공식 probe에서는 실패 전까지 deferral이 유지되고 resolve/cancel API에 도달하지 않았다.
일반 dismiss는 policy에서 defer되며, 최초 driver open은 성공 event를 남겼다. 따라서
복원 open 실패 repair가 canonical 삭제의 유력한 코드 경로다. 그러나 원본에는
그 함수의 반환 enum·repair submit·commit trace가 없어 **그 실행 경로를 직접 관측했다고
단정하지 않는다.** `InvalidScene` 로그만으로 SwiftUI enum이 정확히 `.error`였다고
소급해서 확정할 수도 없다. 오류 발생 이유와 두 번째 생성 요청의 주체는 남은 차단점이다.

## Xcode 27 대조 실행과 한계

1. 기존 probe + bounded 즉시 출력: allow/reject/cancel 각 1회 통과.
2. 열림을 polling 대신 event continuation으로 기다리는 진단 allow 1회 통과.
   실제 열린 통지→닫기 간격은 약 81.894ms로, 공식 실패의 1.711ms를 재현하지 못했다.
   따라서 이 실험으로 빠른 닫기 가설을 배제하지 않는다. 임시 probe 변경은 최종 코드에서 제거했다.
3. callback 중 출력을 하지 않는 bounded 메모리 trace + 원래 probe:
   allow/reject/cancel 각 1회 통과. trace는 verdict 후 출력했다.

모든 대조에서 surviving driver를 통한 복원 open은 `.opened`였고, matching appearance가
반환 전에 ticket을 소비했다. 이는 성공 경로 증거이며 **공식 실패의 actual enum이나
두 번째 요청 출처를 입증하지 않는다.** 총 7개 native case를 조건별로 보존했고,
실패를 통과할 때까지 반복하거나 대기 한도·성공 기준을 늘리지 않았다.

순서·통제 테스트 25개가 통과했다. 이전 검사 제거 A/B는 세 순서 중 repair 전 appearance만
의도한 두 불변식으로 실패했고 나머지 두 통제는 통과했다. 검사 복원 뒤 25개가 다시 통과했다.
세 공개 제품 API baseline(1,825/236/275 symbols)과 source lint도 통과했다.
첫 테스트 편집에는 Swift Testing closure Sendable 추론 컴파일 오류가 있었고 명시 타입으로
수정했다. 이 컴파일 실패를 제품 회귀의 red 증거로 세지 않는다.

## 최소 후속 범위

현재 증거로 정당화할 수 있는 최소 변경은 **진단과 순서 테스트**다. 동작 수정안은 아직
선정하지 않는다. 로컬 진단은 Debug opt-in, process당 256건 한도이며 다음을 연결한다.

- process ID, native 호출별 request UUID, driver owner 등록/해제와 실제 반환 enum
- restoration fallback/driver 출처, lifetime, ticket
- repair 제출, 실행 precondition, transition ID를 포함한 scene commit, repair 결과
- appearance 수락/거부

공식 실패 환경에서 이 진단을 실행해야 마지막 인과 고리를 확인할 수 있다. 사용자가 승인한 게시 범위는 해당 7개 Swift 파일과 이 보고서, 그리고 visionOS native
step에만 `SIMCTL_CHILD_INNOROUTER_SCENE_TRACE=1`을 넣는 workflow 1행이다. 해당 환경변수를
연결하고 native 호출별 UUID와 process ID를 추가해 호출/반환의 대응을 명확히 했다.
공개 API·policy·retry·timeout·합격 조건은 그대로다. 이 PR은 진단용 draft이며
merge/tag/release는 범위에 포함하지 않는다.

이는 Simulator 샘플 진단이다. 실제 적용 앱 pilot, 성능 scorecard, 다른 Xcode/OS 및 실기기
검증을 완료한 것으로 해석하지 않는다. native 실패 반환과 후속 생성의 연결이 확인되기
전까지 7.0 출시 차단을 유지한다.
