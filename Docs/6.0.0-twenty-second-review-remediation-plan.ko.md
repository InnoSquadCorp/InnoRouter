- 미확인: exact commit 원격 CI·downstream revision, 실제 앱에 mount한 macOS/iOS lifecycle runtime, pinned Xcode 26.6/Swift 6.3.3 전체 실행. 로컬 결과는 이 외부 gate를 대신하지 않는다.

## 2. 동작 계약

### 기존 계약 유지

- FR-001: 무효화된 이전 저장의 durable 부활 금지. 저장 명령의 순서는 동기 예약 순서이며, 성공한 삭제 뒤 새로 수락한 저장은 허용한다.
- FR-002: 순환 edge는 제외하고 정상 local·비순환 feature를 보존한다. origin·ambiguity·round-trip 계약을 약화하지 않는다.
- FR-003: 미완료 복원의 자연 소유권 종료와 명시적 stop을 구분한다. 새 navigation과 다른 유효 owner를 보존한다.
- FR-004·005: 지원되는 generic/중첩 helper, 비충돌 선언은 계속 소비 가능해야 하고 실제 충돌은 계속 거절해야 한다.
- FR-006·007: 실패 테스트도 종료·정리되며 직접 증거가 있는 기준만 완료로 표시한다.
- NFR-001~004: 기존 macro-first·3제품·단일 상태 권한·플랫폼/언어 하한·MainActor 밖 I/O·사용자 변경 보존 계약은 그대로다. Swift 6.4 전용 취소 API나 새 의존성을 필수화하지 않는다.

### FR-008 — 탐색 종료 한계와 불완전 탐색의 실패 규칙

라이브러리가 수행하는 macro-generated/feature-bridge 탐색은 concrete 타입이 계속 달라져도 정해진 깊이·작업량 안에 종료한다. 알려진 동일 타입 cycle의 edge 제외와, 미탐색 후보가 남은 budget 초과를 구분한다.

- 정상 cycle: 해당 edge의 catalog 기여는 없음, purity는 false, 해당 edge의 resolve·case-name·URL은 nil. 독립 local 경로의 정상 결과는 보존한다.
- budget 초과: 탐색한 일부 후보만으로 성공을 결정하지 않는다. 해당 최상위 연산의 resolve·case-name·URL은 nil, purity는 false, catalog는 완전한 것처럼 부분 결과를 반환하지 않는다. 제안은 빈 entries와 탐색 한계 상태를 함께 유지하는 것이다. explain은 accepted가 아닌 한계 초과 거절을 표현한다.
- 호출 단위로 context와 budget을 소유한다. 동시에 호출한 두 root, 진짜 중첩된 독립 탐색, catalog 이후 resolve가 서로의 상태를 상속하여 누락을 만들면 안 된다. feature edge의 같은 탐색은 context를 공유한다.
- 재귀 route 값의 생성·Hashable·일반 navigation·Feature embed/extract는 계속 지원한다. 사용자 작성 resolver 자체의 무한 루프나 라이브러리 bridge를 우회한 직접 재귀를 강제 중단한다는 약속은 아니다.

FR-008은 기존 D03의 잘못된 "상한 불필요" 판단을 대체하는 제안이다. 상한으로 깊은 유효 구성의 관찰 결과가 바뀔 수 있으므로 외부 동작 변경으로 문서화한다.

## 3. 기술 설계 제안

### D22-01 — 초기 restore를 한 상태 전이로 표현

대안 A는 `stop`·`detach`마다 두 Bool을 보정하는 것이다. 조합과 종료 경로가 늘어 다시 불가능한 상태를 허용하므로 선택하지 않는다. 대안 B인 단일 초기 복원 phase와 기존 generation/owner lease의 결합을 선택한다. 공개 표시 status는 이 phase를 결정하지 않는다.

| 현재 phase | 사건 | 다음 phase / 다음 activation |
| --- | --- | --- |
| 미시도 | 최초 activation 예약 | 진행 중(lifetime), 예약 시 시작 revision 고정 |
| 미시도 | 아무 시도 전 stop | 미시도 유지. 최초 restore를 영구 차단하지 않음 |
| 진행 중 | noSnapshot 또는 복원 판단 완료 | 완료. 이후 observation-only |
| 진행 중 | 실패 또는 마지막 유효 owner의 자연 종료 | 재시도 가능. 다음 activation이 새 load를 시작 |
| 진행 중 | 명시적 stop | 명시적 중단. 이후 몇 번 detach/attach해도 observation-only |
| 완료·명시적 중단 | stop·자연 detach·재연결 | phase 보존. 초기 snapshot 재실행 금지 |
| 모든 phase | 옛 generation의 worker/caller/detach | 현재 phase·observer·owner 변경 없음 |

완료의 의미에는 기존 restore 결과(적용·거절·deferred 등)에 대한 현재 계약을 보존한다. deferred request family의 수명은 phase와 별도로 추적하며 stop 후 다시 navigation을 commit하지 못해야 한다.

수동 `activate`, modifier `attach/detach`, waiter 취소, stop, deinit의 소유권 종료를 목록화한다. ID만 같은 옛 detach가 새 lease를 종료하지 않는지도 확인한다. 저장 성공/실패/진행은 phase를 변경하지 않으며 `stop()`이 이미 시작한 I/O를 rollback한다고 약속하지 않는다.

대상: `RouterStateRestoration.swift`, 해당 modifier, 필요 시 `RouterRuntimeDependencies.swift`의 package-only 테스트 경계. 공개 root 사용법을 바꾸거나 별도 navigation 상태 소유자를 만들지 않는다.

### D22-02 — root와 child가 같은 탐색 경로를 정확히 한 번 등록

대안 A는 현재 bridge에만 guard를 보강하는 것이다. root 누락을 해소하지 못한다. 대안 B는 generated entry와 runtime bridge가 공통 진입 규약을 쓰는 것이며 이를 선택한다.

- 새 public-root 탐색과 기존 context의 feature-edge dispatch를 명시적으로 구분한다.
- root도 첫 frame으로 등록한다. bridge가 허가한 child가 generated entry에서 이중 등록되어 즉시 cycle 취급되지 않도록 frame 진입 권한을 한 곳에서 관리한다.
- 경로에서 나오면 frame을 해제한다. 같은 child를 공유하는 sibling을 전역 visited 집합으로 제거하지 않는다.
- 다섯 연산(catalog/purity/resolve/case-name/URL)과 explain·outbound round-trip의 교차 호출을 검증한다. 다른 연산이라는 이유로 무제한 새 context를 만들어 종료 budget을 회피해서도 안 된다.
- generated 전용 경로와 수동 DeepLinkRoute conformance의 bridge 경로를 각각 실제 consumer로 확인한다. public signature는 이 계획에 가짜 API로 확정하지 않고 T09에서 최소 API 설계를 기록한다.

대상: `DeepLinkRoute.swift`, `RouterDeepLinkRendering.swift`, 필요 시 `DeepLinkRouteCatalog.swift`의 한계 상태 전달, macro specification/렌더링. 변경되는 public bridge·진단은 baseline·CHANGELOG·DocC·consumer를 함께 갱신한다.

### D22-03 — 동일성 검사에 깊이·전체 진입 budget 추가

대안 A는 타입 이름 문자열이나 generic 명칭만 비교하여 같은 nominal 타입을 모두 cycle로 취급하는 것이다. 서로 다른 정상 특수화를 오진할 수 있어 선택하지 않는다. 대안 B는 concrete 경로 검사에 명시적인 깊이·전체 진입 budget을 추가하는 것으로 선택한다.

제안 기본값은 root 포함 깊이 64, 최상위 탐색당 frame 진입 시도 1,024회다. child별 초기화나 sibling 복제 budget은 금지한다. 깊이만 제한해도 넓은 그래프의 탐색량이 폭증할 수 있으므로 전체 작업량도 제한한다. 메타데이터/child-body 생성에 앞서 진입 허용을 검사한다.

T09에서 63/64/65 깊이와 1,023/1,024/1,025 진입의 정의·경계 fixture를 고정하고, T12에서 지원 하한 toolchain과 현재 toolchain으로 비용·종료를 검증한다. 수치를 바꾸어야 하면 근거·호출자 영향·같은 경계 테스트를 함께 수정하고 기록한다. 검증 없이 "충분한 수치"나 "무제한 지원"이라고 쓰지 않는다. 공개 설정 기능은 이번 범위에 자동 추가하지 않는다.

한계 초과는 context에 남겨 최상위 결과까지 전파한다. 특히 먼저 발견한 local 1건만 반환하거나 URL을 round-trip 성공으로 처리하면 안 된다. 한계 초과 진단을 기존 public 결과로 표현할 수 없다면 필요한 최소 공개 진단 변경을 같은 묶음에서 처리한다.

### D22-04 — 결과·예약·cleanup을 관측하는 테스트 장치

대안 A는 sleep/yield 횟수 또는 timeout만 늘리는 것이다. 경계 증명과 cleanup에 실패하므로 선택하지 않는다. 대안 B는 등록/예약/worker 진입을 제어하는 package-only 의존성과 유한 대기를 사용하는 것이다.

- `RouterRuntimeDependencies` 등 기존 injection 경계를 먼저 활용한다. 필요하면 production 기본값이 즉시 진행하는 최소 package seam을 추가한다. 공개 API에 테스트용 barrier를 노출하지 않는다.
- 시작 revision·observer·lifetime이 확정된 뒤, worker load 진입 전 멈출 수 있어야 한다. load 진입 후 barrier를 AC-012의 대체 증거로 쓰지 않는다.
- durability 명령의 reserve 이벤트와 ticket을 관측한다. `status == .saving`이나 yield 10회로 remove/cancel 수락을 추측하지 않는다.
- 의도된 취소는 정확한 cancellation 결과를 단언한다. 성공해야 하는 cancel/save/remove를 `try?`로 삼키지 않는다.
- 누락/취소/timeout 시 barrier 해제·stream 종료·Task 취소 후 waiter 종료, 공유 queue 후속 진입, host 해제를 확인한다. 마지막 자연 detach의 정리는 안전용 `stop()` 전에 단언한다.
- 별도 프로세스 watchdog은 hang/crash의 최후 검출기다. watchdog 종료를 테스트의 정상 실패·cleanup 성공으로 세지 않는다.

## 6. 검증·증거·완료 조건

### 실행 레인

- 각 묶음: 관련 회귀·정상 suite, macro 변경의 expansion+behavior+실제 consumer, `git diff --check`, source lint.
- 최종 후보: `./scripts/principle-gates.sh --platforms=all`. 내부 전체 suite/플랫폼 compile·interface/DocC/API/docs/examples/consumer/lint/probe를 중복 실행 횟수로 부풀리지 않는다.
- 별도 레인: `./scripts/migration-consumer-smoke.sh`, `./scripts/sanitizer-smoke.sh thread`, `./scripts/sanitizer-smoke.sh address`, `./scripts/performance-smoke.sh .build/performance-smoke.json`.
- coverage: `swift test --enable-code-coverage --jobs 2 --no-parallel` → `./scripts/generate-coverage-report.sh coverage.lcov coverage-full.lcov` → `./scripts/validate-coverage-report.py coverage.lcov --minimum-line-coverage 85`. 기존 기준을 낮추지 않는다.
- 변경 기록: `./scripts/check-docs-consistency.sh`, `./scripts/check-changelog-sync.sh`의 실제 check/skip 결과 구분. API diff가 생기면 해당 baseline·migration·DocC·외부 consumer까지 같은 후보에 포함한다.
- 수명: 실제 macOS mounted modifier를 통한 T10/AC-031 검증과 iOS simulator root 재연결 대조를 수행한다. 나머지 플랫폼의 compile 성공을 native runtime·VoiceOver 성공이라고 표현하지 않는다.
- 호환성: pinned Xcode 26.6/Swift 6.3.3 레인과 현재 Xcode 27/Swift 6.4 레인을 구분한다. 미설치 환경이면 해당 레인은 미실행으로 남기고 설치·원격 실행을 임의로 승인받았다고 보지 않는다.
- 배포 전: exact commit 원격 CI, exact downstream revision, RELEASING의 플랫폼별 필수 runtime/접근성 기준은 별도 배포 gate다. 이번 계획의 수행만으로 tag/release 권한이 생기지 않는다.

상태 표의 한 행에는 `AC → 후보 SHA 또는 scoped 파일 manifest/hash → 명령/환경 → 실제 assertion/exit → 로그 → 통과/실패/미실행`을 연결한다. 미커밋 후보는 tracked diff만이 아니라 새 source/test도 hash에 포함한다. 사용자 생성 산출물은 명시적으로 제외한다. 파일·의존성·설정이 바뀌면 영향 레인을 다시 연다.

### 계획 자체의 반례 검사

다음과 같은 잘못된 구현도 실패해야 이 계획을 충족한다.

- 모든 activate를 observation-only로 바꾸면 최초 restore/자연 retry 대조가 실패한다.
- 모든 Feature 딥링크를 nil로 바꾸면 AC-032·037이 실패한다.
- 모든 같은 child 타입을 전역 제거하면 AC-033이 실패한다.
- root와 bridge 양쪽에서 중복 등록하면 AC-037의 비재귀 child 소비가 실패한다.
- 상한에서 조용히 잘라 첫 local route를 반환하면 AC-036이 실패한다.
- generic Router 자체를 금지하면 AC-037의 일반 navigation·typed consumer가 실패한다.
- cleanup 전에 안전용 stop으로 owner를 지우면 AC-031의 자연 detach assertion을 충족하지 못한다.
- 테스트 수/종료 문구만 검사하면 AC-039가 gate 자체를 실패시킨다.

### 종료·인계

제품 수정 완료는 F01~F03의 원본 반례와 정상 대조가 같은 후보에서 통과한 상태다. 로컬 검증 완료는 Q01과 AC-001~040의 필수 로컬 증거까지 채워진 상태다. 배포 준비와 발행 완료는 별도다. "가능한 결함이 더는 없다"를 종료 조건으로 삼지 않는다.

실행 승인 후에도 필수 경계가 검증되지 않으면 해당 단계의 완료를 보류하고 이유·다음 행동을 보고한다. public API 또는 budget 동작을 이 계획의 제안 범위보다 크게 바꿔야 하면 구현 전에 영향과 대안을 다시 제시한다.

추후 commit·push를 요청받으면 (1) 검증 기반+복원 수명, (2) root 순환, (3) bounded generic 탐색+API/consumer/docs, (4) 나머지 검증+증거 정리의 논리적 묶음을 기준으로 나눈다. green이 아닌 중간 상태를 완료 커밋으로 게시하지 않는다. push 후에는 원격 일치·worktree 보존 확인과 사용자 지침의 XcodeBuildMCP 정리를 수행하되 활성 build를 중단하지 않는다.
