## 1. 목표와 비목표

목표는 새 기능 확장이 아니라 기존 공개 계약의 취소·소유권·타입 안전성을 회복하는 것이다.

- 기본 사용은 `@Router`와 typed helper, `import InnoRouter`를 유지한다. `@Routable`/`@CasePathable`은 지원하는 보조 매크로이며 기본 구조를 대체하지 않는다.
- 공개 제품은 `InnoRouter`, `InnoRouterTesting`, `InnoRouterInspector` 세 개를 유지한다.
- Store만 navigation state를 변경한다. 성공 commit은 assignment/revision 증가 각 1회, 거절·취소 자체의 commit은 0회다. native rollback이 필요한 경우 기존 system-repair 경로를 사용한다.
- Swift 6.3+, iOS/iPadOS 18+, macOS 15+, tvOS 18+, watchOS 11+, visionOS 2+를 유지한다. Swift 6.4 전용 취소 API를 필수 의존성으로 도입하지 않는다.
- 필요한 6.0 breaking change는 허용되지만 우선 내부 소유권과 생성 코드 수정으로 해결한다. 공개 변경이 필요하면 영향·대안·migration을 먼저 기록한다.
- iOS 17 하향, 5.x 호환층 복원, 신규 제품/서비스, 무관한 구조 개편, 자동 commit/push/tag/release는 비목표다.
- 테스트 기대값을 현재 버그에 맞추거나 coverage·성능 threshold를 낮추지 않는다. 단순 sleep/yield 반복을 작업 완료 증거로 삼지 않는다.

## 3. 구현 전 고정할 설계 결정

### D01 — 종료 처리에서 소유권을 먼저 버리지 않는다

복원 활성화의 정상 종료·취소·오류·stop은 generation을 확인한 공통 종료 규칙을 사용한다.
취소/오류로 종료할 때는 해당 request root의 queued/active/deferred family 취소를 요청한 뒤 추적 상태를 해제한다.
이미 terminal인 family는 멱등적으로 정리하고 다른 driver의 요청은 건드리지 않는다.
성공 후 정상 보류된 복원은 기존 소유권을 유지한다. 공유 attachment는 다른 살아 있는 lease를 조기 종료하지 않는다.

### D02 — native 효과의 소유권을 부분 진행 상태와 함께 기록한다

- 효과 식별은 Store identity + scene ID/route + lifetime + operation 세대를 구분한다. 이 기록은 효과 조정용이며 두 번째 navigation Store가 아니다.
- SceneDriver와 lifecycle 복구의 immersive open/dismiss는 같은 native 효과를 다루는 공유 직렬화·소유권 경계를 사용한다. 서로 독립된 큐에서 무조건 dismiss를 실행하는 방식은 피한다.
- 오래된 open이 `.opened`로 완료되면 자신이 실제로 연 공간을 정리한 후 replacement open이 진행되어야 한다. 최신 공간에 대한 늦은 dismiss는 금지한다.
- `onAppear`가 정상적으로 ticket을 해제한 경우와 Store가 scene을 제거/교체한 경우를 구분한다. ticket 불일치만으로 정상 공간을 닫지 않는다.
- Window open/dismiss를 실행할 때 해당 효과의 identity도 함께 기록한다. 전체 reconciliation 성공 끝에만 Store identity를 저장하지 않는다.
- Store 교체 중 부분 상태에 여러 소유자가 섞일 수 있으므로 공유 identity 필드를 일찍 덮는 단순 패치 대신 각 효과가 어느 소유자에 속하는지 보존한다.

공유 효과 경계를 어디에 보관·연결할지는 T02의 작은 내부 설계 검증에서 확정한다. 조건은 Store 교체를 넘는 직렬화, lifecycle 접근, 해제/취소, unrelated owner 보호를 모두 통과하는 것이다. 이를 위해 공개 API가 필요해지면 구현 전에 별도 차이를 보고한다.

### D03 — 여러 History를 지원하고 자기 이동만 중복 기록에서 제외한다

다중 연결을 갑자기 금지하는 대신 owner/request-family 상관관계를 사용한다. `.history` source 전체 무시는 제거한다.

- 자기 이동은 기존 지정 target의 완료/보류 규칙을 적용하고 중복 entry를 만들지 않는다.
- 다른 History가 성공시킨 이동은 현재 탐색값과 동등한 보관 entry가 있으면 그 cursor로 동기화한다. 여러 후보면 현재 cursor와 가장 가까운 것, 동률이면 큰 index를 선택한다.
- 일치하는 entry가 없으면 일반 외부 탐색처럼 forward branch를 정리하고 현재 projection을 기록하며 capacity를 적용한다. 과거 entry의 sourceRevision은 수정하지 않는다.
- 다른 어댑터의 entry/checkpoint/세션키를 복제하지 않는다. 동기화는 Store 이벤트 관측만으로 하며 새 탐색 요청을 발생시키지 않는다.
- 자기 이동 완료가 늦게 반환하더라도 그 사이의 더 최신 commit/cursor를 덮지 않는다. rejected/cancelled 요청 자체로 cursor를 이동하지 않되, 별도 성공한 외부 이동은 반영한다.
- navigation 동등성은 기존 모달·배지·scene inventory 제외 계약을 유지한다. stop한 History는 더 이상 동기화하지 않고 reset은 그 인스턴스의 세션 경계로 유지한다.

### D04 — 매크로는 구문 문맥과 내부 이름을 보존한다

- payload label은 enum 호출에만 사용하고 extract의 내부 변수는 위치 기반으로 충돌 없이 생성한다.
- `#if/#elseif/#else`는 macro host에서 평가하지 않고 target compiler에 전달한다. case 분기와 attribute 분기를 따로 처리하며 조건 안의 무관한 marker를 무작정 복사하지 않는다.
- payload 타입의 `Self`는 TypeSyntax를 통해 원래 enum 문맥으로 정규화한다. 문자열 전체 치환으로 `SelfNamed`·qualified 이름을 훼손하지 않는다.
- 매크로 변경의 완료 증거는 expansion 문자열만이 아니다. `Cases` 멤버를 실제 사용한 debug/release 소비자와 embed/extract 왕복을 포함한다.
- 런타임/Testing 제품에 SwiftSyntax 의존성을 전파하거나 toolchain/의존성을 임의로 올리지 않는다.

### D05 — 생성 소스는 지원하는 식별자 범위 안에서만 출력한다

공통 validator가 단독 `_`를 모든 단일/qualified name component에서 거절한다. `_name`은 계속 지원한다.
`testName`은 단일 선언 이름, route/factory는 기존 qualified-name 규칙을 유지하며 escape/Unicode 지원 범위를 이번에 임의 확장하지 않는다.
`generate`와 `generateFiles`는 같은 오류 타입을 사용하고 source/파일 묶음을 반환하기 전에 검증을 끝낸다.

## 6. 불완전 수정 반례 검토

문서 조건만 형식적으로 만족하면서 의도를 어기는 아래 구현은 완료로 인정하지 않는다.

- inactive만 표시하고 보류 요청은 남기는 수정, source 전체를 취소해 다른 owner를 죽이는 수정.
- stale open 결과에 무조건 dismiss하여 이미 열린 replacement를 닫는 수정, onAppear ticket 해제를 stale로 오판하는 수정.
- 공유 previousStoreIdentity만 일찍 덮어 다른 Store의 남은 native 효과를 최신 것으로 오인하는 수정.
- 외부 history commit을 무조건 append하여 이미 보관된 이전 위치로 cursor를 맞추지 못하는 수정, 과거 await 완료가 최신 cursor를 되돌리는 수정.
- 한 label만 rename, `Self` 전체 문자열 치환, 모든 generated member에 가장 높은 availability를 붙이는 수정.
- macro 선언만 컴파일하고 생성 member는 참조하지 않는 fixture, expansion snapshot만으로 완료 선언.
- 단독 `_`를 막으면서 `_name`까지 거절하거나 generateFiles 한쪽만 수정하는 검증.

이 목록에 없는 유효 반례를 발견하면 요구사항/AC를 보완하고 다시 Draft 검토 대상으로 남긴다. 8건 처리 자체를 무결함 보증으로 해석하지 않는다.
