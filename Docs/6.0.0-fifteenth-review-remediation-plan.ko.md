## 1. 목표와 비목표

목표는 기존 기능의 일관성·취소·생성 코드 안전성을 회복하고, 같은 방어가 인접 경로에서 다시 누락되지 않게 하는 것이다.

- 기본 형태는 `import InnoRouter` + `@Router` + typed helper다. 공개 제품 3개와 RouterStore 단일 authority를 유지한다.
- Swift 6.3+, iOS/iPadOS 18+, Catalyst 18+, macOS 15+, tvOS 18+, watchOS 11+, visionOS 2+를 유지한다. Swift 6.4 전용 취소 API는 필수 의존성으로 도입하지 않는다.
- 정상 transition은 기존 단일 assignment/revision 계약을 지키고, 취소된 미시작 effect는 추가 commit을 만들지 않는다. 필요한 native 실패 복구는 기존 system-repair 경로를 사용한다.
- 6.0 미출시 후보의 필요한 breaking change는 명시적으로 설계한다. 5.x 호환 코드나 충돌하는 deprecated alias를 새로 남기지 않는다.
- iOS 17 하향, 신규 기능·제품, 무관한 리팩터링, 기준 하향, 자동 Git 발행은 범위 밖이다.

## 3. 설계 결정 제안

### D01 — History 이동 확정을 한 경로로 모은다

- 대안 A: restoreCheckpoint의 await 뒤에 revision guard만 추가한다. 덮어쓰기는 줄이지만 commit 당시 cursor 확정이 늦고 다음 이동의 분기 기준이 어긋날 수 있어 채택하지 않는다.
- 선택 B: History가 소유한 이동의 target entry ID, operation generation, request root를 submission 전에 등록한다. committed/unchanged terminal에서 해당 결과의 state/revision으로 entry와 cursor를 확정하는 공통 경로를 둔다.
- 즉시 이동과 deferred resume가 같은 정규화·capacity·forward-branch 규칙을 사용한다. owned metadata는 terminal에서 한 번 소비하고, 외부 History의 이동 동기화와 구분한다.
- 외부 continuation은 더 최신 Store 상태를 읽어 과거 entry를 다시 쓰지 않는다. 반환 transition은 실제 원래 결과를 유지하고, 반환 cursor는 반환 시점 History 상태를 반영한다.
- reset/stop/취소/재보류로 무효화된 generation은 이후 terminal에서 entry를 변경하지 않는다. validation으로 보정된 실제 목표를 기록하며, 이벤트가 가진 결과 대신 무관한 최신 전역 상태를 사용하지 않는다.

### D02 — 항목 변경과 waiter 완료를 같은 경계에서 처리한다

- 대안 A: 문제가 드러난 restoreCheckpoint 한 곳에 resume 코드를 복사한다. deferred/unchanged 경로를 또 놓칠 수 있어 채택하지 않는다.
- 선택 B: entries/cursor/capacity 정리가 끝난 후 조건을 만족한 recordWaiter를 제거하고 완료하는 공통 helper를 둔다. 일반 append, 즉시·보류 체크포인트 복원 등 모든 항목 증가 경로에서 호출한다.
- 각 continuation은 정확히 한 번 끝낸다. 충족 시 true, 미충족 상태에서 caller cancellation/stop이면 false라는 기존 계약을 유지한다. record/revision waiter를 혼동하지 않는다.
- 새 항목이 없는 metadata import 자체는 기록 완료로 보지 않는다. 무한 대기를 polling/sleep 또는 임의 timeout으로 감추지 않는다.

### D03 — effect 실행 유효성과 필수 cleanup 수명을 분리한다

- 대안 A: 공유 큐의 모든 Task에 취소를 전파한다. 이미 열린 obsolete 공간의 보상 dismiss까지 사라질 수 있어 채택하지 않는다.
- 선택 B: host/reconciliation 유효성을 명시적 ticket으로 전달하고, 큐 진입 후 native open/dismiss 및 rollback 시작 전에 host, Store identity, revision, scene lifetime을 다시 검증한다. 새 unstructured Task의 Task.isCancelled만으로 판단하지 않는다.
- host 제거·Store 교체·새 reconciliation은 이전 미시작 작업을 무효화한다. 큐에서 시작도 하지 않은 작업은 native 호출, 실패 이벤트, system repair를 모두 만들지 않는다.
- 이미 시작한 open이 뒤늦게 성공하면 자신이 연 native instance의 정리는 끝낸다. cleanup 완료 뒤 replacement open이 진행되고, 오래된 cleanup이 최신 공간을 닫지 않게 한다.
- driver-owned ticket과 lifecycle 복구 reservation을 구분한다. 정상 onAppear가 reservation을 소비한 성공 경로는 보존한다. 기존 window 부분 성공 캐시도 유지한다.
- 내부 effect bookkeeping만 추가하며 두 번째 navigation Store를 만들지 않는다. 취소 callback의 actor hop보다 먼저 큐가 실행되는 경합도 포함해 검증한다.

### D04 — 매크로의 문맥 보존을 공통화하고 Feature 이름 공간을 분리한다

- F04 대안 A는 특정 value1만 rename하는 패치, 선택 B는 parameter 집합 전체의 고유 local binding allocator다. 외부 label·위치·타입은 유지하고 실제 사용 중인 이름 및 생성 prefix와의 충돌도 피한다. CasePath/Presentation의 서로 다른 label 용도는 보존한다.
- F05 대안 A는 문자열 Self 전체 치환, 선택 B는 타입 구문에 한정된 원래 route 문맥 정규화다. CasePath와 Presentation에서 재사용하되 nested/generic route의 실제 타입 문맥을 보존한다. payload뿐 아니라 유효한 result metatype의 Self 경로도 포함한다.
- F06 대안 A는 catalog case 금지 또는 다른 중첩 예약 이름으로 rename, 선택 B는 metadata를 `Route.routerFeatureCatalog`로 이동하는 것이다. `Route.Feature`에는 case mapping만 두어 `Route.Feature.catalog`를 정상 지원한다.
- 제안된 source migration: 기존 메타데이터 접근 `Route.Feature.catalog` → `Route.routerFeatureCatalog`. `Route.Feature.account` 같은 매핑은 변경하지 않는다. 기존 위치의 metadata alias는 남기지 않는다.
- 새 이름을 `Macros.swift`의 attached extension names에 선언하고 실제 사용자 작성 멤버와의 충돌을 expansion 전에 진단한다. 잘못된 중복 선언 소스를 생성하거나 정상 overload를 과도하게 거절하지 않는다.
- metadata의 ID/namespace/child type 값·순서, 접근 수준과 feature deep-link 합성은 유지한다. 생성 API는 symbol graph만으로 충분히 검증되지 않으므로 실제 consumer 코드로 확인한다.

## 6. 검증 실행과 커밋 경계

아래 명령은 로컬 patch에서 모두 통과했다. 상세 수치는 증거 문서에 기록한다.

```sh
./scripts/principle-gates.sh --platforms=all
./scripts/sanitizer-smoke.sh thread
./scripts/sanitizer-smoke.sh address
swift test --enable-code-coverage --jobs 2 --no-parallel
./scripts/performance-smoke.sh
```

principle gate 안의 전체 테스트·DocC·API·문서 코드·외부 consumer·generated scenario·lint는 별도 통과 여부로 기록한다. coverage는 해당 실행의 fresh profile을 기존 export/검증 절차로 평가한다. 동일 검증을 이유 없이 반복하지 않되, 공개 API 변경이나 새 후보가 생기면 영향을 받는 gate를 다시 수행한다.

발행 요청 시 권장 커밋 경계는 다음과 같다. red 테스트만 있는 중간 상태는 원격 정상 후보로 올리지 않는다.

1. History 일관성·waiter + 회귀 테스트 — T01~02.
2. Scene effect 유효성·cleanup + mounted/수명 회귀 — T03.
3. Presentation 바인딩·Self 공통화 + expansion/behavior/consumer — T04~05.
4. Feature metadata namespace 변경 + 선언·진단·소비자·migration — T06.
5. 통합 gate 연결·추가 회귀·검증 기록 — T07~08. 코드/API 변경에 필수인 문서는 해당 코드 커밋에 포함한다.

## 7. 불완전 수정 반례와 완료 판단

다음은 완료로 인정하지 않는다.

- checkpoint await 뒤 guard만 추가하고 다음 commit이 여전히 잘못된 forward branch에서 출발하는 구현.
- 일반 append 또는 즉시 복원 한 곳에서만 waiter를 완료하는 구현, timeout으로 정상 완료처럼 꾸미는 테스트.
- 공용 queue Task 안의 Task.isCancelled만 검사하거나, cleanup까지 끊어 obsolete native 공간을 남기는 구현.
- value1 하나만 rename하거나 SelfNamed까지 바꾸는 문자열 치환, 매크로 선언만 컴파일하고 생성 helper는 사용하지 않는 검증.
- catalog라는 자연스러운 case를 새로 금지하면서 완료 처리하거나, metadata를 옮긴 뒤 attached names/consumer/migration을 빠뜨리는 구현.
- macOS effect trace·전체 플랫폼 compile을 실제 visionOS native 조작 증거로 보고하는 것.

6건 모두 새 반례가 green이 되고 인접 정상 동작과 품질 기준을 보존해야 구현 완료로 판단한다. 계획 승인·코드 구현·후보 검증·배포 승인은 각각 별도 상태로 유지한다.
