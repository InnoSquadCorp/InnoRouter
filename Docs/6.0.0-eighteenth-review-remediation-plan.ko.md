## 1. 목표와 비목표

목표는 여덟 항목을 닫는 데 필요한 동작 계약, 실패 테스트, 실제 호출자 검증을 함께 완성하는 것이다. 성공 기준은 단순 테스트 개수 증가가 아니라, F01~F06의 수정 전 반례와 정상 대조군이 수정 후 함께 통과하고 Q01~Q02의 검증 공백이 실제 증거로 채워지는 것이다.

- 기본 사용법은 `import InnoRouter` → `@Router` → 생성된 typed helper와 native host다.
- `RouterStore`만 navigation을 변경한다. 수락은 state 할당·revision 증가 각각 한 번, 거부는 둘 다 0번이다.
- Swift 6.3+, iOS/iPadOS 18+, Catalyst 18+, macOS 15+, tvOS 18+, watchOS 11+, visionOS 2+를 유지한다. Swift 6.4 전용 취소 API를 도입하지 않는다.
- 첫 6.0.0 전 필요한 breaking change는 허용한다. 다만 이번 반례와 관계없는 API 재설계, 5.x 호환 계층 복원, 신규 기능·Inspector 확장, iOS 17 지원, 의존성·toolchain 하한 변경은 제외한다.
- 공개 동작을 바꾸면 이유·호출자 영향·migration을 CHANGELOG와 관련 API 문서에 반영한다. symbol 변화가 없다면 API baseline을 불필요하게 갱신하지 않는다.
- 기존 미커밋 변경을 보존하며 `Derived/`, `InnoRouter.xcodeproj/`를 후보·stage 대상에서 제외한다.

## 3. 구현 전에 고정할 설계

### D01 — 복원 activation의 예약·작업·owner를 하나의 수명으로 관리

- **문제:** 예약, worker 진입, 내부 완료, 외부 반환이 서로 다른 상태 필드에 의존하여 F01~F03이 발생한다.
- **제약:** 중복 복원은 금지하고 `.alreadyActive`의 사용 가능 의미를 명확히 한다. 공유 host와 manual owner를 구분하며, 동기 storage I/O의 강제 중단을 약속하지 않는다.
- **대안 A:** 기존 분산 필드에 guard만 추가한다. 개별 반례를 줄일 수 있지만 예약 revision·observer·waiter·claim이 같은 수명인지 모든 쓰기 지점에서 다시 증명해야 한다.
- **선택 B:** private activation 상태/기록을 중심으로 예약·소유권·종료 전이를 모은다. 예약 단계의 MainActor 동기 구간에서 lifetime token, 시작 revision, observer, 복원 시도 상태를 함께 확정한다. worker는 그 기록을 받아 실행하고 상태를 새로 소유하지 않는다. 불가능한 필드 조합과 중복 정리 경로를 줄일 수 있어 선택한다. 필요한 범위만 구조화하고 저장·codec까지 통째로 재작성하지 않는다.
- **실패 시 동작:** caller 취소는 자기 대기/claim만 제거한다. 다른 유효 owner가 남으면 공유 작업을 유지한다. 마지막 owner 취소는 미완료 초기 복원을 재시도 가능하게 정리한다. 명시적 `stop()`은 예약된 활성화까지 무효화하고, 후속 activation은 초기 snapshot을 다시 덮어쓰지 않는 재관찰로 처리한다. load/decode 오류는 노출하며 재시도 가능 상태로 정리한다. 이전 세대의 오류·완료는 새 세대를 변경하지 않는다.
- **검증:** 예약 전후, load/decode/policy 대기, 내부 완료~caller 반환, 관찰·save 경계에 취소·stop·재시작·새 navigation을 배치한다. state/revision뿐 아니라 observer, owner, waiter, 저장 데이터와 실제 저장 횟수를 검증한다.

반환·소유권 계약은 다음과 같이 고정한다.

| 상황 | 반환/상태 계약 |
| --- | --- |
| 최초 활성화 예약 | 첫 suspension 전에 observer와 시작 revision이 유효하다. 초기 복원 시도는 한 번 예약한다 |
| 예약 또는 실행 중 추가 activate/attach | `.alreadyActive`는 관찰이 이미 성립했다는 뜻이다. snapshot 복원 완료를 보장하지 않는다. 해당 반환도 유효 lifetime/claim에 속해야 한다 |
| 최초 caller의 정상 복귀 | 초기 복원 결과를 반환한다. manual 유지 권한은 아직 유효한 claim을 성공적으로 소비할 때만 성립한다 |
| 내부 성공 뒤 stop/cancellation, 이후 caller 복귀 | `CancellationError`로 종료하고 manual owner·observer·status를 되살리지 않는다. 이미 완료된 Store commit을 역으로 되돌리지 않는다 |
| 한 caller 취소, 다른 host/manual owner 존재 | 취소된 caller만 종료한다. 남은 owner의 복원·관찰·저장은 유지한다 |
| 마지막 owner 취소/제거 | 작업·observer·예약 저장과 소유 restore 요청을 정리한다. 미완료 초기 복원은 다음 소유자가 재시도할 수 있다 |
| 명시적 stop→activate | 이전 예약·결과는 무효다. 최초 예약 전 stop은 복원 시도를 소비하지 않지만, 예약 후 stop은 worker 진입 여부와 관계없이 재관찰 정책을 적용한다 |

관찰 등록은 멱등이며 하나의 driver당 최대 하나다. worker 진입, 각 await 이후 상태 쓰기, 외부 effect 시작, caller 반환 모두에서 수명 유효성을 검사한다. stop은 이미 storage에 진입한 I/O를 되돌리지 않는다. 새 stale 자동 저장은 시작하지 않으며, 기존 I/O의 늦은 완료가 새 status나 소유권을 바꾸지 못하게 한다. 명시적 `save()`의 기존 독립 실행 계약도 유지한다.

### D02 — 보류 만료 권한을 등록 인스턴스에 묶기

- **문제:** F06은 sleep이 이미 성공한 Task에 대한 cancel만으로 늦은 callback을 막지 못하고, callback이 ID로 새 요청을 가져오기 때문에 발생한다.
- **제약:** 동일 deferral ID의 정상 재사용, 현재 TTL·용량·재보류·presentation 종료 의미를 유지한다. 모든 timer를 전역 취소하지 않는다.
- **대안 A:** sleep 뒤 `Task.isCancelled`만 확인한다. 현재 반례는 막을 수 있으나 어느 등록을 만료시킬 권한인지 데이터 구조로 표현하지 못한다.
- **선택 B:** timer에 등록별 고유 token을 부여하고 ID와 함께 캡처한다. 취소 검사 뒤, 현재 timer/요청 등록이 같은 token일 때만 MainActor 동기 구간에서 꺼내고 종료한다. 제거 전에 identity를 확인하여 새 요청의 timer까지 취소하는 경로를 차단한다. request-root는 재보류에서 공유될 수 있으므로 수명 ID로 대신 쓰지 않는다.
- **실패 시 동작:** 옛 callback은 no-op이다. 새 요청의 TTL과 timer는 유지하며 실제 만료는 해당 요청의 terminal·presentation 완료를 한 번만 발생시킨다. TTL 없음·0 이하의 기존 계약도 유지한다.
- **검증:** sleep 성공~callback 경계의 같은 ID/다른 ID 대조, cancel/reset/resolve/evict/re-defer, 새 timer의 고유 만료, 잔여 task·request·presentation waiter 정리를 검사한다. runtime dependency의 제어 가능한 시간으로 순서를 고정하고 실제 timer probe를 보조로 유지한다.

### D03 — 매크로 이름 충돌과 payload 문맥 보존

- **문제:** F04는 이름만 비교하고, F05는 payload syntax를 부모 문맥에서 nested helper로 그대로 옮긴다.
- **제약:** macro-first와 생성 metadata/helper의 의미·접근 수준을 유지한다. 조건부 `@FeatureRoute` 자체의 기존 E065 제한을 확대하지 않는다.
- **대안 A:** catalog 이름 전체를 예약하거나 `Self`를 금지하고 명시적 부모 타입을 강제한다. 유효한 Swift 선언을 불필요하게 배제하므로 선택하지 않는다.
- **선택 B:** declaration kind와 parameter clause로 실제 충돌을 분류한다. payload는 SyntaxRewriter로 부모 route 문맥에 맞게 정규화한다. 기존 CasePath·PresentationResult의 Self 처리와 공통화 가능한 최소 부분을 검토하고, 전체 문자열 치환은 사용하지 않는다. 조건부 선언의 활성 여부는 compiler에 맡긴다.
- **실패 시 동작:** 직접 확인 가능한 실제 충돌만 사용자 선언 위치의 전용 진단으로 거절한다. 활성 조건부 충돌은 일반 compiler 진단도 허용한다. 비활성 충돌은 생성 코드를 누락시키거나 정상 컴파일을 막지 않는다.
- **검증:** 일반 Swift 대조군, expansion, behavior, 별도 plugin consumer의 debug/release 결과를 함께 확인한다. 직접·중첩·generic Self와 명시적 부모 타입을 비교하고 embed/extract 및 catalog 값을 실제 소비한다. catalog의 child 타입 표기가 바뀌면 그 의도와 호환 영향을 기록한다.

### D04 — 검증 장치도 실패·취소 계약을 갖게 하기

- **문제:** Q01의 무한 대기는 결함을 CI 정지로 바꾸고, Q02의 완료 과장은 실제 미검증 계약을 숨긴다.
- **제약:** timeout 확대, suite 비활성화, 성공 기대값 하향으로 해결하지 않는다. 검증 목적의 공개 API나 새 외부 의존성을 추가하지 않는다.
- **대안 A:** suite 시간 제한만 추가하고 문서 체크박스만 고친다. 취소에 반응하지 않는 continuation/semaphore를 정리하지 못하므로 선택하지 않는다.
- **선택 B:** 등록/진입/반환 barrier와 cancellation-safe gate를 준비하고, deadline 시 명시적으로 대기를 해제·작업을 종료한다. 이 장치를 제품 수정 전에 검증한다. 증적은 인수 기준별 실제 assertion과 정확한 후보에 연결한다.
- **실패 시 동작:** 이벤트 미전달·worker 정지를 주입하면 지정한 deadline 안에 실패가 감지되고 cleanup이 별도 상한 안에 끝난다. cleanup 완료 전 테스트 성공을 기록하지 않는다. task-group timeout 경쟁에서 취소 불응 child를 그대로 기다리는 구현도 금지한다.
- **검증:** 장치 자체의 실패 주입 테스트와 상위 watchdog으로 유한 종료를 확인한다. MainActor를 무한 semaphore로 막지 않고, 동기 storage gate가 불가피하면 off-actor 유한 대기·명시적 해제 경로를 둔다.

### 단계별·로컬 최종 검증

1. T01~T04의 focused regression, 정상 대조, macro compile-pass/fail을 먼저 실행한다. 컴파일 실패의 원인이 기대 진단인지 확인한다.
2. `swift test --jobs 2 --no-parallel`과 `./scripts/principle-gates.sh --platforms=all`을 실행한다. 새 suite의 실제 discovery와 pass 수를 확인하며 과거 539개를 미래 테스트 개수로 고정하지 않는다.
3. `./scripts/external-consumer-smoke.sh`, `./scripts/build-docc-site.sh --version preview --skip-latest`, 문서·source lint·public API·예제 검사를 gate 포함 여부와 로그로 확인한다.
4. `./scripts/sanitizer-smoke.sh thread`, `./scripts/sanitizer-smoke.sh address`를 실행한다. 새 lifecycle/deferral suite가 필터에서 빠지지 않게 하고, sanitizer PASS를 논리적 순서 검증으로 대신하지 않는다.
5. 새 coverage를 수집하여 기존 report/threshold gate를 적용하고 `./scripts/performance-smoke.sh`로 baseline을 비교한다. coverage 제외식·성능 기준을 낮춰 통과시키지 않는다.
6. `git diff --check`와 전체 변경·문서 연결을 확인한다. exact 후보별 명령·exit·도구·로그를 증적에 남긴다.

### 별도로 충족해야 하는 배포 준비 조건

- pinned Xcode 26.6/Swift 6.3.3의 실제 compiler로 해당 후보를 확인한다. 설치가 없으면 미실행으로 남기며 현재 Swift 6.4 성공으로 대신하지 않는다.
- 정확한 후보 SHA의 원격 필수 CI, 특히 `platforms`의 tvOS/watchOS/visionOS Simulator 테스트를 확인한다. 로컬 `--platforms=all`은 compile-only이며 runtime 증거가 아니다.
- 실제 downstream revision의 macro-first 사용·migration/build/runtime 및 기존에 남은 native visionOS immersive·접근성 검증을 기존 배포 계약과 대조한다. 이번 변경이 관련 코드를 고치지 않았다는 이유만으로 과거 미완료 gate를 닫지 않는다.
- 발행 요청이 별도로 있을 때만 release notes·tag·배포 절차를 진행한다. 계획 승인이나 로컬 테스트 성공은 tag/push 권한을 대신하지 않는다.

## 7. 변경 분리와 완료 보고

구현은 사용자 실행 요청 후 위 순서로 진행한다. 커밋·푸시를 따로 요청받으면 다음 논리 단위를 기준으로 분리하되, 각 단위는 대응 회귀 테스트와 함께 통과해야 한다.

1. 테스트 대기·실패 정리 기반 및 관련 완료 판정 정정.
2. 복원 activation·ownership 수정 + 회귀·mounted 검증.
3. deferral 등록 수명·만료 수정 + 회귀.
4. macro 충돌 판정 + expansion·behavior·consumer.
5. macro payload 문맥 보존 + expansion·behavior·consumer.
6. 남은 검증 연결·공개 동작 문서·최종 증적.

같은 파일에 앞선 사용자 변경이 있으면 diff/hunk 의존성을 확인하고 정확한 경로만 stage한다. 실패 재현 테스트만 배포 브랜치에 발행하거나 `git add -A`로 사용자 산출물을 섞지 않는다. 성공한 push 뒤에는 원격 parity·worktree 보존을 먼저 확인하고, 사용자 지침의 XcodeBuildMCP cleanup을 실행하여 회수 용량·최종 여유 공간 또는 생략 사유를 보고한다. 활성 build/test를 중단하지 않는다.

동일 계약의 추가 반례나 수정 회귀는 해당 단계를 다시 열어 처리한다. 무관한 기존 결함은 우선순위·배포 차단 여부를 기록하고 의미 있는 범위 확대가 필요하면 사용자에게 방향을 요청한다. 새 기능을 이 안정화 계획에 자동 편입하지 않는다.

최종 보고에는 해결 ID, 선택한 설계와 공개 동작 영향, 정확한 후보, 실제 실행 결과, 미실행 항목, 잔여 위험을 포함한다. **수정 완료 → 로컬 검증 완료 → 배포 준비 완료 → 배포 완료**를 구분하며, 이번 범위를 검증한 결과를 모든 플랫폼·입력에서 무결함이라는 선언으로 바꾸지 않는다.
