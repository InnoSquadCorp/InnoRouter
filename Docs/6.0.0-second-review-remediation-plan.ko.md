  일치한다. 계획 작성만을 위해 빌드·테스트를 다시 실행하지 않았다.

- 작업 가정: 아직 배포하지 않은 6.0 후보에는 필요한 API/자료 형식 breaking change를
  허용한다. 잘못된 동작을 보존하는 호환 계층이나 5.x 구현은 만들지 않는다.

  이는 본 Draft 계획의 검토 대상이며 기존 문서에 승인된 설계라고 소급해서 기록하지 않는다.
- 미확인: 실제 채택 앱, 실기기/OS별 UI 검증 대상, Swift 6.3 고정 실행 환경은 유지관리자가
  지정한다. 저장소 내부 수정·독립 소비자 검증은 이 지정 없이 진행할 수 있다.

## 고정할 설계 원칙

1. 기본 사용은 `import InnoRouter` + `@Router` + 기존 host다. 고급 기능 미사용 앱에
   새 필수 설정·제품·수동 라우팅 코드를 요구하지 않는다.
2. 가변 이동 상태는 한 `RouterStore`가 소유한다. feature·복원·history·Inspector 실행·
   replay 모두 실제 정책/큐/reducer/commit 경로를 사용한다.
3. 실패·취소 요청의 추가 상태 변경과 revision 증가는 0이다. 동시에 성공한 다른 요청의
   최신 상태는 보존한다. 모달 결과는 정확히 한 번 완료한다.
4. 기본 미리보기는 사용자 resolver·parameter converter·validator·auth·policy·앱 효과를
   실행하지 않는다. 판단할 수 없는 항목은 미평가로 표시한다.
5. 모든 대기·기록에는 소유권, 상한, 취소·종료 결과가 있다. 취소를 성공으로 위장하거나
   대기자 컬렉션만 비워 실제 작업을 남기지 않는다.
6. 공개 제품은 `InnoRouter`, `InnoRouterTesting`, `InnoRouterInspector` 세 개를 유지한다.
   Swift 6.3+, iOS/iPadOS·Mac Catalyst 18+, macOS 15+, tvOS 18+, watchOS 11+,
   visionOS 2+를 유지한다. Swift 6.4 전용 기능을 6.3 지원 코드에 무조건 도입하지 않는다.
7. 기본 진단은 민감 값을 숨긴다. 원본 녹화/내보내기는 별도 명시적 선택이며 자동 전송은 없다.
8. API·심볼 예산·자료 버전은 변경 이유를 검토한 뒤 갱신한다. lint·coverage·성능 예산을
   수정 통과만을 위해 완화하지 않는다.

범위 밖: iOS 17 하향, 새 라우팅 엔진, 임의 앱 효과의 자동 재현, 과거 모달 세션·창의
재생성, 인증/업무 데이터의 되돌리기, 새로운 원격 서비스와 배포.

## R6R2-T00 — 기준선과 실패 증거 보존

- [x] 실행 시작 시 HEAD, 변경 파일 범위, Swift/Xcode, package 제품을 다시 기록한다.
  기존 미커밋/미추적 작업, `Derived/`, Xcode 프로젝트를 보존한다.
- [x] 임시 진단 13개와 로그를 재검토 증거로 보존하고 A01~12 각각을 저장소 회귀에

- [x] A08의 30ms 진단 watchdog은 정규 테스트의 준비 완료 추측으로 사용하지 않는다.

- [x] 기존 1개 통과 제어 사례도 유지한다. skip, assertion 삭제, 영구 known-issue로
  필수 실패를 숨기지 않는다. 정상 경합 10개×100회와 현재 성능 예산의 기준을 보존한다.

완료 조건: A01~12의 입력 순서·잘못된 결과·예상 정상 결과·검증 파일이 모두 연결되어
있다. 임시 파일이 사라져도 보고서의 반례와 저장된 fixture로 다시 만들 수 있다.

## R6R2-T01 — P1 먼저: 타입 모달과 순수 미리보기

### 1-A. feature 타입 모달

- [x] `RouterFeatureScope.present`와 생성된 타입 요청 overload를 일반 feature 요청과
  같은 실행/commit 전제조건 경로에 연결한다. 제출 시점의 projection만 신뢰하지 않는다.
- [x] 기존 부모 요청의 ID·큐·정책·결과 waiter를 유지한다. 전체 queue를 제출 revision에
  묶어 정상 FIFO까지 거절하거나 상태 변경 후 결과만 거절로 바꾸지 않는다.
- [x] 부모 교체/삭제, 중첩 feature, 같은 feature 두 인스턴스, 창 내부 scope,
  policy await 중 취소, 타입 결과 성공/취소를 검증한다.

변경 접점: `RouterFeatureScope`, `RouterScope`, `RouterStore+Presentation`과 내부 요청
전제조건. 완료 조건: 사라진 feature 요청의 추가 commit/revision 0, sibling 보존,
정상 타입 결과 1회 완료, 기본 macro consumer 유지.

### 1-B. 순수 preview

- [x] 구조적 URL 분석과 앱 변환/실행을 분리한다. `inspectorCatalog: true`를 임의 앱
  코드가 순수하다는 보증으로 사용하지 않는다. 사용자 타입은 기본 미평가로 표시한다.
- [x] framework가 소유한 안전한 변환으로 설명 가능한 항목만 기본 목표 상태를 만든다.
  타입 이름 문자열만 보고 사용자 타입/별칭까지 안전하다고 간주하지 않는다.
- [x] analyze→preview에서 같은 입력의 resolver를 중복 호출하지 않는다. 사용자 action
  closure도 기본 순수 분석에 자동으로 호출하지 않도록 실행 경계를 검토한다.
- [x] 기본 진단의 converter/resolver/validator/auth/policy spy와 store 변경은 모두 0이다.
  built-in 변환 설명, malformed URL, custom parameter, 여러 번의 화면 재평가를 검증한다.
- [x] 사용자 코드 평가가 꼭 필요하면 기본 preview와 다른 명시적 동작/보증 계약으로
  분리한다. opt-in이 있어도 임의 Swift 코드의 순수성을 컴파일러가 증명한다고 주장하지 않는다.

변경 접점: `RouterDeepLinkRendering`, `DeepLinkRouteCatalog`, Inspector analyzer.
완료 조건: A02 통과, 안전한 기본 설명 기능 유지, 별도 명시적 실행은 정상 정책을 통과.
macro expansion·behavior·외부 소비자 세 층을 함께 검증한다.

## R6R2-T02 — 대기 취소, async 종료, 공유 시간, stop 경계

- [x] recorder/history의 개수·revision·observed waiter에 ID 기반 취소 처리를 적용한다.
  등록 전 취소, 등록 경쟁, 등록 후 취소, stop과 동시 취소에서 정확히 한 번 종료한다.
- [x] TestStore의 finish를 소유 작업의 취소·배출 완료까지 기다릴 수 있는 API로 만든다.
  필요하면 `async` breaking change를 사용하고 모든 소비자/생성 테스트도 갱신한다.
  pending 진단은 지우지 않으며 요청·보류·타이머·waiter를 소유자 단위로 정리한다.
- [x] 앱의 비협조적 Task를 강제 종료할 수 있다고 약속하지 않는다. framework가 소유한
  취소 완료와 외부 작업의 미종료를 구분하고, 남은 작업을 버린 뒤 pending=0으로 보고하지 않는다.
- [x] clock 등록 장벽도 owner ID로 필터링한다. 다른 owner 타이머는 준비 조건과 cleanup
  대상에서 제외한다. 같은 기한 순서와 장벽 취소 결과를 검증한다.
- [x] recorder stop의 관찰 경계와 반환 자료를 고정한다. 반복 stop은 동일 자료를 반환한다.
  stop 후 control 호출은 명시적으로 거절하고 clock/store를 새로 조작하지 않는 안을 기본으로 한다.
  stop 전에 시작한 production 요청은 녹화 종료만으로 취소하지 않고 불완전 이유를 남긴다.
- [x] 구조화된 종료 결과 뒤 waiter/소유 Task/deferral/timer 수와 weak 참조 해제를 확인한다.
  단순 `Task.cancel()` 호출 여부나 컬렉션 count만으로 종료 완료를 판정하지 않는다.

변경 접점: `RouterTestStore`, `RouterTestRequest`, `RouterTestClock`,
`RouterScenarioCapture`, `RouterHistory`, 필요한 production deferral 취소 접점.
완료 조건: A08~11 통과, 공유 runtime의 상대 store 유지, 반복 finish/stop 안전,
자기 종료를 기다리는 deadlock 0. 수명 회귀가 sanitizer 필터에도 실제 포함된다.

## R6R2-T03 — 부분 복원의 대체 체인 검증

- [x] 원래 route뿐 아니라 fallback과 replacement도 같은 공통 planner에서 검증한다.
  path·presentation·필수 선택/열 등 모든 대체 분기에 같은 규칙을 적용한다.
- [x] 연속 대체에는 명시적 최대 횟수와 cycle 진단을 둔다. 같은 값 반복이나 긴 체인은
  정해진 상한에서 실패하며 임의 화면으로 조용히 초기화하지 않는다.
- [x] validator 호출 전/await 후 취소를 확인하고, 취소 뒤 후속 validator는 호출하지 않는다.
  최종 topology/domain 유효성, 기준 revision과 정책을 확인한 후 기존 commit을 한 번 수행한다.
- [x] keep/remove/replace/fallback/cycle 보고를 실제 최종 계획과 대조한다. 보고서의 이유와
  위치는 구조 정보이며 원본 route payload를 담지 않는다.

변경 접점: `RouterPartialRestoration`, snapshot/자동 복원 연결, 공통 planner 테스트.
완료 조건: A07 통과; keep, replace→keep, replace→remove, cycle, limit, 취소/timeout/
동시 commit/정책 거절 행렬 통과. 실패 요청의 추가 상태/revision 0, 유효 sibling/scene 보존.

## R6R2-T04 — history 보류 사슬과 checkpoint 정합성

- [x] 최종 commit/unchanged에서만 cursor를 정확히 한 번 이동한다. 재거절·취소·만료·

- [x] 체크포인트 대상이 기존 entries 안에 있는 경우에도 최종 outcome의 실제 navigation

- [x] T03의 공통 planner를 재사용한다. 배열 index나 await 뒤의 전역 최신 store를 대상

- [x] 2회 이상 보류, 승인과 reset/정상 이동 경쟁, 용량 축출, 분기 제거, checkpoint 복원

## R6R2-T05 — 자료 형식, 의존성 preflight, 결정적 replay와 생성

### 5-A. 자료 계약과 사전 검사

- [x] fixture에 route schema/환경 식별, 필요한 앱 의존성의 ID·버전/능력,
  clock/ID 전략, 외부 효과와 스케줄링의 재현 가능 범위를 담는 명시적 metadata를 정의한다.
  비밀 값이나 실행 closure를 직렬화하지 않는다.
- [x] 앱 공급자는 factory 이름 문자열만이 아니라 제공 가능한 의존성과 재현 조건을
  선언한다. 누락·불일치·지원하지 않는 효과·기대값 누락은 첫 요청/앱 효과 전에 진단한다.
  앱이 잘못 선언한 외부 서비스까지 자동으로 검증하거나 복제한다고 약속하지 않는다.
- [x] 형식 변경은 명시적으로 버전 구분한다. 기존 v1/v2에 없는 정보를 추측해서 complete로
  올리지 않는다. 미배포 자료의 호환을 위해 이중 실행 엔진을 만들지 않으며, 읽기 미지원이나
  재현 불완전 반환 중 선택한 정책을 API 검토 기록과 오류 fixture에 남긴다.

### 5-B. ID·종료 결과·제어 사건

- [x] 녹화의 논리 request/deferral/presentation identity와 새 실행의 실제 ID를 연결한다.
  새 보류는 outcome metadata에서 얻고, 재보류 사슬도 매핑한다. 직접 재현할 수 없는
  presentation 세션/앱 결과는 지원 범위 밖으로 사전 표시하며 UUID 재사용으로 속이지 않는다.
- [x] 각 요청은 자신의 종료 outcome state/revision/terminal로 검증한다. revision은
  녹화 시작과 replay 시작의 상대 기준을 사용하며 현재 전역 store 값으로 대체하지 않는다.
- [x] eventIndex/논리 요청 관계를 검증하고 submit/wait/cancel/time/resolve/await를 재생한다.
  3개 이상 겹친 요청에서 임의 Dictionary 순서의 queued 요청을 기다리느라 뒤의 승인/시간
  제어가 실행되지 않는 경우도 검사한다. 이는 새로 추가할 경계 검사이며 기존 재현 수에 포함하지 않는다.
- [x] 거절은 필요한 경우 사유 코드까지 기대값으로 표현한다. 서로 다른 거절이 모두
  `.rejected`라는 이유만으로 같은 올바른 결과로 처리되지 않게 음성 검증을 둔다.

### 5-C. 실행 가능한 회귀 산출물

- [x] 생성기는 Swift Testing 소스와 별도 fixture 자료를 제공한다. 파일명/Swift 식별자,
  크기·버전·불완전 상태를 검사하고 관찰값을 자동 정답으로 복사하지 않는다.
- [x] 임시 외부 패키지/새 프로세스에서 생성 결과를 실제 컴파일·실행한다. 새 UUID,
  시작 revision>0, 여러 보류, 역순 결과 회수, 취소/시간 진행을 포함한다.
- [x] 올바른 기대값은 통과하고 잘못된 상태/revision/종료 사유는 각각 실패해야 한다.
  의존성 누락/호환성 위반은 생성된 테스트에서도 첫 이동 전에 실패해야 한다.
- [x] 실제 실행 테스트 수·exit code·실패 assertion을 기록한다. 생성 문자열 검색이나
  컴파일 오류만으로 런타임 음성 검증을 대체하지 않는다. T02 종료 API를 생성 코드에도 반영한다.

변경 접점: `RouterScenarioCapture`, fixture codec, `RouterScenarioReplay`,
`RouterScenarioSourceGeneration`, `ConsumerSmoke`, `scripts/generated-scenario-smoke.sh`.
완료 조건: A05/A06/G01 통과, 불완전 자료의 재현 성공 주장 0, 음성 preflight의 production 요청 0.

- [x] 실행 상태를 현지화 가능한 구조화된 값으로 바꾸고 성공/거절/보류/취소/미해결을

- [x] 녹화 시작 → 진행/용량 표시 → stop → 완전/불완전 사유 → 명시적 원본 export/import →

- [x] 단계별로 이유를 기록한 public API 변경만 baseline/예산에 반영한다. README 양언어,

- [x] 기존 완료 기록을 삭제하지 않고 이번 반례 및 수정 결과를 후속 이력으로 연결한다.
  명세의 계획/미구현 설명과 구현 상태표를 구분해 최신 증거를 연결한다. 문서 승인 상태는
  유지관리자의 실제 승인 없이 올리지 않는다.
- [x] 최종 코드 재리뷰에서 요구사항 32개와 AC 18개를 다시 대조한다. `implemented`,
  `partial`, `contradicts`, `unverified`와 테스트의 `covered`, `weak`, `absent`, `blocked`를
  분리한다. 새 반례가 있으면 해당 단계를 다시 연다.

### 실행할 gate

아래는 현재 저장소의 실제 명령이다. 구현 과정에서 추가할 세 통합/새 성능 검증도
이 gate 또는 명시적 CI 단계에서 실행되도록 연결한다. 자원을 공유하는 플랫폼 빌드와
sanitizer는 충돌하지 않는 출력 경로로 직렬 실행한다.

```bash
swift test --jobs 2
swift test --package-path ConsumerSmoke --jobs 2
./scripts/generated-scenario-smoke.sh
./scripts/principle-gates.sh --platforms=all
./scripts/external-consumer-smoke.sh
./scripts/sanitizer-smoke.sh thread
./scripts/sanitizer-smoke.sh address
./scripts/performance-smoke.sh
swift test --enable-code-coverage --jobs 2
router_review_artifacts="$(mktemp -d /tmp/innorouter-review-r2-XXXXXX)"
./scripts/generate-coverage-report.sh "$router_review_artifacts/coverage.lcov" "$router_review_artifacts/coverage-full.lcov"
./scripts/test-validate-coverage-report.sh
./scripts/test-summarize-coverage-report.sh
./scripts/validate-coverage-report.py "$router_review_artifacts/coverage.lcov" --minimum-line-coverage 85
./scripts/validate-coverage-report.py "$router_review_artifacts/coverage-full.lcov" --minimum-line-coverage 0
./scripts/summarize-coverage-report.py --gated "$router_review_artifacts/coverage.lcov" --comprehensive "$router_review_artifacts/coverage-full.lcov" --output "$router_review_artifacts/coverage-summary.json"
git diff --check
```

실제 종료 코드, 테스트 수, 실패 assertion, 도구 모음/SDK, 실행 날짜, 증거 파일을 기록한다.
생성 테스트 음성 사례의 의도한 exit 1은 일반 suite 실패와 구분한다.
coverage는 계측 테스트 직후의 profile로 내보낸다. 포괄 보고서의 minimum 0은 자료
검증/공개용이며 portable 85% gate를 대체하거나 낮추는 값이 아니다.

- [x] feature가 사라진 뒤 상태는 바꾸고 반환값만 거절로 바꾸지는 않았는가?
- [x] custom 타입/별칭에 이름만 보고 순수성을 부여하거나 분석 단계에서 앱 closure를 호출하지 않는가?
- [x] 한 번 보류와 고정 UUID만 통과하며 재보류/새 프로세스는 여전히 실패하지 않는가?
- [x] cursor만 수정하거나 stop 때 자료를 덮어써 실제 상태 불일치·유실을 숨기지 않는가?
- [x] finish가 pending 진단을 지우거나 참조를 버릴 뿐 실제 종료는 기다리지 않는가?
- [x] factory 함수명이 있다는 이유로 환경/의존성이 일치한다고 간주하지 않는가?
- [x] 부모 catalog 목록만 늘리고 실제 matcher/feature 인스턴스 충돌은 남겨두지 않았는가?
- [x] 공유 버튼이 명시적이라는 이유로 기본 원문 민감 값 노출을 허용하지 않는가?
- [x] 생성 소스 검색/컴파일, 구성요소 단독 테스트, 기존 성능 결과를 전체 인수 증거로 대체하지 않는가?

## 완료 판정과 별도 승인 경계

| 판정 | 필수 조건 |
| --- | --- |
| 개별 수정 완료 | 기준 반례가 정규 assertion으로 통과 + 정상/실패 인접 분기 + API/문서 검토 + 코드 재리뷰 |
| 로컬 구현 검증 완료 | A01~12 및 G01~03 해결, 세 실제 통합 흐름, 새 성능 예산, 모든 로컬 필수 gate 통과. 남은 UI/환경 항목은 명시 |
| 전체 인수 완료 | 요구사항 증거표의 필수 항목 충족. 지원 플랫폼의 필요한 runtime/UI·접근성 증거까지 확보 |
| 6.0.0 배포 가능 | 위 조건 + Swift 6.3 고정/지원 toolchain CI + 실제 채택 앱 + 정확한 release revision 소비자 + 유지관리자 승인 |

앱·기기 선택은 유지관리자, API/자료 설계 제안과 측정/증거 수집은 구현 담당자의 책임이다.
문제 행동을 정상으로 재정의하거나 UI를 문서화만으로 축소해야 하는 결정은 작업을 멈추고
유지관리자에게 돌려보낸다. 플랫폼 도구 미확보는 관련 검증만 보류하고 독립적인 내부 수정을
막지 않는다. 커밋·푸시·태그·배포는 이 계획 승인만으로 실행하지 않는다.

이 계획을 마쳐도 “더 이상 버그가 없다”는 절대 보장은 하지 않는다. 확인된 계약을 실제
실패 행렬과 실행 증거로 충족시키고, 높은 우선순위 미해결 결함과 숨겨진 미검증 항목 없이
6.0.0 후보를 평가할 수 있는 상태를 목표로 한다.
