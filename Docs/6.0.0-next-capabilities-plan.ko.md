# InnoRouter 6.0 순차 개발 계획 — 추가 기능 1~6

## 계획 상태와 실행 원칙

- 상태: 구현 후보 완료·배포 검증 대기, 버전 0.2, 갱신일 2026-09-05
- 결정 책임자: 프로젝트 유지관리자(사용자)
- 검토자·승인자·승인일: 미기록
- 요구사항: [추가 기능 명세 FR6-036~053](6.0.0-next-capabilities-spec.ko.md)
- 기존 구현 이력: [기존 12단계 계획](functional-expansion-technical-plan.md)
- 실제 구현 상태: 아래 여섯 단계의 공개 기능·회귀 테스트·문서·외부 소비자
  시제품 구현 완료. 고정 Swift 6.3 도구 체인과 실제 플랫폼 UI 검증, 원격 CI,
  태그 기반 소비자 검증은 배포 단계에서 수행

사용자가 요청한 **1 → 2 → 3 → 4 → 5 → 6** 순서로 진행한다. 6번도 이번
개발 범위에 포함하며 앱이 사용할지는 선택 사항이다. 앞 단계는 구현·테스트·문서·
API 검토·재리뷰가 끝난 뒤 완료 처리하고 다음 단계로 이동한다.

기본 사용법, 단일 `RouterStore`, `RouterAction`과 `RouterPlan`의 역할, 세 공개
제품, 기존 플랫폼 하한을 유지한다. 미배포 6.0 후보이므로 필요한 breaking
change는 허용하되 변경 이유·교체 예시·자료 형식 영향을 단계별로 기록한다.

구현 결과 공개 API는 `InnoRouter` 1,116개, `InnoRouterInspector` 163개,
`InnoRouterTesting` 119개 심볼로 추출했고 같은 수를 상한으로 잠갔다. 현재 로컬
검증은 Xcode 27.0 / Swift 6.4에서 수행했으므로, 계획에서 요구한 Xcode 26.6 /
Swift 6.3 결과를 대신하지 않는다.

## T6-01 — 기능 모듈별 경로 합성

### 목표와 설계

두 기능 모듈이 각자의 `@Router`만으로 개발되고, 앱 조립 지점에서 부모 경로에
연결되도록 한다. 기능이 부모 앱이나 다른 기능을 import하지 않아야 한다.

- 부모의 associated-value 경로와 자식 경로를 기존 `CasePath` 기반 삽입·추출로
  연결하는 생성 계약을 검토한다. 매크로가 다른 모듈의 소스 문법을 읽을 수 있다고
  가정하지 않고, 자식 모듈이 내보낸 타입 계약과 카탈로그를 사용한다.
- 상태 읽기와 액션 전달을 분리해 자식 façade를 만든다. 자식이 보유하는 것은
  읽기 전용 값 투영이며 별도의 `RouterStore<Child>`를 생성하지 않는다.
- 매핑 대상은 명시적인 기능 하위 영역이다. 자식 계획은 그 영역만 교체하고
  부모·형제의 경로, 모달, 장면 상태를 보존한다. 매핑 불가능한 경로를 조용히
  걸러내어 잘못된 자식 상태를 만드는 동작은 금지한다.
- 기능 인스턴스 ID와 선언 이름공간을 구분한다. 같은 기능 두 인스턴스의 탭·장면·
  모달 상관관계가 충돌하지 않아야 한다. 창 생성·종료는 앱 권한으로 남긴다.
- 타입 모달 요청과 완료는 부모의 기존 waiter에 연결한다. 자식마다 결과 대기자를
  복제하지 않고 원래 전환·presentation ID와 정확히 한 번 완료를 유지한다.

### 작업 체크리스트

- [ ] 외부 `AccountFeature`, `SearchFeature`, 앱 조립 모듈로 최소 소비자 작성
- [ ] 같은 기능 두 인스턴스와 두 단계 중첩의 API 시안 컴파일
- [ ] 자식 상태 투영·액션 변환·부분 계획 적용 계약 구현
- [ ] 매크로 생성·접근 제어·이름 충돌 진단과 생성 코드 확장 테스트 구현
- [ ] 기존 stack/tab/split/scene host와 환경 읽기·쓰기 연결
- [ ] 부모 소멸·범위 소멸·잘못된 매핑·모달 결과·형제 보존 테스트
- [ ] 외부 모듈의 컴파일 실패 fixture로 잘못된 조합이 거절되는지 확인
- [ ] 기본 소비자 무변경 빌드, API 차이·문서·성능 영향 검토와 재리뷰

주요 변경 지점: `InnoRouterCore/CasePath`, `RouterAction`·`RouterPlan`,
`InnoRouterSwiftUI/RouterScope`·환경·host 연결, `InnoRouterMacrosPlugin`,
`ConsumerSmoke`의 새 독립 기능 모듈. 내부 어댑터 파일은 책임별로 분리한다.

완료 기준: AC6-031~033, SC6-001/004. 자식 이동이 부모 정책을 우회하거나
형제 상태를 변경하면 완료하지 않는다. 스냅샷에서 새 합성 타입의 Codable 형태와
기존 미배포 fixture 영향도 이 단계에서 기록한다.

## T6-02 — 가상 시간과 동시성 시나리오 테스트

### 목표와 설계

외부 개발자가 취소·시간 초과·만료·요청 겹침을 동일한 production 실행 경로에서
제어한다. 가상 시계는 `InnoRouterTesting`에 제공하고 runtime의 의존성 연결은
기존 package 경계를 활용한다. 일반 앱 설정에 테스트 전용 필수 인자를 추가하지 않는다.

- 가칭 `RouterTestClock`으로 현재 시간·대기 등록·시간 진행·취소를 제어한다.
  벽시계 날짜와 경과 시간의 관계, 같은 시각의 기한 처리 규칙을 명시한다.
- `RouterTestStore`에 요청 시작 핸들, 정확한 생명주기 도달 장벽, 결과 대기,
  취소, 지연 승인 제어를 추가한다. `send`의 기존 간단한 사용법은 유지한다.
- 전환 ID 공급과 fixture의 논리 요청 ID를 분리한다. 녹화 UUID가 테스트 실행을
  임의로 바꾸거나 충돌하지 않도록 한다.
- 시계만 바꾸면 임의 actor/네트워크 스케줄링까지 결정적이 된다고 주장하지 않는다.
  라우터가 소유한 대기와 테스트가 명시적으로 제어한 앱 의존성만 재현 범위로 둔다.
- 엄격한 종료 검사에는 미완료 요청·승인·타이머가 포함된다. 테스트 소유 작업의
  취소·continuation 정리와 객체 해제를 검증한다.

### 작업 체크리스트

- [ ] 공개 테스트 시계와 package 의존성 연결 구현
- [ ] 요청 핸들·장벽·취소·승인·결과 확인 API 구현
- [ ] 기본 실제 시간 모드와 기존 `RouterTestStore` 호환성 검증
- [ ] 10개 시나리오: FIFO, busy, keep-first, replace-pending, 두 overflow 전략,
  정책 시간 초과, 지연 만료, 취소 우선, 승인과 상태 변경 경쟁
- [ ] 각 시나리오 100회 반복과 독립 외부 테스트 소비자 검증
- [ ] 미종료 진단·소유자 해제·동일 시각 기한 경계 TSan/ASan 검증
- [ ] API·문서 검토와 재리뷰

주요 변경 지점: `RouterRuntimeDependencies`, `RouterStoreConfiguration`의 package
접점, `InnoRouterTesting`, 기존 수동 시간 테스트 및 `ConsumerSmoke`.

완료 기준: AC6-034~036, SC6-002. 벽시계 대기나 반복 `Task.yield()` 횟수에
의존하는 외부 시나리오는 완료 증거로 사용하지 않는다.

## T6-03 — 부분 복원과 복원 보고서

### 목표와 설계

마이그레이션된 상태의 유효한 영역을 보존하는 복원 계획을 만든다. 첫 범위는
정상적으로 디코딩된 경로에 대한 앱의 도메인 유효성 검사다. 손상된 JSON이나
알 수 없는 route 표현을 자동으로 건너뛰는 별도 디코더는 만들지 않는다.

- 유효성 검사는 불변 경로·범위 정보를 받아 유지·제외·대체를 반환한다. 실제
  데이터 조회와 인증 구현은 앱이 공급하며 검사 취소·시간 제한 계약을 둔다.
- 트리 순회와 대체 결과 적용으로 가칭 `RouterRestorationPlan`과 구조 보고서를
  준비한다. 실제 적용은 기존 `RouterPlan`으로 수렴하며 별도 실행 엔진은 없다.
- 스택 중간 경로를 제외하면 그 경로에 의존한 뒤쪽 경로도 제거한다. 다른 탭과
  독립 창은 유지한다. 빈 선택·분할 필수 열·잘못된 대체 경로는 지정된 규칙으로
  처리하거나 실패한다.
- 검사 시작의 revision을 보관하고, 검사 완료 뒤 정상 정책을 거쳐 한 번 커밋한다.
  오래된 검사 결과는 새 사용자 이동을 덮어쓰지 않는다.
- 복원된 모달 상태는 과거 비동기 결과 대기자를 생성하지 않는다. 영향받는 현재
  모달 세션 처리도 기존 presentation 수명 계약을 따른다.
- 보고서는 변경 위치·동작·이유 코드를 제공하고 원본 경로 payload는 숨긴다.

### 작업 체크리스트

- [ ] 유지·제외·대체 결정, 구조 보고서, 명시적 대체 규칙 정의
- [ ] 트리별 부분 복원 계획과 검증 구현
- [ ] 수동 `restore`와 자동 복원 드라이버에 opt-in 경로 연결
- [ ] 2단계 시계로 취소·제한시간·revision 경쟁·정책 거절 검증
- [ ] 삭제된 상세, 빈 탭, 분할 열, 다중 창, 잘못된 대체, 전부 무효 fixture
- [ ] 자료 버전·실패 이유·정상 복원 무변경 회귀 검증
- [ ] API·문서 검토와 재리뷰

주요 변경 지점: `InnoRouterCore/RouterSnapshot` 및 별도 복원 계획 파일,
`RouterStore+Snapshot`, `RouterStateRestoration`, `InnoRouterTesting`의 복원 assertions.

완료 기준: AC6-037~039, SC6-003. 어느 경로가 왜 사라졌는지 설명할 수 없거나
검사 실패가 부분 커밋을 남기면 완료하지 않는다.

## T6-04 — 생성 경로 목록과 딥링크 진단 화면

### 목표와 설계

매크로 선언과 실제 파이프라인이 사용하는 경로 정보를 Inspector에서 확인한다.
검사기는 동일한 파서·우선순위·입력 제한을 사용해 matcher와 결과가 달라지지 않게 한다.

- 매크로가 경로 이름공간·종류·패턴·매개변수 형식을 내보내는 카탈로그를 생성한다.
  1단계 자식 카탈로그는 공개 메타데이터 계약을 통해 결합한다.
- admission에 읽기 전용 설명 결과를 추가한다. 출처 거절, 매칭 후보, 선택 이유,
  변환 실패, 준비 가능한 계획과 현재 상태 차이를 보여준다.
- 기본 미리보기는 매크로 생성 규칙만 안전하게 평가한다. 순수함을 보장할 수 없는
  사용자 resolver·인증·정책 closure는 실행하지 않고 미평가로 표시한다. 실제 실행은
  별도 버튼을 통해 기존 파이프라인에 보내고 그 결과를 보여준다.
- 새 진단 화면의 입력 URL과 payload 노출은 개발자의 명시적 선택으로 관리한다.
  기존 support bundle에 진단을 넣을 경우 버전 변경 필요성을 검토하고 유실 없이
  읽는 계약을 정의한다.

### 작업 체크리스트

- [ ] 카탈로그 생성·자식 조합·동적/사용자 resolver 한계 정의
- [ ] 공통 파서 기반 설명 결과와 구조화된 실패 단계 구현

## T6-05 — 명시적 녹화에서 회귀 테스트까지

### 목표와 설계

현재 `RouterActionSequence`를 기반으로 요청 제출·시간·취소·승인·결과를 표현하는
가칭 `RouterScenario` 자료와 생성 도구를 만든다. 녹화와 기대 동작의 정의를 구분한다.

- capture는 `.started` 이벤트만 관찰해서 구현하지 않는다. 현재 실행 전 거절
  이벤트에는 원래 액션이 없으므로, 제출 시점과 종료를 연결하는 opt-in package
  hook 또는 필요한 최소 공개 관측 계약을 먼저 설계한다.
- 기본 지원 자료는 지금처럼 payload를 숨긴다. 원본 타입 녹화는 별도의 시작·종료·
  용량 계약을 갖고, 메모리/파일 보관과 내보내기 전 노출 범위를 표시한다.
- 초기 상태, 논리 요청 ID, 액션·맥락, 제어 사건, 관찰 결과, 자료 버전, 누락과
  필요 의존성을 저장한다. Codable 자료를 데이터로 읽고 임의 코드를 실행하지 않는다.
- 2단계 제어점으로 재현 가능한 순서를 명시한다. 임의 production 스케줄러 전체를
  녹화했다는 보장은 하지 않고 미포착 외부 효과는 필요한 앱 의존성으로 표시한다.
- 생성기는 Swift Testing 테스트 골격과 자료 파일을 만든다. 경로 생성 코드를
  문자열로 추측하지 않고 Codable 자료와 앱이 제공한 테스트 조립 함수를 사용한다.
- 관찰 결과는 참고 자료다. 개발자가 원하는 기대 결과를 명시해야 회귀 assertion을
  확정한다. 기대값이나 의존성이 빠지면 미완료 진단을 제공한다.

### 작업 체크리스트

- [ ] 제출·거절·병합·취소·승인 관측 계약과 누락 감지 설계
- [ ] 상한 있는 녹화 수명 및 자료 schema 구현
- [ ] `RouterActionSequence`와의 관계·전환 및 재현 가능 범위 정의
- [ ] 시나리오 실행·의존성 공급·기대값 정의·테스트 생성 구현
- [ ] Inspector 녹화 상태·범위·불완전 표시·내보내기/가져오기 연결
- [ ] 녹화→자료→새 테스트 프로세스에서 재생하는 외부 소비자 검증
- [ ] 잘못된 기대값 실패, 누락 자료 실패, 민감 fixture 미노출, fuzz·수명 검증
- [ ] API·자료 형식·문서 검토와 재리뷰

주요 변경 지점: `RouterStore`의 제출·생명주기 관측, `InnoRouterTesting` 시나리오·
녹화·생성, `InnoRouterInspector` 제어 화면, 독립 생성 테스트 소비자.
필수 새 공개 제품이나 분석 서비스 의존성은 추가하지 않는다.

완료 기준: AC6-043~045. 큐에서 사라진 요청을 숨기거나, 녹화한 버그를 그대로
기대값으로 삼아 통과한 테스트는 회귀 테스트 생성 완료로 인정하지 않는다.

## T6-06 — 이동 기록과 체크포인트

### 목표와 설계

한 저장소에 선택적으로 연결하는 가칭 `RouterHistory` 어댑터를 제공한다. 이력이
보유하는 것은 과거 이동의 값과 cursor이며, 렌더링되는 현재 상태는 원래 저장소만 소유한다.

- 기본 기록 범위는 stack 경로, tab/split 선택, 이미 존재하는 창·몰입 공간 내부
  경로다. 배지·모달 세션·장면 생성/종료·앱 업무 상태는 과거 값으로 덮어쓰지 않는다.
- 체크포인트는 ID·이름·기록 범위·세션 경계·호환 버전을 가진다. 개수 상한,
  같은 이름의 처리, 동일 경로 병합, 명시적 삭제·전체 초기화를 제공한다.
- 이름 중복은 기본 거절하고, 덮어쓰기는 명시적인 선택으로 한다. 이전 기록으로
  이동한 뒤 새 전환이 성공하면 앞으로 기록을 제거한다.
- 대상 적용은 3단계의 검증·부분 복원 규칙과 현재 상태 병합을 재사용한다. 과거 창이
  사라졌으면 자동으로 다시 열지 않는다. 해당 영역의 열린 모달과 충돌하면 거절한다.
- 이력 이동 자체가 새 이력으로 재기록되는 루프를 방지한다. cursor는 적용 성공 또는
  목표 상태 동일 확인 후에만 이동하고 실패 시 원래 위치를 유지한다.
- 계정·문서 세션 변경은 앱이 제공하는 경계 키 또는 명시적 reset으로 구분한다.
  자동으로 인증 상태를 추론하지 않는다.
- 공개 기록 API는 메모리 기반으로 시작한다. 명시적 checkpoint 직렬화가 필요한
  소비자를 위해 Codable 자료 경계를 제공하되 저장 위치와 자동 저장은 앱이 선택한다.

### 작업 체크리스트

- [ ] 기록 범위·checkpoint 값·상한·세션 경계·중복 규칙 정의
- [ ] 정상 커밋 기록, 뒤로·앞으로·checkpoint 이동과 cursor 처리 구현
- [ ] 복원 계획·정책·revision·모달/장면 수명 연결
- [ ] 기본 버튼 상태와 선택적 macOS 키보드/명령 연결 예제 제공
- [ ] 거절·취소·오래된 대상·분기·동일 상태·영역/세션 소멸 검증
- [ ] 5단계 자료를 이용한 복합 이동 시나리오와 보관/해제 검증
- [ ] 자료 형식·API·문서·플랫폼 검증과 재리뷰

주요 변경 지점: runtime 내부 별도 이력 어댑터, 복원 계획 공통 계층,
`RouterStore` 관측·정책 접점, 테스트 도구, 예제. 기본 `@Router` 설정은 그대로 둔다.

완료 기준: AC6-046~048. 취소되었는데 cursor가 이동하거나 과거 모달·배지·업무
상태가 되살아나면 완료하지 않는다.

## 공통 완료 게이트와 최종 통합

각 단계 완료 시 다음 자료를 남긴다.

1. 해당 FR/AC를 실제 코드·테스트·외부 소비자 증거에 연결한다.
2. 변경된 공개 API를 검토하고, 의도된 차이만 기준선과 심볼 예산에 반영한다.
3. 매크로 변경은 expansion과 runtime behavior 양쪽을 검증한다.
4. 관련 테스트·소유권/취소·잘못된 입력·실패 불변성 검증을 수행한다.
5. 한국어 사용자 문서, 정식 영문 API/DocC, 예제와 자료 형식 변경 기록을 갱신한다.
6. 코드 재리뷰의 유효한 결함을 수정한 뒤 회귀 검증하고 해당 단계만 완료 표시한다.

전체 최종 시나리오는 다음 세 가지로 고정한다.

- **모듈 합성과 정책:** 두 독립 기능, 중첩 영역, 두 창에서 이동·모달 결과·
  지연 승인을 수행하고 형제 상태와 단일 전환 권한을 확인한다.
- **삭제된 데이터와 복원:** 일부 상세가 무효인 저장 자료를 복원해 유효한 탭과
  창을 살리고, 검사 중 새 이동·취소·정책 거절을 재현한다.
- **진단에서 회귀 방지까지:** 딥링크 검사 → 명시적 실행/녹화 → 자료 내보내기 →
  새 테스트 프로세스 재현 → 수정된 기대값 검증 → 체크포인트 이동을 연결한다.

최종 검증은 아래의 기존 게이트를 재사용한다. 문서만 변경하는 현재 계획 단계에서는
문서 무결성만 검사하며, 구현 검증을 완료했다고 표시하지 않는다.

```sh
./scripts/principle-gates.sh --platforms=all
swift test --enable-code-coverage --jobs 2
./scripts/generate-coverage-report.sh coverage.lcov coverage-full.lcov
./scripts/validate-coverage-report.py coverage.lcov --minimum-line-coverage 85
./scripts/summarize-coverage-report.py --gated coverage.lcov --comprehensive coverage-full.lcov --output coverage-summary.json
./scripts/sanitizer-smoke.sh thread
./scripts/sanitizer-smoke.sh address
./scripts/performance-smoke.sh
./scripts/migration-consumer-smoke.sh
```

새 회귀 suite를 sanitizer·성능·플랫폼 검증에 연결하고, 해당 테스트가 실제로
실행됐는지 확인한다. `.github/workflows/platforms.yml`의 runtime matrix와 동일한
host 검증, 새 Inspector의 실제 조작 검증도 기록한다. 컴파일만 성공한 플랫폼을
실제 UI 동작 확인으로 표시하지 않는다.

배포 전에는 Xcode 26.6 / Swift 6.3 고정 도구와 실제 소비자 앱 통합 검증이 필요하다.
현재 Xcode 27.0 / Swift 6.4에서 통과한 기존 결과는 새 기능 완료의 증거가 아니다.
태그 뒤 정확한 배포 버전을 사용하는 소비자 검증과 원격 일치는 별도 배포 단계다.
