# Restoration operation lifetime and admission

Verification narratives below were recovered from earlier work. They describe
historical scoped observations, not fresh evidence for this recovery commit.
See the recovery validation matrix for newly rerun exact-source results.

This 7.0 development contract covers application partial-restoration validation
and history validation. It does not claim a calibrated release memory budget.

## Ownership and counting

`RouterStoreConfiguration.maximumActiveRestorationOperationCount` defaults to
**8**, a provisional, uncalibrated value. `nil` explicitly opts out; zero and
negative values prevent planning (negative values normalize to zero).

Each Store owns one `RouterOperationRegistry` for restoration. Both its partial
restore APIs and every `RouterHistory` attached to that Store use this registry,
even when calls use different validator values. A registry is not created per
request, per validator, or per history adapter.

One slot represents one actual planner task. It includes that plan's sequential
route checks, replacement checks, and fallback callback. It is reserved before
creating the task and retained until the entire operation actually terminates.
Timeout or caller cancellation settles the caller exactly once and requests
cooperative cancellation; it **does not** return the slot while application work
is still alive. Late completion cannot apply state or produce a second result.

This budget is separate from policy/authorization capacity. Its count is not a
count of requests, callbacks, timeout tasks, queued requests, or policy tasks.
Snapshot decoding and native UI work are outside its scope. The registry can
outlive a Store while a noncooperative operation is still alive, but the library
operation closure does not retain the Store. Application closures remain
responsible for their own captures.

Swift cancellation cannot forcibly stop application code. A validator that
never returns keeps its slot indefinitely. Synchronous MainActor blocking also
prevents the timeout from running; this feature makes no hard real-time promise.

## Admission failure

At capacity, no planner task or application callback is created. The API throws
`RouterPartialRestorationError.operation(RouterRestorationOperationFailure)`.
The failure has a stable extensible code, `.capacityExceeded`, and typed
`maximumCount` / `activeCount` details. Unknown future codes remain representable.
Library-generated admission failures retain no route payload, callback reason,
or app error text; their description contains only the code.

A failed or cancelled restoration does not apply a partial plan or increment the
Store revision. Ordinary navigation remains available when restoration capacity
is exhausted. History reports the same failure through its validation result.

## Verification boundaries

`RouterRestorationOperationBudgetContractTests` exercises the production planner
and registry directly, including 1,000 saturated attempts for timeout, caller
cancellation, and noncooperative fallback; late exit and slot reuse; sequential
callback counting; pre-admission cancellation; and extensible diagnostic coding.

`RouterRestorationOperationBudgetTests` exercises the canonical Store engine and
public data-based restore API: 1,000 retries with fresh validators; default,
zero, negative, and explicit unbounded configuration; shared history admission;
no partial commit; actual-exit recovery; and Store/registry deallocation.

The restoration runner's `bypass-validator-admission` negative control removes
reservation and registry ownership, reproducing the pre-fix planner task body.
Tests must fail on actual admission/counting behavior, not a compile/setup error.
Both runners preserve source hashes, logs, and prior attempts.

Linux runner results validate the compiled production Foundation/Core and Store
engine boundaries. They do not validate native SwiftUI rendering, animation,
Apple lifecycle callbacks, the full package, release calibration, or minimum
supported Apple toolchains. See the run provenance for exact substitutions.
