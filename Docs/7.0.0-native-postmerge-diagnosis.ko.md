출시 준비는 차단 상태다. 아래의 좁은 runtime 수정과 원래 native 실패의
인과관계를 구분한다. 통과 재실행을 과거 실패의 해결 증거로 취급하지 않는다.

## 순서를 고정해 확인한 queued repair 경합

실패한 native open은 canonical scene 제거를 Store에 요청한다. 이 요청이
다른 Store 작업 뒤에서 기다리는 동안 같은 native scene이 나타나면 lifecycle
modifier가 restoration ticket을 소비한다. 기존 구현은 native open 반환 직후
ticket을 확인했지만, 나중에 실제 repair를 실행할 때는 같은 ticket인지
재검증하지 않았다. 따라서 이미 나타난 scene의 canonical state를 제거할 수 있었다.

`appearanceFencesQueuedRestorationFailureRepair`는 continuation과 request
observation으로 이 순서를 고정한다. Sleep이나 재시도에 의존하지 않는다.

- appearance 없는 대조군: native error의 canonical repair가 그대로 적용된다.
- matching appearance가 먼저 발생한 케이스: 수정 전에는 scene이 제거되고
  revision이 추가 증가하여 실패했다.
- 수정: repair의 execution precondition에서 동일 restoration ticket을 다시
  검사한다. 전체 `RouterSceneLifecycleTests` 21개가 통과했으며 기존 genuine
  failure repair, 다른 lifetime 보호와 driver 교체 대조군도 유지했다.

공개 API, policy 우회 범위, 오류 분류와 native 재시도 정책은 변경하지 않았다.

임시 계측을 제거한 수정본을 Xcode 27.0 (27A266a), Swift 6.4에서 빌드해
visionOS 27 Simulator의 native allow/reject/cancel 세 시나리오가 모두
통과했다. CI 정책 테스트 94개와 변경한 `platforms.yml`의 `actionlint`도
통과했다. raw actionlint는 기존 `concurrency.queue` 문법을 인식하지
못했다. 저장소의 정식 `check-ci-workflows.py`는 검토된 정확한 위치와
값의 호환 처리를 이미 포함하며, 변경 없이 실행해 checksum-pinned
actionlint 1.7.12로 11개 workflow가 모두 통과했다. raw 진단도 보존했다.

같은 수정본의 Xcode 27 전체 principle gate도 통과했다. Debug 패키지
테스트 1,357개(기존 의도된 known issue 1건), DocC 세 제품, 공개 API
baseline, 문서 Swift 컴파일 9건, 독립 소비자와 generated scenario,
source lint, recursive deep-link 및 의도된 fail-fast 검증을 포함한다.
Release 구성에서도 같은 1,357개 테스트와 기존 known issue 1건을 확인했다.
Xcode 27 Release에서 iOS, Mac Catalyst, macOS, tvOS, watchOS, visionOS의
두 소비자 빌드와 세 공개 제품의 interface 계약도 통과했다. iPadOS는 같은
generic iOS Simulator 빌드를 공유하고 별도 interface 계약을 검사했다.

## native 계측과 남은 인과관계

임시 메모리 trace에 driver 등록/해제, native close 반환, policy defer,
ticket 생성/소비, open 반환, canonical commit 순서를 기록했다. 출력은 probe
종료 시점에 모았다. 개별 allow/reject/cancel, 한 프로세스의 combined 순서,
기존 rapid-reopen 순서와 event 기반 관찰에서 정상 경로를 확인했다.
정상 trace에서는 surviving driver가 유지됐고, native close 반환 후 복원이
시작됐으며 matching appearance가 open 반환 전에 ticket을 소비했다.

이 계측 실행에서는 원본 native error가 발생하지 않았다. 따라서 새로 재현한
queued repair 경합이 원본 CI 실패의 원인과 같다고 아직 결론 내리지 않는다.
임시 계측과 관찰용 probe 변경은 제품 변경에서 제거했다.

후속 실패의 순서를 보존하기 위해 vision probe에 공개 콜백만 관찰하는
bounded trace를 남겼다. native close 시작/반환, appearance 시점의
canonical state, policy defer와 driver 바깥 boundary의 수명을 최대
256개까지 메모리에 모아 종료 시 출력한다. 내부 driver 등록이나 ticket
소비를 직접 증명하는 trace는 아니다. 라이브러리 runtime, 관찰 대기 간격,
timeout, 재시도 및 성공 조건은 바꾸지 않았다.

Inspector의 다음 실제 hang에서 원인을 볼 수 있도록 기존 pinned CI에
`watch-inspector-hangs.py`를 추가했다. XCTest의 main-thread-busy 오류가
발생한 해당 Simulator 앱 프로세스만 한 번 샘플링하며 앱을 종료하지 않는다.
수집 실패도 receipt로 남긴다. 실제 로컬 healthy-process sampling과 수집기
종료, 이벤트 필터·중복·PID 재사용 대조 검사를 확인했다. 진단 trigger가 없다는
사실은 앱이 정상이라는 증거가 아니다. 테스트 조건, timeout, retry와 성공
판정은 기존대로 유지한다.

원본 실패와 연결되는 native 실패 trace 또는 원격 hang stack을 확보하고,
그 원인을 수정한 exact-head CI를 확인하기 전에는 이 문서를 출시 완료나
실제 앱 pilot 완료로 해석하지 않는다.
