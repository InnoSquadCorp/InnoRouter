# InnoRouter 6.0.0 배포 실행

시작: 2026-09-16, 기준 HEAD `e6099d3bf4d474a4f2afa153147669cc3a893854`.
사용자 승인: 남은 수정·검증을 순서대로 수행하고 6.0.0 정식 배포까지 진행.

## 현재 검증 범위 — 사용자 결정

2026-09-16 사용자가 앞선 실기기 완료 조건을 변경해 **“시뮬로만 검증해줘”**라고 요청했다.
이에 따라 이후 기기 UI 검증은 전용 Simulator로 제한하고, 실제 iPhone/Watch/TV의
설치·조작·설정 변경은 진행하지 않는다. 실기기 VoiceOver·리모컨·크라운 실사용은
이번 배포의 선행 조건에서 제외하되 **미검증**으로 남긴다. 과거 문서의 실기기 필수
조건보다 이 명시적 범위 변경이 우선하며, 완료 체크로 바꿔 증거가 있는 것처럼 기록하지 않는다.
자동 테스트·sanitizer·coverage·API·문서·플랫폼 빌드·정확한 후보 CI와 발견된 코드 결함
해결 조건은 유지한다. 이미 확보한 macOS native 결과는 이전 증거로만 보존한다.

현재 요청의 종료점: 남은 문제 수정, 미커밋 작업의 커밋·푸시, 정확한 최종 후보의
CI 확인까지 수행해 **배포 가능 상태**를 만든다. 정식 태그·GitHub Release 발행은
이번 작업에서 실행하지 않는다.

범위 변경 후 재검증:

- iOS 27 Simulator: 최신 작업 트리의 플랫폼 테스트 10개 통과, 실패·skip 0. `ios27-simulator-only.xcresult`와 실행 종료 코드 0을 확인했다. 기존 body-only tab-host fixture의 미마운트 State 경고 1건은 남아 있다.
- iPadOS 18.5 Simulator: `NativeSceneSmoke/.build/native-ipad.z7nmYT/runtime.log`의 allow/reject/cancel 및 최종 PASS, 실행 스크립트 종료 코드 0.
- visionOS 2.5 Simulator: `NativeSceneSmoke/.build/native-vision.TTUG72/runtime.log`의 allow/reject/cancel 및 최종 PASS, 실행 스크립트 종료 코드 0.
- 두 native 로그에 FAIL 없음. 추가 macOS UI·실기기 조작은 수행하지 않았다. 이 결과는 아래 Inspector 미해결 항목이나 최종 후보 원격 CI를 대신하지 않는다.

## 설계와 제한

- 문제: 최신 R24 수정은 로컬 검증만 완료됐고, 이전 원격 HEAD의 Xcode 26.6 / Swift 6.3.3 ASan 실행이 signal 4로 종료됐다. native 수명주기·실패 정리 증거와 배포 문서도 남아 있다.
- 제약: macro-first, 공개 제품 3개, Swift 6.3 및 OS 하한 유지. 기존 수정 보존. 실패 테스트·sanitizer·배포 gate를 끄거나 기준을 낮추지 않는다.
- 대안: 로컬 Swift 6.4 성공으로 즉시 태그를 만들기 / 정확한 후보를 원격 하한 toolchain과 native 경로에서 검증한 후 태그 만들기.
- 선택: 후자를 선택한다. CI 성공만으로 미실행 native 인수 조건을 완료 처리하지 않는다. 이 실행 문서의 존재도 배포 승인이 아니다.
- 실패 동작: 원인 미확정 충돌 또는 필수 gate 실패가 남으면 정식 태그·발행을 보류한다. crash report와 원래 exit code를 보존하고 원인을 좁힌다. 이미 공개한 태그를 강제 이동하지 않는다.
- 검증: 아래 단계별 exact SHA·로그·통과/실패/미실행을 연결한다. push마다 원격 parity와 작업 트리를 확인한 뒤 지정된 XcodeBuildMCP cleanup을 실행한다.

## PUB-F01 — native 복구 창 닫기 경쟁 / P2

- 문제: 실제 macro-first SwiftUI 앱에서 native 창 닫기 → deferral → 창 복구 → allow 후 canonical 창은 0개지만 native 창 1개가 남는 반례를 재현했다. 복구된 host의 onAppear를 기다리고 테스트가 닫힌 NSWindow를 강하게 보유하지 않아도 재현됐다.
- 반례: `NativeSceneSmoke`의 allow/reject/cancel 실행. 초기 1회 통과 뒤 반복 실패했고, `.build/native-scene.Ri3HQD/stdout.log`에 canonical=0/native=1/revision=2를 보존했다. 이 초기 성공을 native gate 완료로 사용하지 않는다.
- 제약: Store가 유일한 상태 권한이다. 새로운 공개 API나 AppKit 전용 production bridge를 추가하지 않는다. 다른 살아 있는 창을 닫지 않는다.
- 대안: driver의 value-based dismiss를 시간 지연 후 재시도 / canonical root가 없는 host가 자기 native scene context에서 닫힘을 보정.
- 선택: host-local 보정을 검증한다. 임의 지연은 native 등록 완료를 보장하지 않으므로 쓰지 않는다. driver의 정상 diff 처리는 유지한다.
- 실패 시: native 반례가 계속 실패하면 정식 태그를 보류한다. 단위 테스트 성공으로 native 실패를 덮지 않는다.
- 검증: 같은 앱의 실패→통과 및 반복 실행, scene 인접 회귀, public API와 모든 플랫폼 compile/interface. iPadOS/visionOS 실동작은 macOS 증거와 별도로 남긴다.
- 수정 후 같은 macOS native 앱을 5회 연속 실행해 allow/reject/cancel 모두 통과했다. 로그는 `.build/release600/native-scene-fixed-{1...5}.log`에서 각 실행의 독립 산출물 경로를 연결한다. scene 인접 42 tests + mounted 3 tests도 통과했다. 최종 전체 gate는 수정된 소스로 다시 실행 중이다.

## PUB-F02 — 하한 도구체인 ASan deep-link stack guard / P1

- 원인 증거: run `35079013561`의 `swiftpm-testing-helper-2026-09-16-092728.ips`에서 cooperative worker의 stack guard 접근을 확인했다. 실패 경로는 `TwentyThirdBoundaryRoute.deepLinkURL` → root/feature traversal 반복 → leaf URL 생성이며, R23 depth 64 경계 검사다. 버퍼링된 stderr 위치 때문에 앞서 보인 restoration 테스트 이름을 원인으로 단정하지 않았고, 이 crash report로 실제 경로를 확인했다.
- 문제: Xcode 26.6 / Swift 6.3.3의 ASan Debug에서 생성 진입 허가를 지우는 중첩 TaskLocal scope와 fresh-root 분기의 프레임 비용이 깊은 탐색의 스택을 소진한다.
- 제약: production depth 64 / work 1,024와 경계 테스트를 그대로 유지한다. sanitizer 제외, main-thread 강제 이동, 큰 스택 테스트 worker로 우회하지 않는다. 새 공개 API를 추가하지 않는다.
- 대안: 허용 깊이를 줄이거나 테스트 스택을 늘리기 / 생성 진입 허가를 한 번 소비하는 package-internal permit으로 바꾸고 fresh-root 느린 경로를 분리하기.
- 선택: 후자. 이미 소비된 permit은 사용자 conversion과 새 Task에서 다시 사용할 수 없어야 하고, 독립 root에는 새 context를 준다. root/child accounting·cycle·budget 판정은 바꾸지 않는다.
- 실패 시: 기존 회귀 또는 하한 ASan이 실패하면 태그를 보류하고 원래 crash 및 새 결과를 남긴다.
- 검증: 63/64/65 및 1,023/1,024/1,025 경계, nested conversion/Task/cross-operation 회귀, macro 동작, performance와 전체 gate. pinned ASan의 실제 성공이 필요하다.

## PUB-F03 — durable 순서 fixture의 독립 자동 저장 간섭

- LLDB 직접 launch 진단은 정상 실행됐으나 R19 disk test에서 1회 실패했다. 기존 fixture의 변경된 초기 restore가 remove 후 새 automatic save를 만들 수 있었고, 10회 yield는 remove 수락 barrier가 아니었다.
- 기존/새 save 계약은 유지한다. disk test의 초기 in-memory state와 snapshot을 같게 해 별도의 restore commit을 배제하고 revision 0을 검증한다. 이미 있는 synchronous reservation hook으로 remove ticket 1을 확인한 뒤 load를 해제한다.
- focused 2 tests, local ASan 284 tests, 동일 LLDB 190 tests가 통과했다. 생산 저장소 로직이나 sanitizer 기준은 변경하지 않았다.

## PUB-F04 — visionOS 빠른 재진입 / 로컬 수정 검증 완료

- 문제: native view disappearance 직후 새 immersive enter를 수락하면, 이전 dismissal event 뒤 새 공간이 나타나지 않는 반례가 2회 재현됐다. 완료 event를 기다리는 독립 allow/reject/cancel 시나리오는 통과하지만 이 성공으로 빠른 재진입 실패를 덮지 않는다.
- 제약: canonical state·lifetime/queue ownership 유지, native 효과 완료 전에 다음 효과를 허용하지 않음, 임의 sleep이나 테스트 제외로 우회하지 않음.
- 대안: caller에게 timing barrier 요구 / driver와 native effect queue의 실제 전후 관계를 추적해 원인을 수정.
- 선택: 후자. 아직 원인을 확정하지 않았으며 source/event/system 진단 후 최소 수정을 결정한다.
- 검증: 반복 rapid reopen 반례, allow/reject/cancel 기본 경로, queued cancellation·running effect 회귀, 최종 전체 gate.
- 실패 시: 정식 배포 보류. 로그 `.build/release600/vision-native-rapid2.log` 보존.
- 진단 결과: revision 3의 새 native open 중 오래된 host의 disappearance가 새 lifecycle token으로 revision 4 dismiss를 만들었다(`vision-native-trace1.log`). effect queue 미완료 문제가 아니라 조건부 host boundary와 appearance 소유권 문제였다.
- 수정: immersive host는 canonical root가 비어도 안정된 ZStack boundary를 유지하고 lifecycle modifier는 appearance 당시 token을 보존한다. 영구 mounted 회귀는 새 lifetime을 렌더링한 뒤 이전 host를 detach하고 실제 callback 완료 hook까지 기다려 새 상태가 보존되는지 검사한다. 진단 print는 제거했다.

## Inspector UI 후속 수정 — 최종 검증

앞서 실행한 macOS Inspector 검증에서 실행·취소·payload-redacted export·Timeline 선택과
검색·녹화 시작/종료는 확인했다. 그러나 좁은 sidebar의 녹화 컨트롤 잘림, 검색 결과가
비어도 기존 상세가 남는 표현을 확인했다. 테스트 앱의 `inspectorCatalog` 옵션 누락으로
정상 catalog preview 검증도 미완료다. `.build/release600/inspector-ui-review.md`에
근거를 보존하며, 시뮬레이터 범위 변경을 이유로 이 항목을 통과 처리하지 않는다.

- 수정 설계: 넓이만 강제하는 대신 녹화 버튼을 각기 독립된 List 행으로 분리하고,
  status도 세로 label/value로 표시한다. sidebar는 최소 240 / 권장 300pt를 요청하되
  좁은 화면에서는 줄바꿈을 허용한다. 공개 API와 기본 native control을 유지한다.
- Timeline은 view-local observable projection에서 입력 변경 시에만 필터링한다.
  숨겨지거나 eviction된 선택은 즉시 해제하고, 검색을 지워도 복구하지 않는다.
