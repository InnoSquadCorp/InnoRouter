## 1. 목표와 유지할 계약

- `import InnoRouter` + `@Router` + typed helper의 macro-first 사용법을 유지한다.
- RouterStore만 navigation 상태를 변경한다. History·restoration의 내부 요청 관리가 두 번째 Store가 되지 않는다.
- Swift 6.3+, iOS/iPadOS 18+, Catalyst 18+, macOS 15+, tvOS 18+, watchOS 11+, visionOS 2+를 유지한다. Swift 6.4 전용 취소 API에 의존하지 않는다.
- `Route.routerFeatureCatalog`와 `Route.Feature.<case>`의 공개 사용법은 유지한다. 이번 수정에 새 metadata 이름·호환 alias·제품 추가는 필요하지 않다.
- 현재 15차 수정본과 사용자 소유 `Derived/`, `InnoRouter.xcodeproj/`를 보존한다. 무관한 리팩터링·iOS 17 하향·의존성 업그레이드는 제외한다.
- 정상/거절/취소의 결과와 revision 계약을 보존한다. 회귀를 테스트 기대값 변경이나 품질 기준 하향으로 숨기지 않는다.

## 3. 설계 결정

### D01 — History 요청 소유권은 이벤트 경계에서 이전

- 문제정의: `await store.perform` 뒤의 등록보다 resume/cancel terminal 이벤트가 먼저 도착할 수 있다.
- 제약: Store 이벤트의 순서·공개 outcome·기존 History entry ID와 revision 의미를 바꾸지 않는다.
- 대안 A: 반환 후 Store의 deferral 목록을 조회하여 남은 요청만 등록한다. stale 보유는 줄여도 이미 놓친 terminal의 entry/cursor 정규화는 복구하지 못하므로 채택하지 않는다.
- 선택 B: submission 전에 active ownership을 등록하고, 최초 deferred 이벤트에서 active→pending 이전을 동기적으로 처리한다. re-defer는 새 deferral ID로 이전하고 terminal에서 정확히 한 번 소비한다.
- 실패 시 동작: generation 무효화·stop/reset·실제 caller cancellation과 이미 정상 완료된 ownership 제거를 구분한다. 늦은 반환이 terminal 처리된 항목을 재생성하거나 정상 요청을 `.cancelled`로 오인하지 않는다. 실패 요청 때문에 무관한 요청을 취소하지 않는다.
- 검증: 큐 유무 × 즉시 resume/cancel, re-defer, unchanged, reset/stop, 후속 commit을 장벽으로 재현한다. History entry/cursor/sourceRevision과 잔여 ownership을 함께 비교한다.

### D02 — 공유 복원 작업과 개별 호출자 취소 수명을 분리

- 문제정의: 첫 attach 호출자의 취소 처리에서 공유 observation까지 제거한다.
- 제약: 최초 복원은 중복 실행하지 않고 기존 `.alreadyActive` 사용법을 유지한다. 취소된 호출자는 신속하게 반환해야 하며 storage의 동기 I/O를 강제로 중단하지 않는다.
- 대안 A: catch에서 attachment 개수만 검사하여 observation 제거를 건너뛴다. 초기 복원 결과·상태·예약 저장·manual owner 정리가 여전히 취소된 호출자에 묶여 있어 채택하지 않는다.
- 선택 B: driver가 소유하는 초기 activation 작업과 호출자별 대기를 분리한다. host attachment와 manual activation 소유권을 명시적으로 관리하고, 개별 취소는 해당 호출자의 대기/소유권만 정리한다. 하나라도 유효 owner가 있으면 공유 복원·관찰을 유지한다.
- 실패 시 동작: 마지막 owner 해제 또는 명시적 `stop()`이 전체 작업을 무효화한다. 실제 load/decode/restore 실패는 상태에 드러내고 기존 재시도 계약을 유지한다. 이전 generation의 늦은 완료는 새 observation·상태·저장을 건드리지 않는다. 먼저 시작한 manual activation의 취소가 뒤에 성립한 manual ownership을 지우지 않게 한다.
- 검증: attach A/B, attach+manual, 단독·동시 manual 호출, 마지막 owner 제거, stop→reactivate, load 지연·실패, deferred restore, caller cancellation의 반환과 실제 storage save 완료를 확인한다. 새 task/continuation 보유로 retain cycle이 생기지 않는지도 검사한다.

### D03 — 명확한 Swift 이름 충돌만 전용 진단

- 문제정의: 이름 문자열만 검사해 비충돌 instance 속성은 거절하고 실제 enum case 충돌은 놓친다.
- 제약: generated metadata의 타입·접근 수준·값·순서는 유지한다. 모든 동일 이름 선언을 예약어로 금지하지 않는다.
- 대안 A: `routerFeatureCatalog`라는 이름을 모든 선언에서 금지하거나 metadata를 다시 rename한다. 정상 소비자를 불필요하게 깨므로 채택하지 않는다.
- 선택 B: 직접 선언된 멤버의 종류와 static/instance 구분을 검사한다. instance 속성은 허용하고 실제 충돌하는 static 속성·parameterless case와 생성 nested `Feature` 타입의 충돌은 사용자 선언 위치에서 명확히 진단한다. 함수·연관값 case 등 다른 선언 형태는 실제 compiler 대조로 판단하여 과잉 금지하지 않는다.
- 실패 시 동작: 확정 충돌은 E067 등 기존 진단 체계로 실패한다. 비충돌 소비자는 계속 생성하며 잘못된 중복 코드를 성공으로 취급하지 않는다.
- 검증: expansion 진단 위치·ID, behavior의 instance/static 동시 소비, 직접 consumer compile-pass/compile-fail을 모두 확인한다.

### D04 — 조건부 멤버의 활성 여부는 컴파일러에 위임

- 문제정의: 매크로가 모든 `#if` clause를 활성 선언처럼 취급한다.
- 제약: 현재 매크로의 syntax만으로 사용자 빌드 플래그·SDK 조건을 임의 평가하지 않는다. 조건부 `@FeatureRoute` 자체에 대한 기존 E065 제한은 이번 작업에서 변경하지 않는다.
- 대안 A: 매크로에 build-flag/OS 조건 평가기를 만들거나 모든 조건부 충돌을 무조건 진단한다. 컴파일러와 다른 판정을 하거나 지원 범위를 넓히므로 채택하지 않는다.
- 선택 B: 직접 확인 가능한 충돌에는 D03을 적용한다. 조건부 멤버는 unconditional E067 판단에서 제외하고, 해당 구성의 실제 활성 선언 충돌을 컴파일러가 검증하게 한다.
- 실패 시 동작: 비활성 충돌 선언은 컴파일을 막지 않는다. 활성인 실제 충돌은 컴파일 실패를 유지한다. 이 경우 일반 Swift 충돌 진단을 허용하며, 항상 E067이 나온다고 문서·테스트에서 약속하지 않는다. 생성 자체를 무조건 생략하여 정상 feature metadata를 누락시키지 않는다.
- 검증: 같은 fixture를 flag off/on으로 각각 컴파일한다. nested `#if/#elseif/#else`, 플랫폼 조건, instance/static 구분을 조합한다. 성공 빌드에서는 생성 metadata를 실제로 사용하여 단순 생성 누락도 검출한다.

- [x] 완료/실패/미실행을 증거 문서에 나누어 기록하고 소스 변경·사용자 변경 보존 상태를 확인한다.

완료 조건: AC16. 기존 테스트 통과뿐 아니라 이번 반례와 실제 consumer·mounted host 검증까지 통과함. 실행하지 못한 환경 검증은 미완료로 남김.

## 6. 검증 실행과 증거 기준

1. 단계별 focused tests 및 consumer red/green. 느린 저장소와 queue는 명시적 gate로 제어하고 제한 시간은 hang 감지에만 사용한다.
2. `swift test --jobs 2 --no-parallel`, `./scripts/principle-gates.sh --platforms=all`로 전체 package·API·문서·consumer·플랫폼 compile/interface를 검증한다. 중복 실행은 같은 수정본·도구의 로그가 있으면 합리적으로 생략하고 출처를 기록한다.
3. `./scripts/sanitizer-smoke.sh thread`와 `address`를 실행한다. 신규 회귀 suite가 두 필터에 포함되도록 한다.
4. coverage를 새로 수집한 뒤 저장소 스크립트로 내보내고 현행 기준을 검증한다. `./scripts/performance-smoke.sh`, SwiftFormat/SwiftLint 및 `./scripts/lint-source-gates.sh`, `git diff --check`를 확인한다. 기존 threshold를 낮추지 않는다.
5. macro consumer는 현재 도구와 프로젝트의 pinned Swift 6.3 도구에서 debug/release로 확인한다. pinned 환경이 없으면 검증 미완료로 표시한다. 플랫폼 compile 성공을 실제 native 동작 성공으로 부르지 않는다.
6. commit 전에는 HEAD만으로 미커밋 후보를 식별하지 않는다. 변경 파일 목록·patch 해시·도구·명령·로그·실행일을 함께 기록하고, 커밋 후에는 정확한 SHA로 연결한다.

15차에서 남은 native visionOS immersive·정확한 원격 후보 검증은 별도 배포 게이트다. 이번 History/restoration/macro 수정의 통과로 그 게이트를 자동 완료 처리하지 않는다.

## 7. 변경 분리와 인계

구현 후 별도로 커밋·푸시를 요청받으면 아래 논리 단위로 분리한다. 각 커밋은 대응 회귀 테스트를 포함하고 통과해야 한다. T01의 공통 테스트 기반은 먼저 분리할 수 있지만 실패 상태의 테스트만을 배포 브랜치에 발행하지 않는다.

- 테스트 동기화 기반 및 Q02 보강.
- History ownership 수정 + F01 회귀.
- 공유 restoration activation 수정 + F02 회귀·mounted 검증.
- 직접/조건부 macro 충돌 수정 + F03/F04/Q01 expansion·behavior·consumer.
- 공통 검증 연결·문서·증거 정리.

15차와 겹친 파일을 통째로 stage하지 않고 diff/hunk 의존성을 확인한다. 자동 `git add -A`, 기존 사용자 변경 삭제, 이슈 해결을 위한 강제 reset을 하지 않는다. 수정이 인수 기준을 깨뜨리면 해당 변경을 고쳐 재검증하고, 검증 기준을 약화하여 통과시키지 않는다.

성공한 push가 있을 때에만 exact-SHA 원격 CI·parity·worktree 확인을 끝낸 후 사용자 지침의 XcodeBuildMCP cleanup을 수행한다. 활성 build/test/compiler를 중단하지 않으며 회수 용량·최종 여유 공간 또는 skip 사유를 보고한다.

최종 인계는 **구현 완료 / 로컬 검증 / 미실행 환경 / 원격 검증 / 배포 승인**을 구분한다. 이 계획의 완료나 로컬 테스트 통과는 태그·릴리스 승인이 아니다.

## 2026-09-14 후속 정정 — 18차 재검토

16차 실행 로그와 당시 통과 사실은 보존한다. 다만 후속 17·18차 반례에서 activation 예약~worker 진입, 내부 성공~caller 반환, 같은 ID의 deferral timer 재사용, 연관값 catalog case, feature payload의 부모 `Self` 문맥에 추가 결함이 확인되었다. 따라서 16차의 T01·T03~T06 및 AC02·AC08~16 완료 표시는 당시 후보에서 확인한 범위로 한정한다.
