## 확인된 사실과 설계 전제

### 확인된 사실

- 직전 리뷰에서 현재 빌드에 링크한 독립 프로그램으로 네 결함과 변형을 각각 3회 재현했다.
  이번 계획 작성에서는 현재 코드와 보존 로그를 대조했다. 제품 테스트를 새로 실행한 결과로 합산하지 않는다.
- 직전 전체 테스트 417개와 공개 API 기준선/예산 1149 / 207 / 222는 통과했다.
  기존 intentional known issue 1개가 있으며 새 실패와 구분한다.
- F01: 빈 pending slot은 cancel해도 generation이 변하지 않는다. persistence restore는 별도 수명과
  await 이후 Task 취소를 검사하지 않아 취소한 링크가 되살아난다.
- F02: 원본 history는 validator 실행 전 revision을 고정하지만 재생은 `expectedRevision: nil`을 사용한다.
  큐에서 stale로 거절된 원본과 달리 재생은 추가 commit 후 실패한다.
- F03: recorder는 모든 resolution 요청의 cancelled terminal에서 cancel control을 생략한다.
  `resolve(.allow)` 실행 중 Task 취소까지 빠져도 complete로 표시한다.
- F04: history preflight는 allow + cancelled 관찰 결과만으로 수명 누락을 판정한다.
  해당 요청의 명시적 cancel control을 추가해도 정상 자료를 거절한다.
- 현재 sanitizer 필터에는 `RouterLinkPipelineTests`가 없다. F01 회귀를 그 suite에 추가한다면
  필터도 갱신해야 sanitizer 실행이 해당 수정의 증거가 된다.

### 유지할 계약

- macro-first, 단일 `RouterStore`, 공개 제품 3개, Swift 6.3+ 및 현재 OS 하한을 유지한다.
- 일반 plan은 exact-state, history는 navigation-only다. 취소·거절 요청의 추가 commit/revision은 0이다.
- 재생은 실제 reducer·정책·스케줄러를 사용한다. 관찰 상태 복사, 거절 결과 강제 반환, 기대값으로
  실행 명령을 생성하는 방식은 허용하지 않는다.
- 앱 소유의 비협조적인 동기 I/O를 강제 중단하거나 성공한 과거 commit을 rollback하지 않는다.
  늦은 결과의 적용을 차단하고 각 작업이 소유한 자원만 정리한다.
- iOS 17 하향, 5.x 호환층, 새 기능군 추가, 원격 배포는 이번 수정 범위가 아니다.

### R6R8-T01 — pending-link 취소와 복원 수명

접점: `RouterPendingLinkPersistence.swift`, `RouterPendingLinkSlot`, `RouterLinkPipelineTests`.

- [x] cancel 시작 시 이전 복원을 무효화한다. 빈 slot에서도 효력이 있어야 한다.
- [x] load/decode 전후와 slot 제출 직전 Task 취소·수명·slot generation을 확인한다.
- [x] 취소된 복원은 `CancellationError`로 종료하는 안을 적용하고, 최신 작업만 status를 갱신한다.
  이전 성공/실패/catch/defer가 새 작업의 상태를 덮어쓰지 않게 한다.
- [x] 최종 저장소를 실제 저장 가능한 test storage로 확인한다. stub remove 호출만으로
  cancel 뒤 비어 있음이나 새 값 보존을 판정하지 않는다.
- [x] 정상 round trip, 새 submit, 새로운 restore, 중복 cancel, load/decode 실패 및
  저장/삭제 실패를 대조한다. I/O 실패는 성공한 내구성 취소로 보고하지 않는다.

완료 조건: AC01. 취소 뒤 이전 링크의 복원·재저장 0, 새 작업에 대한 영향 0.

### R6R8-T02 — 원본 실행 조건과 취소의 값 모델

접점: request observation, Store scheduling/deferral, fixture/recorder metadata.

- [x] 원본 expectedRevision을 검사 시점이 아닌 실제 preparation 시점에서 기록한다.
  validator 대기로 submission 시점 상태가 바뀌어도 원본 제약을 잃지 않는다.
- [x] revision 제약 없음과 값 누락을 구분한다. capture baseline 이전 제약도 표현하거나
  구체적으로 사전 거절하며 unsigned underflow·overflow를 방지한다.
- [x] 취소 결정/실행 중 요청 취소/history 수명 종료의 소유 ID와 event 순서를 정의한다.
  중복 취소, 이미 terminal인 요청, 다른 history/새 generation에 대한 기준을 명시한다.
- [x] 형식 5의 필수 필드, 오류, completeness, 생성자·decode 규칙을 확정한다.
  기대값 설정과 JSON 왕복이 새 원본 메타데이터를 유실하지 않게 한다.

완료 조건: F02~04를 정상 반복 rebase와 함께 설명하는 하나의 값 모델이 있고, 정보가 없을 때의 실패가 명시된다.

### R6R8-T03 — 최초 history revision 제약 재현

접점: `RouterHistory`, `RouterTestStore.startHistoryNavigation`, scenario replay.

- [x] 기록된 revision 제약을 replay baseline 기준으로 변환해 production perform에 전달한다.
- [x] 최초 요청, validator 대기, 큐 진입/실행, requireUnchangedState/rebase 재개의

- [x] 앞 요청이 commit한 뒤 history가 stale로 거절되어 최신 navigation과 scene을 보존하는지 확인한다.
- [x] 일반 exact-plan 요청에 같은 기록 정보 누락이 있는지 접점을 확인하고 공통 모델을 재사용한다.

완료 조건: AC02. 정상 자료는 성공하며 stale history의 추가 policy/commit이 원본보다 늘지 않는다.

### R6R8-T04 — 재개 요청의 실제 취소 기록

접점: Store cancellation observation, `RouterScenarioRecorder`, control graph.

- [x] 실제 취소가 접수된 소유 요청과 시점을 수집한다. cancelled terminal만 보고 cancel을 만들지 않는다.
- [x] resolve(.cancel) 결정과 resolve(.allow) 도중 Task 취소를 구분해 중복·누락 없이 기록한다.
- [x] 활성·큐 대기·반복 deferral의 일반 action/history 모두 동일한 취소 계약을 사용한다.
- [x] 기록이 중단되거나 제어 원인을 포착하지 못하면 incomplete로 내보낸다.
- [x] 정책 gate를 해제하기 전에 replay 취소 terminal과 소유 작업 정리를 확인한다.
  늦은 allow/reject/deferral과 무관한 요청·관찰자도 검사한다.

완료 조건: AC03. cancel control을 손으로 보완하지 않은 실제 recorder 출력으로 재현된다.

### R6R8-T05 — 명시적 history 취소와 미지원 수명 구분

접점: `RouterScenarioHistoryValidator`, 공통 control validator, source generator.

- [x] 원인과 해당 requestID의 submit/start/cancel/terminal 순서를 함께 검증한다.
- [x] 명시적 취소가 있는 유효 history는 generator/runner 모두 통과하고 추가 revision 없이 끝난다.
- [x] stop/reset 또는 앱 수명 조건이 표현되지 않은 자료의 구체적 사전 거절을 유지한다.
  근거 없는 cancel control 하나를 추가해 모순이 숨겨지지 않게 한다.
- [x] 다른 ID, terminal 이후 cancel, 잘못된 producer/deferral, 원인·revision·action 불일치를
  generator와 runner가 공통으로 거절한다. policy 호출·새 revision·새 pending은 0이다.
- [x] 기존 창 보존, 반복 rebase, 최초·재개 action 변조 회귀를 유지한다.

완료 조건: AC04. 지원 가능한 취소와 수명 누락을 동일한 관찰 terminal만으로 분류하지 않는다.
